## 一、一句话结论

腾讯音乐花了两年、400+ Agent、一整套平台，最后用数据证明了一件事：

> **编码提效 ≠ 交付提效。AI 最确定的价值是降低开发工作量，不是提升需求吞吐量。**

这句话值钱的地方在于：它是**先建了大平台之后才得出的结论**。对还没建平台的团队，等于省了两年。

## 二、三重挑战（他们踩过的坑，几乎是通用剧本）

| 挑战 | 具体表现 | 本质 |
|---|---|---|
| **工具碎片化** | 多工具并存、能力各自为政；编码环节渗透高，需求/测试/运维渗透低；外部工具有代码外泄风险；个人经验无法复用；数据标准不一难采集 | 工程师个人能用好，团队层面没有能力沉淀 |
| **流程断层** | 编码快上来了，但需求评审还线下凑人、测试还等提测才介入；经验集中在少数探索者；产出风格不一致；测试周期反成新瓶颈 | AI 不知道任务处于哪个研发阶段，单点能力无法端到端协同 |
| **价值难证** | 用的人很多，但答不出"需求交付周期缩短多少"；代码生成量、工具调用次数映射不到业务结果 | 使用量 ≠ 业务价值，度量停在工具层 |

**对应三个组织级问题**：
1. AI 如何安全可控进入企业 → 建企业级工具/Agent 分发基建
2. AI 如何贯通研发链路 → 测试左移、自动用例、一站式链路
3. AI 如何证明创造价值 → 度量体系 + 有效代码识别

## 三、他们的解法（三层，按建设顺序）

### 第一层：基建 —— 三道门槛

1. **统一接入**：外部工具做企业级改造，接入内部认证、权限、审计
2. **统一复用**：Agent / MCP / Skill 不能各团队自建，否则重复配置、经验不沉淀
3. **统一治理**：和需求管理、代码管理、发布系统、知识体系打通

**成果**：沉淀 **400+ 共享型 Agent**，配置复用覆盖率从 **28% → 100%**。
**原话**："自建工具只是载体，组织复用才是价值。"

**工具形态选型（2024 调研数据）**：
- IDE 分布：VS Code 44% + JetBrains 26% = 覆盖 70% 开发场景
- AI 使用场景：**IDE 内编码只占 50%**，剩下一半在需求、知识、测试、交付
- 结论：**同一能力内核，插件 + CLI 双入口**。插件覆盖编码，CLI 串联流程，不重复建设

> 这条对我们的意义：如果只做 IDE 插件，天然只能覆盖一半场景。

### 第二层：链路 —— 7 节点 + 人工门禁

```
需求澄清 → 方案设计 → 编码 → 代码审查 → 开发自测 → 测试验收 → 发布反馈
   ↓门禁     ↓门禁     ↓门禁    ↓门禁      ↓门禁      ↓门禁      ↓回写
```

每个节点由**单一职责 Agent** 执行，产出**结构化产物（Artifact）**，通过**人工门禁**连接下一节点。

核心机制三件：
- **状态机**约束流程走向（不许跳步）
- **Artifacts** 承接阶段上下文（解决"阶段失忆"）
- **统一调度**控制执行边界（解决"规范失控"）

质量四层防护（"生成即验证"）：
1. 生成前：P0 编码规范、业务规则前置嵌入 Prompt
2. 生成时：本地 Hook 即时检测，P0 问题当场拦截
3. 生成即校验：自动补 Review 用例
4. CI 后：转测前 P0+P1+P2 全面检测 + 修复 Agent

**试点效果（关键）**：
- 角色间协同时间 **-83%**
- 试点业务月需求吞吐量 **+56%**
- **但**：适配效果最好的是 **3 天以内需求，约占总任务量 60%**
- 明确边界：不替代 TAPD/代码库/发布平台；不承诺复杂项目完全自主

### 第三层：度量 —— 四层指标

| 层级 | 回答什么 | 指标 |
|---|---|---|
| L1 使用覆盖 | 多少人在用 | 使用人数、团队覆盖率、场景分布 |
| L2 生成有效 | AI 代码是否有效 | 生成率、采纳率、入库率 |
| L3 需求维度 | 是否覆盖业务交付 | AI 需求覆盖率、AI 浓度 |
| **北极星** | 是否带来交付价值 | **需求交付周期、需求吞吐量** |

并行成本体系：Token 消耗、模型调用规模、实际费用。

**他们的实测结论**：
- 试点团队需求覆盖率 80%，需求 AI 入库率 **90%+**
- **但**："AI 用得越多，月需求完成量越高"——**不成立**。AI 使用强度增加，需求吞吐量没有显著变化。

## 四、他们解决的两个硬技术问题（这部分最实操）

### 1. Agentic Coding 让代码采集失效

**问题**：传统采集是"单会话、单目录"。但父 Agent 会拆任务给多个 Subagent，在不同 Worktree 并行改、并行提交。代码可能在另一个 git 目录、另一个分支，甚至提交后工作区已 clean，主仓基线看不到。

**他们的结论**：采集对象不再是"会话目录"，而是**本次 Turn 实际触达的所有 Worktree 集合**。

**双层对账方案**：
1. **Turn 建基线**：提交 Prompt 时创建 `baseline_id`，首次触达文件时记 HEAD 和 dirty 状态
2. **PostToolUse 实时采集**：每次工具修改后触发，拿文件 diff、Bash checkpoint
3. **Subagent 对账**：Subagent 结束时按 `agent_id` 单独对账，提交/未提交都能恢复
4. **Parent Stop 兜底**：父任务结束做最终补偿，去重后上传

**四不**：不漏采（committed/dirty/untracked 全覆盖）、不误采（只处理本轮触达的 Worktree）、可恢复、可扩展（适配 apply_patch / Bash 编辑 / 文件写入）。

### 2. 怎么算"AI 写了多少有效代码"

**两步**：
1. **先定义有效行**：排除注释、空行、纯格式变更，输出可用于比较的 Commit 有效行
2. **再匹配 AI 贡献**：四层由粗到细 —— 长度 diff 过滤 → 完全一致匹配 → Jaccard 预过滤 → 字符级精确匹配

**再往上关联**：统一主键 `repo / commit / file / line`，代码行 → Commit → 版本 → 需求，最终算出**需求 AI 入库率**和**版本 AI 入库率**。

## 五、四条最值得抄的经验（他们自己总结的）

1. **AI 让我们敢于重做流程** —— Agent 让前置对齐与并行成为可能，这是流程重构的前提，不是结果
2. **度量必须可归因** —— 从效率指标逐步走向业务指标，不能停在"用了多少次"
3. **先结构化，才可度量** —— 原文原话："如果流程都是零散的、线下的，根本没法衡量 AI 到底带来了多少价值。"
4. **判断与责任归人，执行与认知扩展交给 AI** —— 三层协作：人负责判断/架构/评审并承担最终责任；人机协作拓展认知边界（暴露"未知的未知"）；AI 主执行边界明确的任务

## 六、对 EZR 的对照（我们家的问题在哪个位置）

| 他们的建设 | 我们现状 | 差距判断 |
|---|---|---|
| 统一接入（认证/权限/审计） | OpenClaw 已跑通，但以个人工作流为主 | **部分具备**，缺团队级分发与审计口径 |
| 400+ 共享 Agent、配置复用 100% | Skill 有沉淀但分散，复用率未知 | **明显缺**：没有 Skill 市场/复用率指标 |
| 插件 + CLI 双入口 | CLI 为主（OpenClaw），IDE 插件少 | **缺 IDE 入口**，覆盖不到 44% VS Code 场景 |
| 7 节点 + 人工门禁 | 有需求→开发→测试→发布，但门禁靠人盯 | **缺状态机和结构化产物** |
| 四层质量防护 | 靠测试同学人工兜底 | **最薄的一环**，没有生成前规则约束和 Hook 拦截 |
| 四层度量 + 北极星 | 有工时、有 Bug 数，没有"需求 AI 入库率" | **完全缺**：现在答不出"AI 到底帮了多少" |
| Turn 级代码采集 | 无 | 不做也没关系，但**要先定"怎么算有效"** |

## 七、直接可用的三条（针对当前待拍板的 AI Coding 编排层）

### 判断 1：不要先建平台，先量一次

他们的顺序是"基建 → 链路 → 度量"，但拿到真相的是**度量**。
我们现在的状态比他们起步时更轻，**先花两周做一次最小度量**，比先建编排层更划算：

- 选 1 个真实定制项目
- 记录：估时 / 实际周期 / 返工次数 / 一次验收通过率 / 线上 Bug 数
- 对比一个不用 AI 的同类项目

**判据**：如果两周后答不出"这个项目 AI 省了多少人天"，那建编排层也只是把不确定性放大。

### 判断 2：编排层的第一版不该是"全链路"

他们明确说了：**最好用的是 3 天以内的需求，占 60%**；复杂项目不承诺自主。
所以编排层第一版应该只做**两个门禁**，不是七个节点：

1. **需求澄清门禁**：AI 先扫需求，把模糊点和与现有设计冲突点列出来，人工确认后才进开发
2. **提测门禁**：AI 生成用例 + 覆盖度检查，不达标不许转测

选这两个的理由：他们的数据里，需求澄清是协同时间最长的环节（凑人 1-2 天），提测是最容易变成瓶颈的环节。**这两个卡点解决，协同时间就能下去；其他五个节点是锦上添花。**

### 判断 3：度量口径要现在就定死，不能等

我们要定的最小口径（不用做系统，先用表）：

| 指标 | 怎么算 | 为什么 |
|---|---|---|
| 需求 AI 覆盖率 | 用了 AI 的需求数 / 总需求数 | 回答"渗透到哪了" |
| AI 采纳率 | AI 生成被保留的行数 / 生成总行数 | 回答"生成的东西有没有用" |
| 一次验收通过率 | 一次验收通过的需求数 / 提测需求数 | 回答"质量有没有变好" |
| 需求交付周期 | 从需求确认到上线 | **北极星**，其他都是过程指标 |

**关键纪律**：这四条必须在一个项目开始前就定义，不能项目结束再补——补出来的数是讲故事，不是度量。

## 八、不适用 / 要打问号的地方

| 项 | 问题 |
|---|---|
| 400+ Agent、复用率 100% | 自述口径，"复用率"怎么定义未说明。100% 这个数太整，可能是"配置都走统一模板"而非"都被真实使用" |
| 协同时间 -83% | 未说明基线怎么测的。协同时间本身就是最难量化的部分 |
| 吞吐量 +56% | 试点期数据，可能有霍桑效应（被关注所以效率高） |
| 需求 AI 入库率 90%+ | 入库率高不代表价值高，可能只是 AI 写的格式类改动多 |
| METR "2 小时任务成功率 50%" | 引用的是行业研究，非他们自己数据，且任务定义宽泛 |
| 成本 | 只提"追踪 Token 消耗"，**没给任何金额**。这是最该问但最常被跳过的一项 |
