# Day16｜Skill评审机制：从个人工具到组织资产

## 今日主题

Day15 讲了目录、发布和生命周期。今天继续往前推进一个管理动作：**Skill 进入目录之前，必须先经过评审。**

核心问题是：

> 一个 Skill 不是“写出来就能上架”，而是要判断它是否值得做、是否能复用、是否安全、是否有人负责。

如果没有评审机制，Skill 很容易变成三类问题：

1. **重复建设**：不同团队写了相似能力，但口径不一致。
2. **价值不清**：能运行，但解决不了真实业务问题。
3. **风险外溢**：权限、数据、口径、自动执行边界没管住。

所以 Day16 要学的是：把 Skill 从个人工具，变成组织资产前，要过哪几道关。

---

## 技术原理（技术视角）

### 1. Skill 评审不是代码评审，而是能力准入评审

代码评审主要看实现质量；Skill 评审要多看 5 件事：

| 评审项 | 要回答的问题 | 不通过的典型表现 |
|---|---|---|
| 场景价值 | 解决哪个高频/高价值问题 | 只是“看起来智能” |
| 输入输出 | 调用前后边界是否清楚 | 输入随意，输出不可验收 |
| 复用性 | 是否能被多人、多场景复用 | 只适合某个人的一次性 prompt |
| 风险边界 | 权限、数据、动作是否可控 | 可能越权看数据或误触发动作 |
| 责任归属 | 谁维护、谁解释、谁下线 | 出问题没人认领 |

Skill 的本质是“可调用能力单元”，所以评审重点不是“写得炫不炫”，而是“能不能被组织安全复用”。

### 2. 推荐的四道准入门

一个业务 Skill 建议经过四道门：

```text
问题评审 → 设计评审 → 灰度评审 → 上架评审
```

| 阶段 | 评审重点 | 产出物 |
|---|---|---|
| 问题评审 | 值不值得做成 Skill | 业务问题卡 / ROI 假设 |
| 设计评审 | 输入、输出、权限、异常是否清楚 | Skill 设计说明 |
| 灰度评审 | 小范围是否真的有人用、有效果 | 灰度数据 + 用户反馈 |
| 上架评审 | 是否能进入目录并承诺维护 | 目录登记 + 负责人 + 版本号 |

这四道门可以很轻，但不能没有。尤其是客户可见、导购触达、经营诊断、自动执行类 Skill，必须先灰度再上架。

### 3. 评审材料要短，但字段必须硬

建议每个 Skill 评审只要求一页材料：

```text
1. Skill 名称
2. 目标用户
3. 业务场景
4. 输入参数
5. 输出结果
6. 使用边界
7. 权限范围
8. 成功指标
9. 负责人
10. 当前状态
```

评审材料不是为了增加流程，而是为了让大家在同一张纸上判断：这个能力到底值不值得进入组织能力库。

## 业务翻译（业务视角）

业务上可以这样理解：

> Skill 评审就是 AI 能力的“上架质检”。不是谁写了就能卖，而是要确认它有场景、有价值、可复用、可治理。

对 SaaS CRM 来说，Skill 一旦进入客户场景，就不只是工具，而会影响客户经营判断。比如：

- 推荐错会员，导购会浪费触达机会。
- 话术不合规，可能影响品牌体验。
- 指标口径不准，客户经营会误判。
- 自动动作越权，可能造成数据和权限风险。

所以管理者要盯住一句话：

> 低风险内部提效 Skill 可以快；客户可见和自动执行 Skill 必须稳。

## 典型场景（EZR 业务版）

### 场景 1：导购话术生成 Skill 评审

评审时不要只看“话术写得像不像人”，要看：

| 评审点 | 要求 |
|---|---|
| 场景 | 新品推荐、沉默会员唤醒、生日关怀等是否拆清楚 |
| 输入 | 会员画像、最近购买、偏好、门店活动是否明确 |
| 输出 | 是否区分“推荐理由”和“可发送话术” |
| 边界 | 是否避免承诺库存、价格、权益等不确定信息 |
| 指标 | 导购采纳率、触达率、转化率是否能跟踪 |

如果只生成漂亮文案，但没有导购采纳和转化反馈，就不能算一个成熟 Skill。

### 场景 2：经营诊断 Skill 评审

经营诊断类 Skill 最重要的是口径稳定：

```text
事实数据 → 指标解释 → 异常判断 → 建议动作
```

评审必须问：

1. 数据来源是否可追溯？
2. 指标口径是否有版本？
3. 建议动作是否区分确定性和推测性？
4. 客户可见内容是否脱敏？
5. 错误结果是否能回滚和解释？

这类 Skill 不能追求“像顾问”，先要保证“不误导经营”。

### 场景 3：AI Coding / 测试辅助 Skill 评审

研发内部 Skill 可以更快，但也要评审边界：

| Skill | 重点评审问题 |
|---|---|
| 需求改动点分析 | 是否能稳定识别影响范围和依赖系统 |
| 测试用例生成 | 是否覆盖核心路径、异常路径、回归路径 |
| Bug 根因摘要 | 是否标注置信度，避免把猜测当结论 |
| 发版风险检查 | 是否有明确的阻断项和人工确认项 |

内部提效 Skill 的评审目标不是“百分百正确”，而是明确：哪些能自动化，哪些必须人工确认。

## 管理者关注点（成本 / 效率 / 风险）

### 1. 成本

评审机制能避免重复造 Skill。尤其是会员洞察、经营诊断、话术生成、测试用例生成这些高频能力，应该尽量做成共用资产，而不是每个项目单独写一套。

### 2. 效率

评审不是拖慢速度，而是让后续复用更快。只要一页评审材料够硬，后面目录登记、灰度、上架、复盘都会顺很多。

### 3. 风险

越接近客户、数据和自动执行，评审越不能省。内部文本辅助可以快跑；客户可见、自动触达、经营建议、权益动作必须有权限、审计和人工确认。

## 一句话总结

Skill 评审不是加流程，而是把“个人会用的 AI 工具”筛成“组织敢复用的能力资产”。
