# Day29｜Skill 安全边界：权限、审批、回滚与人工确认

## 今日主题

Day28 讲的是 Skill 执行结果如何沉淀，避免每次从零开始。

Day29 继续补一条底线：**业务 Skill 一旦从“生成建议”走向“调用系统能力”，安全边界必须前置设计。**

> 一个能干活的 Skill，价值来自能进入真实流程；风险也来自它真的能影响客户、数据、订单、权益和经营决策。

所以业务 Skill 不能只写“能做什么”，还要写清楚：

- 谁能用；
- 能看到什么数据；
- 能执行到哪一步；
- 哪些动作必须人工确认；
- 出错后如何撤回；
- 过程如何审计。

---

## 技术原理（技术视角）

### 1. Skill 的权限要按“身份 + 场景 + 动作”判断

不要只按账号判断权限。

一个成熟业务 Skill 至少要同时判断三件事：

```text
1. 身份：当前调用者是谁？总部运营、店长、导购、客服、管理员？
2. 场景：当前是在看数据、生成建议、提交审批，还是执行动作？
3. 动作：这个 Skill 准备读什么、改什么、发什么、触达谁？
```

例如导购可以查看自己会员池里的客户跟进建议，但不应该看到全品牌会员明细；运营可以生成活动策略，但大额发券不应自动执行；总部可以配置规则，但敏感动作仍需要审批链。

### 2. Skill 动作要分级，不同级别用不同控制方式

建议把 Skill 动作分成四级：

```text
L0 只读查询：查看数据、读取知识库、生成摘要。
L1 建议生成：生成方案、话术、清单、诊断结论。
L2 半自动执行：生成待执行动作，由人确认后提交。
L3 自动执行：系统直接触发发送、改价、发券、建单、改配置。
```

控制原则：

- L0 / L1 可以相对开放，但要记录来源与口径；
- L2 必须有人工确认与可追溯记录；
- L3 必须非常谨慎，默认先不放开，除非有明确权限、额度、审计和回滚机制。

### 3. 高风险动作必须有审批、限额和回滚

业务 Skill 最容易出风险的动作通常包括：

- 批量触达客户；
- 发放优惠券 / 权益；
- 修改会员标签或等级；
- 调整价格、库存、商品状态；
- 生成对外承诺；
- 批量导出敏感数据。

这些动作不能只靠“提示词约束”。真正可控要靠系统机制：

```text
权限校验 → 风险分级 → 人工确认 → 审批流 → 执行记录 → 异常回滚 → 复盘沉淀
```

## 业务翻译（业务视角）

业务上可以这样理解：

> AI 不能因为“更聪明”就绕过原来的经营权限。越能干活，越要讲边界。

过去 SaaS 的权限主要管“人能点什么页面”。

AI 时代要升级成：

- Agent 能代表谁工作；
- Agent 能调用哪些 Skill；
- Skill 能读哪些数据；
- Skill 能不能改业务状态；
- 改了以后谁负责；
- 出错后怎么恢复。

这不是拖慢创新，而是让 AI 真正进入生产系统的前提。

如果没有这层治理，AI 很容易变成“聪明但不可控的操作员”。

## 典型场景（EZR 业务版）

### 场景：导购客户跟进 Skill

Skill 可以帮助导购生成今日重点客户清单和话术，但边界应该这样设计：

```text
允许：
- 读取导购本人会员池
- 生成重点客户排序
- 生成一对一话术建议
- 推荐适合的商品或权益

需要人工确认：
- 实际发送话术
- 选择触达渠道
- 选择是否发券

需要审批：
- 批量发券
- 高面额权益
- 跨门店客户触达
- 可能引发客诉的营销动作

禁止默认自动执行：
- 未经确认自动群发
- 越权查看其他导购会员
- 自动修改会员等级或核心标签
```

这样 Skill 才既能提效，又不会破坏客户关系和品牌规则。

### 场景：会员经营诊断 Skill

Skill 可以输出沉默会员、流失风险会员、高价值会员分层建议。

但它不能直接把诊断结论写死成会员标签，除非满足：

- 数据来源可解释；
- 规则口径已确认；
- 标签影响范围清楚；
- 有人工审核或灰度机制；
- 标签后续可修正。

## 管理者关注点（成本/效率/风险）

### 1. 不要一开始追求全自动

业务 Skill 的成熟路径应该是：

```text
先生成建议 → 再人工确认 → 再小范围半自动 → 最后少量高确定动作自动化
```

如果一上来就全自动，试点风险会非常高，也容易让业务团队不信任。

### 2. 权限设计要进入 Skill 评审

每个业务 Skill 评审时，至少问 5 个问题：

1. 这个 Skill 读了哪些数据？
2. 这个 Skill 会不会改变业务状态？
3. 哪些动作必须人工确认？
4. 出错以后有没有撤回方式？
5. 执行记录能不能追溯到人、时间、输入、输出和动作？

### 3. 安全不是技术附属，而是商业化前提

如果 EZR 要把 Skill 做成可交付产品，权限、审批、审计、回滚就是商业化能力的一部分。

客户会关心的不只是“AI 准不准”，还会关心：

- 会不会乱发；
- 会不会越权；
- 会不会泄露；
- 出错谁负责；
- 能不能查清楚。

| 审计记录 | 记录哪些输入、输出、动作和责任人 |

## 本日自检

1. 我们现在设计 Skill 时，是只写功能，还是已经写清权限边界？
2. 哪些 Skill 动作会真正影响客户、订单、权益或标签？
3. 有没有把“人工确认点”设计成产品流程，而不是口头要求？
4. 如果 Skill 执行错了，今天能不能查到是谁、何时、基于什么输入做出的动作？

---

## 一句话总结

> 业务 Skill 要进入真实经营流程，必须从第一天就设计权限、审批、回滚和审计；没有边界的自动化，不是能力，是风险。
