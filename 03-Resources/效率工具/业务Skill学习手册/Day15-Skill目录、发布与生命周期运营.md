# Day15｜Skill目录、发布与生命周期运营

## 今日主题

今天进入第三阶段最后一篇：**学会产品化与规模化。**

Day14 讲效果评估，解决的是“Skill 有没有价值”。Day15 要解决的是更偏运营的问题：

> 当 Skill 越来越多之后，组织不能只靠口口相传使用 Skill，而要有目录、发布、下线和复盘机制。

业务 Skill 一旦成为组织能力资产，就不只是某个人写的工具，而是团队可发现、可申请、可调用、可治理、可迭代的能力目录。

---

## 技术原理（技术视角）

### 1. Skill 目录解决“能不能被找到”

一个可运营的 Skill 目录，至少要包含这些字段：

| 字段 | 作用 | 示例 |
|---|---|---|
| Skill 名称 | 让人知道能力是什么 | 会员触达建议 Skill |
| 适用场景 | 说明什么时候用 | 导购每日经营、沉默会员唤醒 |
| 输入要求 | 告诉调用前要准备什么 | 门店、会员范围、时间周期 |
| 输出结果 | 告诉使用后能得到什么 | 会员名单、推荐理由、触达话术 |
| 权限范围 | 控制谁能用、能看什么 | 导购只看自己会员池 |
| 负责人 | 出问题找谁 | 产品负责人 / 技术负责人 |
| 版本状态 | 判断能否生产使用 | 内测 / 灰度 / 正式 / 废弃 |
| 效果指标 | 判断是否值得继续维护 | 采纳率、转化率、节省时间 |

目录不是为了好看，而是为了让团队少问“有没有这个能力”，多问“这个能力能不能解决我手上的问题”。

### 2. 发布流程解决“能不能安全上线”

Skill 发布建议分四步：

```text
草稿定义 → 内部验证 → 灰度使用 → 正式发布
```

| 阶段 | 要验证什么 | 通过标准 |
|---|---|---|
| 草稿定义 | 场景、输入、输出、边界是否清楚 | 能说清楚解决哪个业务问题 |
| 内部验证 | 能不能稳定跑通 | 成功率、准确性、异常处理达标 |
| 灰度使用 | 真实用户是否采纳 | 有目标用户使用并反馈 |
| 正式发布 | 是否值得规模化 | 过程或业务指标有改善 |

不要把“能跑”当成“可发布”。能跑只是技术起点，可发布必须能被真实用户稳定使用。

### 3. 生命周期解决“能不能长期治理”

Skill 生命周期可以按 5 个状态管理：

```text
Draft 草稿 → Beta 内测 → GA 正式 → Maintain 维护 → Deprecated 下线
```

每个状态都要有规则：

| 状态 | 管理重点 |
|---|---|
| Draft | 只验证问题是否值得做 |
| Beta | 小范围试用，允许快速调整 |
| GA | 稳定发布，必须有版本、权限、审计 |
| Maintain | 根据指标持续优化 |
| Deprecated | 明确替代方案和下线时间 |

真正成熟的 Skill 运营，不是不断新增，而是持续判断：哪些扩、哪些改、哪些停。

## 业务翻译（业务视角）

业务上可以这样理解：

> Skill 目录就是公司的“AI 能力货架”；发布流程决定什么能力能上架；生命周期运营决定哪些能力继续卖、哪些能力下架。

管理者要重点问四个问题：

1. 团队是否知道现在有哪些 Skill 可用？
2. 每个 Skill 是谁负责、解决什么问题、适合谁用？
3. Skill 上线前有没有灰度和验收？
4. 长期不用、效果差、风险高的 Skill 是否有下线机制？

没有目录，Skill 会变成个人小工具；没有发布机制，Skill 会变成生产风险；没有生命周期，Skill 会变成维护负担。

## 典型场景（EZR 业务版）

### 场景 1：导购智能助手 Skill 目录

建议把导购相关能力整理成一个目录：

| Skill | 使用人 | 核心输出 | 状态 |
|---|---|---|---|
| 今日重点会员推荐 | 导购 / 店长 | 会员名单 + 推荐理由 | Beta |
| 会员触达话术生成 | 导购 | 微信/企微话术草稿 | Beta |
| 沉默会员唤醒分析 | 运营 / 店长 | 唤醒分层 + 动作建议 | Draft |
| 导购执行复盘 | 店长 / 区域 | 触达完成率 + 转化反馈 | Draft |

这样产品推进时，不再笼统说“做智能导购”，而是能看到每个能力的状态、价值和缺口。

### 场景 2：指标库 / 经营诊断 Skill 发布

指标库类 Skill 不能只看是否能回答问题，还要看口径是否稳定。

发布前建议检查：

```text
1. 指标口径是否有版本
2. 数据来源是否写清楚
3. 输出是否区分事实、判断和建议
4. 客户可见版本是否脱敏
5. 错误口径是否能回滚
```

如果这些没准备好，就只能内部试用，不能直接进入客户经营会议。

### 场景 3：AI Coding / 测试辅助 Skill 运营

研发内部 Skill 最容易出现“个人好用，但团队不可复用”。建议目录化：

| Skill | 解决问题 | 负责人 | 验收指标 |
|---|---|---|---|
| 需求改动点分析 | 从需求中提取影响范围 | 产品/研发共同负责 | 遗漏点下降 |
| 测试用例生成 | 根据改动点生成用例 | 测试负责人 | 用例覆盖率提升 |
| Bug 根因摘要 | 从日志/描述中总结原因 | 研发负责人 | 定位时间下降 |
| 发版风险检查 | 上线前检查高风险项 | 项目负责人 | 线上问题下降 |

只有进入目录，研发提效才不会停在“某个人会用 AI”。

## 管理者关注点（成本 / 效率 / 风险）

### 1. 成本

Skill 越多，维护成本越高。目录和生命周期能避免重复建设，也能及时下线低价值能力，减少“AI 工具债”。

### 2. 效率

有目录后，业务和研发可以直接复用已有能力，不必每次从零开始写 prompt、接数据、做流程。真正的效率来自复用，而不是单次生成。

### 3. 风险

没有发布规则的 Skill 进入生产，会带来权限、口径、执行和客户体验风险。尤其是导购触达、优惠券、客服承诺、经营诊断类 Skill，必须先灰度、再正式发布。

## 本日自检

1. 现在团队已经做过的 AI 能力，有没有统一目录？
2. 哪些能力已经可以正式发布，哪些只能内部灰度？
3. 如果一个 Skill 两周没人用、效果不好或风险偏高，是否有明确下线规则？

---

## 一句话总结

Skill 规模化的关键不是“多写几个”，而是把它们当成产品运营：有目录、能发布、可评估、会迭代、该下线就下线。
