# Day28｜Skill 记忆与沉淀：让执行结果反哺能力

## 今日主题

Day27 讲的是：Skill 执行前，Agent 要拿到正确、清晰、可判定的业务上下文。

Day28 继续往后走一步：**Skill 执行之后，结果是否能沉淀回组织资产，让下一次调用更准、更快、更稳。**

> 没有沉淀机制的 Skill，只是一次性自动化；能把执行结果、异常、口径、案例持续回写的 Skill，才会变成会进化的业务能力。

---

## 技术原理（技术视角）

### 1. Skill 的输出不应只交给用户，还应回到资产层

一个业务 Skill 执行完，至少会产生四类可沉淀信息：

1. **结果数据**：本次生成了什么结论、动作、清单、报告。
2. **过程证据**：调用了哪些数据源、引用了哪些知识库、用了什么口径。
3. **异常经验**：哪里缺数据、哪里权限不足、哪里口径冲突、哪里需要人工确认。
4. **复盘判断**：用户是否采纳、业务是否有效、下次如何优化。

如果这些信息不回写，下一次 Agent 仍然从零开始，组织不会积累经验。

### 2. 沉淀要分层，不要什么都写进长期记忆

Skill 结果沉淀建议分三层：

```text
1. 临时上下文：本次任务内有效，例如当前对话、当前报告草稿。
2. 项目记忆：某个客户、项目、专题内持续有效，例如 PVH 项目规则、资源预警口径。
3. 组织知识：可跨项目复用，例如字段定义、评审模板、最佳实践、风险清单。
```

不是所有执行记录都值得长期保存。真正值得沉淀的是：

- 重复出现的问题；
- 被验证有效的做法；
- 已确认的业务口径；
- 关键风险边界；
- 可复用模板和检查清单。

### 3. 业务 Skill 要设计“回写字段”

一个成熟 Skill，最好在设计阶段就写清楚：

```text
执行结果写到哪里？
哪些字段必须回写？
哪些内容只留日志？
哪些结论需要人工确认后才能沉淀？
沉淀后谁负责维护？
过期后如何清理？
```

否则 Skill 越跑越多，知识库反而会变成噪音库。

## 业务翻译（业务视角）

业务上可以这样理解：

> 以前做系统，是把流程跑完；现在做 Skill，是让每次流程跑完后，组织都更懂这件事。

例如智能导购场景里，Agent 给导购生成了跟进建议，如果只停在“生成话术”，价值有限。

更应该沉淀的是：

- 哪类客户用了什么话术；
- 导购有没有执行；
- 客户有没有回复；
- 是否到店 / 下单 / 领取权益；
- 哪些话术被证明有效；
- 哪些客户分层规则需要修正。

这才是从“AI 内容生成”走向“经营能力进化”。

## 典型场景（EZR 业务版）

### 场景：导购客户跟进 Skill

一次 Skill 调用可能输出：

```text
今日重点客户：10 人
推荐动作：企微私聊 / 优惠券提醒 / 新品推荐 / 到店邀约
推荐话术：每人 1-3 条
执行边界：导购确认后发送，不自动群发
```

如果没有沉淀，下一次仍然只是重新生成。

更好的回写设计是：

```text
1. 执行回写
- 导购是否采纳建议
- 实际发送的话术版本
- 发送时间
- 触达渠道

2. 结果回写
- 客户是否回复
- 是否点击 / 领券 / 到店 / 下单
- 成交金额 / 客单价 / 连带件数

3. 经验沉淀
- 哪类客户对哪类话术响应更好
- 哪类推荐容易被导购忽略
- 哪些权益或活动真正带来转化

4. 风险记录
- 是否出现客户反感
- 是否涉及敏感优惠
- 是否触发权限或审批问题
```

这套回写，最终会形成导购 Agent 的经验资产。

## 管理者关注点（成本 / 效率 / 风险）

### 1. 成本

没有沉淀，Skill 每次都像临时工；有沉淀，Skill 才会逐步变成组织能力。

### 2. 效率

复用已确认口径、模板和案例，能显著降低重复解释和反复校验成本。

### 3. 风险

沉淀错误口径比不沉淀更危险。涉及客户数据、经营结论、外部触达的内容，必须有人工确认、来源记录和过期清理机制。

## 一句话总结

Skill 的价值不只在“帮你做一次”，而在“每做一次，组织就多一份可复用经验”。
