# Day26｜Agent 调用视角：让 Skill 被正确理解、选择和执行

## 今日主题

Day25 讲的是：当 Skill 能跨客户、跨团队复制时，如何从标准 Skill 走向产品能力。

Day26 往 Agent 调用视角再走一步：**一个 Skill 写得再好，如果 Agent 不能准确理解它、判断何时该用它、知道边界在哪里，它就无法稳定进入真实工作流。**

> Skill 不是给人看的功能说明，而是给 Agent 做决策时使用的能力说明书。

---

## 技术原理（技术视角）

### 1. Agent 调用 Skill 前会做三件事

一个合格的 Agent 在调用 Skill 前，通常需要判断：

1. **意图是否匹配**：用户问题是不是这个 Skill 能解决的。
2. **输入是否足够**：是否已有必要参数、权限、上下文。
3. **风险是否可控**：是否涉及外部发送、数据写入、审批、删除、公开发布等动作。

所以 Skill 文档不能只写“能做什么”，还必须写清楚：

- 什么时候应该用；
- 什么时候不应该用；
- 缺什么信息要先问；
- 哪些动作必须确认；
- 输出结果应该如何被解释和复盘。

### 2. 一个可被 Agent 稳定调用的 Skill，至少要有 5 个要素

| 要素 | 作用 |
|---|---|
| 触发条件 | 让 Agent 知道什么时候该用 |
| 输入要求 | 让 Agent 知道缺什么不能硬跑 |
| 执行步骤 | 让 Agent 少走弯路，减少自由发挥 |
| 风险边界 | 让 Agent 知道哪些动作要先确认 |
| 输出格式 | 让结果能被人读、被系统接、被后续流程继续用 |

如果这 5 个要素缺失，Skill 很容易变成“偶尔有用的提示词”，而不是“可治理的组织能力”。

### 3. description 是第一道分流器

在 OpenClaw Skill 机制里，`description` 不是普通简介，而是 Agent 判断是否读取 Skill 的关键线索。

好的 description 应该回答：

```text
这个 Skill 解决什么问题？
适用于哪些触发词 / 业务场景？
不适用于哪些情况？
最终产出是什么？
```

差的 description 常见问题：

- 只写“用于提升效率”，太泛；
- 只写技术能力，不写业务场景；
- 没有触发词，Agent 很难自动命中；
- 没有产出物，调用后不知道交付什么。

## 业务翻译（业务视角）

业务上可以这样理解：

> 以前我们写操作手册，是教人怎么用系统；现在写 Skill，是教 Agent 怎么替人调用能力。

这会带来一个管理变化：

- 功能页面关注“人会不会点”；
- Skill 关注“Agent 会不会判断”；
- 产品能力关注“Agent 执行后有没有业务结果”。

所以业务 Skill 的关键不是写得多完整，而是写得足够清楚，让 Agent 不误用、不漏用、不越权。

---

## 典型场景（EZR 业务版）

### 场景：会员跟进建议 Skill

如果只写：

> 根据会员数据生成跟进建议。

这对 Agent 来说太模糊。

更适合写成：

```text
当用户需要为导购生成会员跟进名单、唤醒话术、复购建议、沉睡会员激活方案时使用。
输入至少需要：品牌/门店范围、会员筛选口径、活动目标、可用权益、导购权限范围。
如果涉及自动发券、自动群发、对外发送消息，必须先向用户确认。
输出包括：目标会员分组、跟进理由、建议话术、推荐动作、回写字段、复盘指标。
```

这样 Agent 才知道：

- 哪些需求能接；
- 缺哪些信息要问；
- 哪些动作不能擅自执行；
- 最终要交付什么。

## 管理者关注点（成本 / 效率 / 风险）

### 1. 成本

Skill 调用说明写不清，后续会消耗大量人工纠偏成本。尤其是 CRM、会员、导购、营销这类高上下文场景，模糊描述会让 Agent 频繁误判。

### 2. 效率

真正提效的不是“多写几个 Skill”，而是让 Agent 能自动选择正确 Skill，并把结果接到后续动作里。

### 3. 风险

所有涉及客户数据、会员权益、外部触达、自动发送、批量修改的 Skill，都必须把人工确认和审计边界写进说明里。

## 一句话总结

> Skill 的本质不是功能说明，而是 Agent 的行动边界；写清触发、输入、步骤、风险和输出，才可能从个人工具变成组织能力。
