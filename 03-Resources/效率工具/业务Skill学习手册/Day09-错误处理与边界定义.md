# Day09｜错误处理与边界定义

## 今日主题

今天继续第二阶段：**学会把 Skill 写对。**

Day07 讲「参数」：让 Skill 拿到稳定输入。  
Day08 讲「输出」：让 Skill 返回可执行结果。  
Day09 讲「错误处理与边界」：让 Skill 在不确定、缺数据、无权限、风险较高时，不乱干活。

一句话：

> 好 Skill 不只是会完成任务，更要知道什么时候不能完成、不能直接完成、必须升级确认。

很多业务 Skill 真正危险的地方，不是答错，而是“看起来很自信地错”：数据缺失还下结论、权限不足还给执行建议、风险动作不提示审批、边界条件不说明。

---

## 技术原理（技术视角）

### 1. 错误处理是 Skill 的安全阀

Skill 至少要定义 4 类异常：

| 异常类型 | 典型情况 | 正确处理 |
|---|---|---|
| 参数缺失 | 没有 brandId、dateRange、memberId | 明确指出缺什么，要求补齐 |
| 数据不足 | 样本太少、接口无数据、数据延迟 | 降低置信度，不做强结论 |
| 权限不足 | 无权查看会员明细、无权发券 | 停止执行，提示需要授权/审批 |
| 高风险动作 | 批量触达、自动发券、客户风险判断 | 只生成建议，不自动执行 |

错误处理不是“报错文案”，而是控制 Skill 行为边界。

### 2. 边界要写进 Skill 描述和输出

一个稳定的业务 Skill，要明确：

```text
它能做什么？
它不能做什么？
什么情况下只给建议不执行？
什么情况下必须人工确认？
什么情况下需要升级给管理者？
```

如果边界没写清，Agent 编排时就容易越界。

### 3. 输出要带置信度和限制说明

推荐输出中增加：

```json
{
  "confidence": "medium",
  "limitations": ["仅基于近7天数据", "不包含线下试穿反馈"],
  "requiresApproval": true,
  "blockedReason": null
}
```

这能让业务知道：这个结果能不能直接用、要不要复核、哪里不能过度解读。

---

## 业务翻译（业务视角）

业务侧不关心异常类型，但很关心三件事：

1. **别误导我**：数据不够时不要装确定；
2. **别越权**：不能替人做高风险动作；
3. **别甩锅**：失败时说清原因和下一步。

差的 Skill：

- 数据没查到，却继续给管理建议；
- 样本只有几个，却判断全品牌趋势；
- 直接生成批量触达动作，没有审批提醒；
- 报错只说“系统异常”，业务不知道该找谁。

好的 Skill：

- 明确告诉你缺什么；
- 不确定时标注置信度；
- 高风险动作自动降级为“建议”；
- 给出下一步补数、复核或升级路径。

## 典型场景（EZR 业务版）

### 场景 1：会员标签洞察 Skill

**风险点**：标签覆盖率低，不一定代表导购没维护，也可能是新客入会链路未触发、标签规则变更、数据同步延迟。

建议边界：

```json
{
  "summary": "近7天新客标签覆盖率偏低，但当前无法直接判断为门店执行问题。",
  "confidence": "medium",
  "limitations": [
    "仅覆盖近7天新入会会员",
    "未校验标签规则是否近期变更",
    "未确认数据同步是否延迟"
  ],
  "suggestedActions": [
    "先核对标签规则变更记录",
    "抽查覆盖率最低的10家门店",
    "确认新客入会链路是否正常触发自动标签"
  ],
  "requiresApproval": false
}
```

管理重点：不要把数据异常直接变成人的问题，先排除规则和链路问题。

### 场景 2：导购触达建议 Skill

**风险点**：AI 可以生成话术，但不应自动批量发送，尤其涉及促销、敏感会员、投诉风险客户。

建议边界：

```json
{
  "recommendation": "建议导购先以尺码顾虑切入，不直接推券。",
  "messageDraft": "上次您看的那款我帮您确认过尺码，按您之前买过的版型建议选M，会更稳。",
  "riskNote": "该会员近30天有一次售后记录，建议导购人工确认后再发送。",
  "allowedAction": "generate_draft_only",
  "requiresHumanConfirm": true
}
```

管理重点：导购 Skill 的边界是“辅助判断 + 生成草稿”，不是无审计自动触达。

### 场景 3：资源预警 Skill

**风险点**：工时数据不完整时，不能直接判断某个人低负载或高负载，更不能直接形成绩效结论。

建议边界：

```json
{
  "summary": "当前只能判断排期表上业务测试组负载偏高，不能代表真实工作饱和度。",
  "confidence": "medium",
  "limitations": [
    "未包含临时支持任务",
    "未包含线上问题插单",
    "部分任务预估工时可能未更新"
  ],
  "decisionNeeded": "是否由负责人补充未登记任务后再做调配判断。",
  "forbiddenUse": "不得直接用于个人绩效评价"
}
```

管理重点：资源预警是调度工具，不是绩效裁判。

## 边界定义清单

写业务 Skill 时，至少检查 10 项：

1. 缺少必填参数时怎么提示？
2. 数据为空时是报错、返回空结果，还是给补救建议？
3. 样本不足时是否降低置信度？
4. 是否标注数据周期、口径和限制？
5. 是否区分“建议”和“执行”？
6. 哪些动作必须人工确认？
7. 哪些动作必须审批？
8. 哪些结论不能用于绩效/处罚/客户定责？
9. 是否提供下一步补数或复核动作？
10. 是否方便下游 Agent 判断继续执行还是停止？

## 图示

```text
Skill 接收请求
  ↓
参数是否完整？——否→提示补充
  ↓ 是
权限是否允许？——否→停止并提示授权/审批
  ↓ 是
数据是否足够？——否→低置信度 + 补数建议
  ↓ 是
动作是否高风险？——是→只给建议 / 需人工确认
  ↓ 否
输出结论 + 动作 + 风险 + 复盘口径
```

## 今日小结

Day09 的关键不是让 Skill 少做事，而是让它**可控地做事**。

业务 Skill 真正进入生产场景后，价值不只来自智能程度，还来自边界清楚、失败可解释、风险可升级。

一句话收口：

> Skill 的专业度，不只看它会不会答，更看它知不知道什么时候该停、该问、该交给人。
