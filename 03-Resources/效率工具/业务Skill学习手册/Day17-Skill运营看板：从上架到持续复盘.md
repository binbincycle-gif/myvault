# Day17｜Skill运营看板：从上架到持续复盘

## 今日主题

Day16 讲了评审机制，解决的是：**什么 Skill 可以进入组织能力库。**

Day17 继续往后走一步：Skill 上架之后，不能只看“有没有人用”，而要用一张运营看板持续回答：

> 这个 Skill 是否还在创造业务价值？是否稳定？是否需要升级、合并或下线？

很多 AI 能力的问题，不是第一版做不出来，而是上线后没人复盘：

1. 使用量有了，但不知道是否真的提效。
2. 输出看起来不错，但业务结果没有改善。
3. 版本改了多次，没人知道当前口径是否还可信。
4. 异常和投诉只在群里流转，没有沉淀成产品改进。

所以今天要学的是：把 Skill 当成“业务能力产品”来运营，而不是当成一次性工具交付。

---

## 技术原理（技术视角）

### 1. Skill 运营看板要同时看四类指标

一个业务 Skill 至少要看四类指标：

| 指标类型 | 解决的问题 | 示例 |
|---|---|---|
| 使用指标 | 有没有被真实调用 | 调用次数、活跃用户数、使用频次 |
| 质量指标 | 输出是否稳定可信 | 成功率、错误率、人工退回率、置信度分布 |
| 业务指标 | 是否带来结果改善 | 转化率、节省工时、闭环率、采纳率 |
| 风险指标 | 是否出现不可控问题 | 越权拦截、敏感数据触发、客户投诉、异常执行 |

只看调用量会误判价值。一个 Skill 被频繁调用，但输出经常被人工改掉，说明它可能只是“热闹”，不是“有效”。

### 2. 看板不是报表，而是运营动作入口

运营看板的价值不是展示数据，而是触发动作：

```text
数据异常 → 定位原因 → 决定动作 → 记录结果 → 下次复盘
```

建议把每个 Skill 的运营动作分成 5 类：

| 动作 | 触发条件 | 处理方式 |
|---|---|---|
| 扩大灰度 | 使用稳定、指标改善 | 扩人群 / 扩品牌 / 扩场景 |
| 优化提示词/逻辑 | 输出质量波动 | 调整 prompt、规则、样例、参数 |
| 补数据/补权限 | 经常因为上下文不足失败 | 补字段、补知识库、补权限判断 |
| 合并重复 Skill | 多个能力重叠 | 统一口径，保留一个主版本 |
| 下线/冻结 | 长期无人用或风险高 | 标记 Deprecated，给替代方案 |

看板必须能直接服务决策：扩、改、合、停。

### 3. 每个 Skill 都要有“运营责任人”

Skill 一旦进入目录，必须明确三类责任：

| 责任角色 | 负责什么 |
|---|---|
| 业务负责人 | 判断场景价值、业务口径和指标 |
| 技术负责人 | 保障稳定性、权限、日志、版本 |
| 运营负责人 | 跟踪使用、收集反馈、推动复盘 |

早期可以一个人兼任，但责任不能空着。否则 Skill 出问题时，会变成“没人维护的智能功能”。

---

## 业务翻译（业务视角）

业务上可以这样理解：

> Skill 上架不是结束，而是开始进入“经营”。

过去 SaaS 功能上线后，常见问题是：只看是否发布，不看是否被用好。Skill 更不能这样，因为它会参与判断、生成建议，甚至触发动作。

管理者要盯住一句话：

> 一个 Skill 是否值得继续投，不看它多智能，而看它有没有稳定改善业务过程或业务结果。

---

## 典型场景（EZR 业务版）

### 场景 1：导购话术生成 Skill

建议看板字段：

| 维度 | 指标 |
|---|---|
| 使用 | 日调用次数、活跃导购数、品牌/门店覆盖数 |
| 质量 | 话术采纳率、人工修改率、敏感词拦截次数 |
| 业务 | 触达率、回复率、转化率、客单价变化 |
| 风险 | 客诉数、权益/价格误导次数、越权调用次数 |

复盘重点不是“生成了多少话术”，而是：导购是否愿意用、客户是否响应、风险是否可控。

### 场景 2：经营诊断 Skill

建议看板字段：

| 维度 | 指标 |
|---|---|
| 使用 | 诊断报告生成次数、管理者查看次数 |
| 质量 | 指标口径错误数、数据异常提示准确率 |
| 业务 | 问题识别后行动闭环率、复盘采纳率 |
| 风险 | 错误建议次数、客户质疑次数、人工纠偏次数 |

经营诊断类 Skill 最怕“说得像顾问，但没有证据”。看板必须跟踪数据来源、口径版本、建议采纳和后续动作。

### 场景 3：AI Coding / 测试用例生成 Skill

建议看板字段：

| 维度 | 指标 |
|---|---|
| 使用 | 需求分析次数、用例生成次数、研发/测试活跃人数 |
| 质量 | 人工采纳率、遗漏缺陷数、生成失败率 |
| 效率 | 需求分析节省时间、用例编写节省时间、回归准备时间 |
| 风险 | 错误影响范围判断、误导性根因、未覆盖核心链路 |

内部提效 Skill 的核心不是“用了 AI”，而是能不能缩短交付周期，同时不放大质量风险。

## 管理者关注点（成本 / 效率 / 风险）

### 1. 成本

看板能帮助管理者及时停掉低价值 Skill，避免团队持续维护“没人用、没结果、风险还高”的能力。

### 2. 效率

高价值 Skill 应该被复制，而不是只停留在一个团队、一个客户、一个项目里。看板能识别哪些能力值得扩大灰度。

### 3. 风险

越接近客户、经营建议和自动执行，越要看风险指标。调用量增长不等于成功，风险同步增长时必须先控边界。

## 本日自检

1. 当前已经上架或准备上架的 Skill，有没有定义使用、质量、业务、风险四类指标？
2. 哪些 Skill 应该扩大灰度？哪些应该先冻结优化？
3. 每个关键 Skill 是否都有业务负责人、技术负责人和运营负责人？
4. 下周能不能选 1 个 Skill 做周度运营看板样板？

---

## 一句话总结

Skill 上架只是进入能力货架，运营看板才决定它能不能持续成为组织资产。
