# Day12｜Skill的权限、审批与审计

## 今日主题

今天继续第三阶段：**学会产品化与规模化。**

Day11 讲的是 Skill 组合成工作流。Day12 要补上工作流能进入真实业务系统前最关键的一层：

> Skill 不是“会调用能力”就够了，还必须知道谁能调用、调用到哪一步、哪些动作要审批、事后能不能追溯。

业务 Skill 一旦进入 CRM、会员、营销、订单、客服、导购等场景，就不再是普通问答工具，而是在接触真实客户、真实经营数据、真实业务动作。没有权限、审批和审计，Skill 越强，风险越大。

---

## 技术原理（技术视角）

### 1. 权限解决“谁能看、谁能做”

Skill 权限至少分三层：

| 权限层 | 解决问题 | 示例 |
|---|---|---|
| 数据权限 | 能看到哪些数据 | 总部看全品牌，区域看大区，导购只看自己会员池 |
| 操作权限 | 能执行哪些动作 | 查询、生成建议、提交审批、触达客户、发券 |
| 场景权限 | 在什么业务场景下可用 | 日报可汇总，会员明细需脱敏，投诉客户需人工确认 |

核心原则：

```text
默认最小权限，只开放完成任务所需的最小数据和最小动作。
```

### 2. 审批解决“什么时候不能自动做”

不是所有 Skill 动作都应该自动执行。

建议把动作分为四类：

| 动作类型 | 示例 | 默认策略 |
|---|---|---|
| 查询类 | 查会员概况、查指标、查任务列表 | 可自动执行，受数据权限控制 |
| 分析类 | 生成诊断、识别风险、输出建议 | 可自动执行，但要标置信度和限制 |
| 草稿类 | 生成话术、生成邮件、生成方案 | 可自动生成，但发送前需确认 |
| 执行类 | 发券、群发、改客户状态、提交工单 | 默认需要审批或人工确认 |

一句话：**AI 可以自动准备，不能默认自动替人承担经营责任。**

### 3. 审计解决“出了问题能不能追溯”

一个可规模化的 Skill，至少要记录：

```json
{
  "skillName": "member_reach_suggestion",
  "operator": "导购A / 运营B / Agent实例",
  "role": "store_guide",
  "inputSummary": "近30天未触达高价值会员",
  "dataScope": "门店X会员池",
  "actionType": "generate_draft_only",
  "approvalStatus": "not_required / pending / approved / rejected",
  "outputSummary": "生成10条触达建议",
  "timestamp": "2026-05-20T09:00:00+08:00"
}
```

审计不是为了“追责”，而是为了三件事：

1. 出错能还原现场；
2. 效果能复盘优化；
3. 规模化后能符合合规和管理要求。

---

## 业务翻译（业务视角）

业务上不要只问：

> 这个 Skill 能不能做？

还要追问：

1. 谁可以用？
2. 能看到什么数据？
3. 可以做到哪一步？
4. 哪些动作必须审批？
5. 出错后能不能知道是谁、基于什么数据、做了什么？

如果回答不清，这个 Skill 只能做内部辅助，不能进入生产经营流程。

## 典型场景（EZR 业务版）

### 场景 1：导购小龙虾会员触达 Skill

**风险点**：会员数据敏感，触达动作会影响客户体验，不能让 AI 自动群发。

建议设计：

```text
导购可查看：自己会员池、会员偏好、最近互动、推荐理由
导购不可查看：其他门店会员、全品牌敏感经营数据
AI 可执行：生成推荐理由、生成触达草稿、提示风险
AI 不可直接执行：自动发送消息、自动发券、自动修改会员标签
```

审批/确认点：

- 单个会员触达：导购确认后发送；
- 批量触达：店长或运营确认；
- 涉及优惠券：按品牌营销审批规则走。

审计记录：

- 推荐基于哪些会员行为；
- 导购是否采纳；
- 是否发送；
- 是否成交或反馈未成交原因。

业务价值：既能放大导购能力，又不会让 AI 变成无审计的“自动骚扰器”。

---

### 场景 2：AI 客服 Skill

**风险点**：客服回答会影响客户关系，涉及订单、售后、权益时不能只靠模型自由发挥。

建议设计：

```text
AI 可自动处理：知识库问答、流程指引、状态查询摘要
AI 需人工确认：退款解释、责任归因、补偿建议、投诉升级
AI 必须转人工：高价值客户投诉、法律/合同争议、超 SLA 问题
```

审批/确认点：

- 普通 FAQ：可自动回复；
- 涉及赔付/补偿：生成建议，人工确认；
- 涉及客户风险：自动打标并升级负责人。

审计记录：

- 引用了哪条知识；
- 客户问题分类；
- 是否转人工；
- 最终解决状态；
- 是否进入复盘样本。

业务价值：AI 客服不是“答案生成器”，而是服务流程编排器。

---

### 场景 3：经营诊断 / 指标库 Skill

**风险点**：经营指标会影响管理判断，口径错误或越权查看会放大决策风险。

建议设计：

```text
总部：可查看全局指标与品牌经营诊断
区域：只看所属区域与可比口径
门店：只看门店经营与导购执行建议
外部客户：只看授权范围内报告，不暴露内部治理数据
```

审批/确认点：

- 内部诊断报告：可自动生成草稿；
- 对客户发送版本：需人工确认；
- 涉及经营建议或费用策略：需负责人确认。

审计记录：

- 指标口径版本；
- 数据时间范围；
- 数据权限范围；
- 报告接收对象；
- 是否被用于客户沟通或内部决策。

业务价值：指标库 Skill 能成为 Agent 调度底座，但前提是口径、权限、审计都稳定。

## 设计方法：权限审批审计三件套

### 1. 权限矩阵

先按角色列出能看什么、能做什么：

```markdown
| 角色 | 可查看数据 | 可执行动作 | 禁止动作 |
|---|---|---|---|
| 导购 | 自己会员池 | 生成话术、记录反馈 | 查看其他门店会员、自动群发 |
| 店长 | 本店会员与导购表现 | 审核批量触达 | 查看全品牌敏感数据 |
| 总部运营 | 授权品牌经营数据 | 生成策略、提交审批 | 绕过审批直接发券 |
```

### 2. 审批规则

按动作风险设置确认机制：

```markdown
| 动作 | 风险等级 | 是否需要确认 | 审批人 |
|---|---|---|---|
| 查询会员画像 | 中 | 否，受权限控制 | 无 |
| 生成触达话术 | 低 | 否 | 无 |
| 批量发送消息 | 高 | 是 | 店长/运营 |
| 发放优惠券 | 高 | 是 | 营销负责人 |
```

### 3. 审计字段

每个生产级 Skill 都要保留最少审计字段：

```markdown
- 调用人 / Agent
- 调用时间
- 角色与权限范围
- 输入数据范围
- 输出结果摘要
- 是否触发审批
- 是否执行外部动作
- 结果回写状态
```

## 今日练习

请选一个当前最接近落地的业务 Skill，补齐下面模板：

```markdown
## Skill 名称
例如：AI 客服问题分流 Skill

## 使用角色
谁会用？总部、区域、门店、导购、客服、管理者？

## 数据权限
可以看哪些数据？不能看哪些数据？

## 动作权限
可以自动做什么？只能生成建议什么？绝对不能做什么？

## 审批规则
哪些动作需要人工确认？由谁确认？

## 审计字段
至少记录哪些字段，保证后续可追溯？

## 风险底线
如果权限不足、数据缺失、涉及敏感动作，Skill 应该如何降级？
```

## 今日小结

Day12 的重点不是让 Skill 变慢，而是让 Skill 能安全地变大。

记住一句话：

> 没有权限，Skill 不能进生产；没有审批，Skill 不能做高风险动作；没有审计，Skill 不能规模化。

对 EZR 来说，权限、审批和审计不是附加功能，而是 SaaS CRM 做 AI Agent 底座的核心护城河。
