# Day10｜可复用性判断：什么能力值得做成 Skill

## 今日主题

今天收口第二阶段：**学会把 Skill 写对。**

前面几天已经讲了描述、参数、输出、错误处理。Day10 要解决一个更关键的问题：

> 不是所有功能、流程、报表、Prompt 都值得做成 Skill。真正值得 Skill 化的，是那些高频、稳定、可复用、可治理，并且能进入业务闭环的能力。

Skill 不是“把一个需求包装成 AI”。Skill 的本质是：把一个可重复调用的业务能力，沉淀成 Agent 能理解、能执行、能组合、能审计的标准单元。

---

## 技术原理（技术视角）

### 1. Skill 要有稳定边界

一个能力要做成 Skill，至少要回答清楚：

```text
输入是什么？
处理规则是什么？
输出是什么？
失败时怎么处理？
谁可以调用？
调用后能不能复盘？
```

如果每次都要临场解释、临场判断、临场改口径，它更像一次性任务，不适合直接做成 Skill。

### 2. Skill 要能被 Agent 编排

OpenClaw 的 Skill 机制，本质上是让 Agent 在合适场景下读取 `SKILL.md`，按照里面的流程和边界使用工具或产出结果。

所以一个好 Skill 不只是“会做一件事”，还要方便被上游任务调用、被下游流程接住：

- 上游：用户一句话能触发；
- 中间：参数、权限、数据口径清楚；
- 下游：输出结构稳定，可继续进入报告、消息、审批、任务流。

### 3. 判断标准：三高两稳一闭环

建议用这个判断模型：

| 维度 | 判断问题 | 不满足时的处理 |
|---|---|---|
| 高频 | 是否反复发生？ | 先做模板或 SOP |
| 高价值 | 是否影响效率、收入、风险或体验？ | 不急着 Skill 化 |
| 高确定性 | 输入、规则、输出是否相对稳定？ | 先固化口径 |
| 稳边界 | 能做/不能做是否说得清？ | 先补边界定义 |
| 稳责任 | 谁调用、谁确认、谁复盘是否清楚？ | 先明确责任链路 |
| 有闭环 | 调用后有没有业务动作和结果反馈？ | 先补反馈机制 |

## 业务翻译（业务视角）

业务侧判断一个能力值不值得做成 Skill，不要先问“AI 能不能做”，而要问：

1. 这件事是不是经常重复？
2. 每次是不是都要找同一批人、查同一批数据、写同一种结论？
3. 如果标准化后，是否能明显减少沟通、等待、返工？
4. 结果是不是能推动下一步动作？
5. 做错了有没有风险，需要权限、审批或人工确认？

如果答案大多是“是”，它就值得进入 Skill 候选池。

差的 Skill 候选：

- 一次性的老板提问；
- 口径还没统一的临时报表；
- 只有炫技、没有业务动作的 AI Demo；
- 权限和风险边界不清的自动执行；
- 依赖大量人工判断、无法结构化输入输出的复杂议题。

好的 Skill 候选：

- 每日线上问题整理；
- 资源负载预警；
- 会员标签洞察；
- 导购触达建议；
- 高风险客户识别与跟进建议；
- 品牌经营日报/周报自动生成。

## 典型场景（EZR 业务版）

### 场景 1：会员标签洞察

**是否值得 Skill 化：值得。**

原因：

- 高频：品牌、运营、门店都会反复看；
- 高价值：影响会员分层、导购跟进、营销策略；
- 输出稳定：覆盖率、异常门店、标签分布、建议动作；
- 可闭环：能进入导购打标、运营检查、门店培训。

建议 Skill 边界：

```json
{
  "skillName": "会员标签洞察",
  "input": ["brandId", "dateRange", "tagGroup"],
  "output": ["summary", "topIssues", "storeRanking", "suggestedActions", "limitations"],
  "riskBoundary": "不直接判断个人执行问题，需先排除规则变更和数据延迟"
}
```

### 场景 2：智能导购试衣间推荐

**是否值得 Skill 化：值得，但必须小闭环。**

不要一上来做“全能导购 AI”。先做一个具体 Skill：

> 根据会员画像、试穿商品、未成交原因，生成下一次导购跟进建议。

判断依据：

- 高频：导购每天会遇到试穿未成交；
- 高价值：直接影响转化和复购；
- 输入可结构化：试了什么、为什么犹豫、为什么没买、历史偏好；
- 输出可执行：下一次推荐商品、跟进话术、风险提醒。

### 场景 3：迭代管理流程判断

**是否值得 Skill 化：暂时不直接做完整 Skill，先做规则助手。**

原因：

- 流程口径可能还在统一；
- 不同项目类型、客户紧急程度、发版窗口会影响判断；
- 直接自动判定容易引发管理争议。

更稳的做法：

先做“迭代流程材料检查 Skill”：

- 检查需求背景是否完整；
- 检查影响范围是否说明；
- 检查上线风险是否列出；
- 检查是否需要审批升级。

先检查材料，不直接替管理者拍板。

## 可复用性判断清单

写 Skill 前先过 12 个问题：

1. 这件事过去 30 天是否重复出现 3 次以上？
2. 是否有明确使用人？
3. 是否有稳定输入？
4. 是否有稳定输出？
5. 是否有清楚的数据来源？
6. 是否有统一业务口径？
7. 是否能节省沟通、查询、整理或判断时间？
8. 是否能进入下一步业务动作？
9. 是否需要权限控制？
10. 是否存在误判或越权风险？
11. 是否能记录调用结果并复盘？
12. 是否能被其他 Skill 或工作流复用？

建议判断：

```text
≥9 个“是”：优先做成 Skill
6-8 个“是”：先做半自动模板 / SOP，再观察
≤5 个“是”：暂时不要 Skill 化，先沉淀规则
```

## 管理者关注点（成本 / 效率 / 风险）

- **成本**：不要把低频一次性需求都做成 Skill，后续维护成本会反噬。
- **效率**：优先做能减少重复查询、重复整理、重复汇报的能力。
- **风险**：涉及客户触达、营销动作、绩效判断、经营决策的 Skill，必须先定义权限、审批和边界。
- **规模化**：Skill 值钱的地方不在单次回答，而在能被反复调用、组合进流程、持续复盘优化。

## 一句话总结

> 值得做成 Skill 的，不是“AI 能回答的问题”，而是“业务会反复调用、结果能进入闭环、风险边界能被治理的能力”。
