# Day01｜Skill是什么：从功能到能力单元

## 今日主题
很多团队一说 Skill，第一反应是“把现有功能包装一下”。但真正的 Skill，不是页面功能的别名，也不是 prompt 的合集，而是**可调用、可复用、可治理的业务能力单元**。如果第一天不把这个认知建立起来，后面写出来的往往不是 Skill，而是功能说明书。

## 一、Skill 不是什么
### 1. Skill 不是页面功能
页面功能是给人点的，Skill 是给人和系统一起调用的。

### 2. Skill 不是单个接口
接口只是技术暴露方式，Skill 强调的是“完成一个业务任务的能力”。

### 3. Skill 不是 prompt 模板
prompt 只是生成的一部分，Skill 更关注输入、处理、输出、边界和结果。

## 二、Skill 到底是什么
一句话理解：

> Skill 是把一个稳定、可复用的业务动作，抽象成标准化能力单元，让系统和人都可以调用。

它至少要回答 5 个问题：
1. 这个能力解决什么问题
2. 谁会用它
3. 输入是什么
4. 输出是什么
5. 成功标准是什么

## 三、为什么 Skill 比功能更适合 AI 时代
### 1. 功能面向操作，Skill 面向结果
功能关心“用户点了什么”，Skill 关心“任务有没有完成”。

### 2. 功能难复用，Skill 天然适合编排
一个 Skill 可以被多个入口、多个角色、多个流程复用。

### 3. Skill 更容易沉淀组织经验
业务人员的方法、规则、判断，可以逐步被固化成 Skill，而不是只存在于人脑里。

## 四、举个业务例子
### 错误写法：
“会员标签页面查询”

这是一个页面动作，不是 Skill。

### 更好的 Skill 写法：
“会员高潜人群识别”
- 输入：会员行为、消费记录、标签条件
- 输出：高潜会员名单 + 推荐理由
- 价值：帮助运营快速锁定优先触达人群

你会发现，Skill 写法天然更接近业务价值。

## 五、今天的关键认知
从今天开始，团队写 Skill 时不要再先想：
- 这个页面有什么按钮
- 这个接口叫什么名字

而要先想：
- 这个业务动作有没有稳定价值
- 它能不能被重复调用
- 它值不值得成为一个能力单元

Skill 不是功能的另一个名字，而是把业务动作抽象成可调用、可复用、可治理能力单元的过程。
