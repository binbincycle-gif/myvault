# Day05｜输入输出思维：Skill 的最小闭环

## 今日主题

今天看一个非常关键的判断标准：**一个 Skill 能不能落地，先看它有没有清楚的输入和输出闭环。**

很多业务 Skill 写不清，不是因为技术不会做，而是因为一开始没有回答三个问题：

1. 用户给什么？
2. Skill 处理什么？
3. 最后交付什么结果？

如果这三个问题模糊，Skill 就会变成“泛泛聊天”或“功能介绍”；如果这三个问题清楚，Skill 才会变成可以反复调用、可以治理、可以评估的业务能力单元。

---

## 技术原理（技术视角）

### 1. Skill 本质上是一个可调用能力单元

从技术视角看，一个 Skill 至少包含：

```text
触发条件 → 输入参数 → 执行逻辑 → 输出结构 → 错误处理
```

其中最容易被忽略的是输入和输出。

- 输入不清楚：Agent 不知道该收集哪些信息，也不知道缺什么要追问。
- 输出不清楚：用户拿到结果后不知道该怎么用，也很难判断这次调用是否成功。

所以 Skill 设计不是先写“我能做什么”，而是先写：

> 在什么场景下，用户给我什么，我返回什么可用结果。

### 2. 输入要尽量结构化

业务输入通常有三类：

| 输入类型 | 示例 | 设计重点 |
|---|---|---|
| 身份类 | 品牌、门店、导购、会员 | 决定权限和视角 |
| 场景类 | 看标签、查会员、做推荐、生成报告 | 决定处理流程 |
| 约束类 | 时间范围、渠道、活动、门店范围 | 决定查询边界 |

好的 Skill 不会要求用户一次性说得很完整，而是要能判断：

- 哪些输入是必须的
- 哪些输入可以默认
- 哪些输入缺失时必须追问

### 3. 输出要能直接进入下一步动作

输出不是“展示数据”就结束，而是要支持用户下一步动作。

例如标签洞察 Skill，不应该只输出：

> 高价值会员占比 18%。

更好的输出是：

> 高价值会员占比 18%，较上周下降 3 个点。建议优先检查高价值会员近 30 天复购下降门店，并对沉睡高价值会员做二次触达。

也就是：

```text
数据 → 解释 → 判断 → 建议动作
```

## 业务翻译（业务视角）

业务侧不关心 Skill 的内部代码，但关心三件事：

1. 我问它什么问题？
2. 它给我的结果靠不靠谱？
3. 我拿到结果后能马上做什么？

所以业务 Skill 的最小闭环应该是：

```text
业务问题 → 必要输入 → 可信结果 → 下一步动作
```

举例：

### 不成闭环的写法

> 会员分析 Skill：可以分析会员数据、标签、消费情况。

问题：太泛，用户不知道怎么问，也不知道结果是什么。

### 成闭环的写法

> 当运营想判断某品牌近 30 天高价值会员变化时，输入品牌和时间范围，Skill 输出会员规模变化、关键标签变化、异常门店、建议动作。

这就清楚很多：

- 谁用：运营
- 什么时候用：判断高价值会员变化
- 输入什么：品牌、时间范围
- 输出什么：变化、异常、建议
- 后续动作：运营跟进

## 典型场景（个人版）

### 场景 1：把“查数据”改成“给结论”

原始需求：

> 帮我看一下会员标签情况。

Skill 化后：

```text
输入：品牌 / 时间范围 / 标签类型
输出：标签覆盖率、变化趋势、异常标签、经营建议
```

这样输出才适合管理层或运营直接使用。

### 场景 2：把“生成报告”改成“管理动作”

原始需求：

> 生成一份资源预警报告。

Skill 化后：

```text
输入：人员任务数据 / 时间窗口 / 角色分组
输出：超负载人员、低负载人员、可释放人员、调配建议、风险说明
```

这类 Skill 的价值不在报告本身，而在帮管理者更快做资源调配判断。

### 场景 3：把“客户洞察”改成“导购下一句话”

原始需求：

> 看看这个会员怎么样。

Skill 化后：

```text
输入：会员ID / 最近行为 / 可推荐商品范围
输出：会员画像、购买意图、推荐理由、导购话术
```

导购不需要一堆复杂分析，他需要的是：今天该说什么、推什么、为什么。

## 图示

```text
┌──────────────┐
│ 业务问题      │
│ 用户真正想解决什么 │
└──────┬───────┘
       ↓
┌──────────────┐
│ 输入设计      │
│ 必填 / 默认 / 追问 │
└──────┬───────┘
       ↓
┌──────────────┐
│ 执行逻辑      │
│ 查询 / 分析 / 生成 │
└──────┬───────┘
       ↓
┌──────────────┐
│ 输出结构      │
│ 数据 / 解释 / 建议 │
└──────┬───────┘
       ↓
┌──────────────┐
│ 下一步动作    │
│ 可决策 / 可执行 / 可追踪 │
└──────────────┘
```

图示阅读建议：
1. 不要从“我有什么功能”开始，而要从“用户要解决什么业务问题”开始；
2. 输入决定边界，输出决定价值；
3. 如果输出不能支持下一步动作，这个 Skill 就还没有闭环。

## 管理者关注点（成本 / 效率 / 风险）

### 1. 成本

输入输出越清楚，后续开发和维护成本越低。否则每次业务提问都要临时解释、临时补逻辑。

### 2. 效率

清楚的输入输出可以让 Skill 更容易被复用，也更容易接入自动化流程。

### 3. 风险

业务 Skill 很容易因为输出“像结论”但口径不清，引发误判。所以输出里必须写清：

- 数据口径
- 时间范围
- 适用边界
- 不确定性

### 4. 评估

如果输入输出不固定，就无法评估 Skill 效果。只有结构稳定，才能评估：

- 调用成功率
- 结果采纳率
- 节省时间
- 问题闭环率

2. 如果用户少给了一个关键信息，Skill 是否知道该追问什么？

## 一句话总结

一个业务 Skill 的最小闭环不是“能回答”，而是：**用户给出明确输入后，Skill 能返回可判断、可执行、可追踪的结果。**
