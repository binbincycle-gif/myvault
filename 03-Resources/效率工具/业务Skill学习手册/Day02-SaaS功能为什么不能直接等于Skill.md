# Day02｜SaaS功能为什么不能直接等于Skill

## 今日主题
很多团队在做业务 Skill 时，最容易犯的错误就是：直接把现有 SaaS 页面功能、接口能力原样搬出来，当成 Skill 去开放。这样做上线可能很快，但后面一定会遇到两个问题：**一是不好复用，二是不好治理。**

## 一、为什么 SaaS 功能不能直接等于 Skill
### 1. SaaS 功能是为“人工操作”设计的
SaaS 页面强调的是：
- 用户点哪里
- 哪个页面先后进入
- 哪个按钮触发哪个动作

它更像一条“人操作系统”的路径。

### 2. Skill 是为“任务完成”设计的
Skill 关心的不是页面结构，而是：
- 这件事怎么完成
- 输入是什么
- 输出是什么
- 哪些边界必须控制
- 结果如何被别的系统继续使用

所以 Skill 更像一块“能力积木”。

## 二、直接搬运 SaaS 功能会出什么问题
### 1. 参数会很脏
很多页面功能为了兼容历史逻辑，会带很多前端状态字段、页面跳转字段、兼容字段。对人勉强可用，但对 Skill 调用方来说非常不友好。

### 2. 返回结果不稳定
页面接口常常为了前端渲染，返回很多展示层字段。这种结构适合页面，不适合长期当成标准能力输出。

### 3. 权限边界不清
页面功能默认前提是“人在系统里，已经登录并拥有某种页面权限”。但 Skill 开放出去以后，必须明确：谁能调、在什么场景调、能调到什么深度。

### 4. 难以复用
页面功能常常只适合当前一个场景。Skill 则要求后续能被多角色、多流程、多入口复用。

## 三、应该怎么判断一个功能值不值得 Skill 化
在决定 Skill 化前，先问 4 个问题：

1. 这是不是一个稳定存在的业务动作？
2. 这个动作是否会被重复调用？
3. 这个动作是否值得跨角色、跨流程复用？
4. 这个动作能否被抽象成清晰的输入和输出？

如果这 4 个问题里有 2 个以上答不上来，就不要急着 Skill 化。

## 四、举个例子
### 直接搬页面的错误写法
“客户列表页面查询”

问题：
- 太贴近界面
- 没有业务结果
- 不知道真正解决什么事

### 更好的 Skill 写法
“高潜客户筛选”
- 输入：客户标签、行为条件、时间范围
- 输出：高潜客户名单 + 推荐理由
- 价值：帮助运营优先锁定最值得跟进的人群

你会发现，后者才能真正被不同入口调用，也更像业务能力。

## 五、正确的迁移思路
更合理的路径不是：
**页面功能 → 直接开放为 Skill**

而应该是：
**页面功能 → 识别背后的业务动作 → 抽象成标准能力 → 再封装成 Skill**

也就是说，Skill 化不是搬运，而是再设计。

## 一句话总结
SaaS 功能解决“用户怎么操作”，Skill 解决“系统怎么完成业务动作”，两者不能直接划等号。
