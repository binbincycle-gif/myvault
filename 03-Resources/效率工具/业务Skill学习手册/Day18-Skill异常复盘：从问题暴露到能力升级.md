# Day18｜Skill异常复盘：从问题暴露到能力升级

## 今日主题

Day17 讲了运营看板，解决的是：**Skill 上架后怎么持续观察价值和风险。**

Day18 再往前推进一步：当 Skill 出现异常、误判、越权、口径错误或业务投诉时，不能只在群里解释一句“AI 出错了”，而要把每一次异常变成能力升级的输入。

> Skill 的成熟度，不看它从不出错，而看它出错后能不能被定位、复盘、修正和防复发。

业务 Skill 一旦进入真实流程，就一定会遇到问题：

1. 输入不完整，导致输出看似合理但实际偏了。
2. 数据口径没对齐，导致管理建议被业务质疑。
3. 权限边界没控住，调出了不该看的信息。
4. Prompt 改了以后，原本稳定的结果突然波动。
5. 用户把 Skill 用到设计外场景，触发不可预期输出。

所以今天要学的是：建立一套 Skill 异常复盘机制，把“出问题”变成“能力变强”的机会。

---

## 技术原理（技术视角）

### 1. Skill 异常要先分类，不要混在一起处理

建议把 Skill 异常分成 5 类：

| 异常类型 | 典型表现 | 处理重点 |
|---|---|---|
| 输入异常 | 用户问题不完整、参数缺失、上下文不足 | 补充校验、追问机制、输入模板 |
| 数据异常 | 数据源为空、口径不一致、字段过期 | 数据校验、口径版本、异常提示 |
| 逻辑异常 | 推理链条错、规则冲突、结论跳跃 | 调整规则、样例、判断步骤 |
| 权限异常 | 访问越权、敏感信息外泄风险 | 权限拦截、审计日志、人工审批 |
| 体验异常 | 输出太长、格式不可用、无法直接执行 | 优化结构、缩短路径、增加操作建议 |

不要把所有问题都归因成“模型幻觉”。很多问题本质是输入、数据、规则、权限、流程没有设计好。

### 2. 每次异常都要保留最小复盘证据

一次有效复盘至少要保留 6 个字段：

| 字段 | 说明 |
|---|---|
| 异常时间 | 什么时候发生 |
| 使用场景 | 哪个客户 / 项目 / 团队 / 业务动作 |
| 用户输入 | 用户原始问题或参数，敏感信息需脱敏 |
| Skill 输出 | 当时的完整输出或关键片段 |
| 影响判断 | 影响效率、质量、客户、风险中的哪一类 |
| 处理动作 | 回滚、修正、补规则、补数据、加审批、下线 |

没有证据的复盘，最后只会变成感觉讨论。

### 3. 异常复盘最终要落到版本改进

复盘不是写报告，而是推动 Skill 升级。建议每个异常最终归入四类动作：

```text
补输入 → 补字段 / 补模板 / 补追问
补规则 → 补判断标准 / 反例 / 边界条件
补权限 → 增加审批 / 拦截 / 日志
补体验 → 调整输出结构 / 缩短结果 / 增加可执行动作
```

如果一次异常没有改变 Skill 的任何规则、数据、权限或输出结构，那它大概率没有真正复盘。

## 业务翻译（业务视角）

业务上可以这样理解：

> Skill 不是一次性交付物，而是持续训练出来的业务能力。

过去做 SaaS 功能，线上问题常常是修完 bug 就结束。Skill 不一样，它处理的是业务判断、经营建议、自动生成和流程编排，问题背后往往暴露的是业务规则不清、数据口径不稳、权限边界没定。

管理者要盯住一句话：

> 每一次 Skill 异常，都应该沉淀成一个更清楚的边界、一条更稳定的规则，或者一个更可靠的校验点。

## 典型场景（EZR 业务版）

### 场景 1：导购话术生成 Skill 出现客户投诉

问题表现：导购使用 AI 生成话术时，把活动权益说得过满，客户到店后发现不符合条件。

复盘不能只说“话术生成不准确”，要拆：

| 复盘点 | 要追问 |
|---|---|
| 数据 | 活动规则是否结构化接入？是否有适用门店 / 人群 / 时间限制？ |
| 输入 | 导购是否说明客户身份、门店、活动场景？ |
| 权限 | Skill 是否允许在不确定时直接承诺权益？ |
| 输出 | 是否必须带“以门店实际活动为准”或触发人工确认？ |

改进动作：
- 活动权益类话术必须引用活动规则字段。
- 不满足字段时输出“需人工确认”，不能直接生成承诺型话术。
- 高风险词如“必送、一定、免费、无门槛”进入风险拦截。

### 场景 2：经营诊断 Skill 给出错误建议

问题表现：Skill 判断某门店复购率下降，建议加大会员唤醒，但实际是数据同步延迟导致复购数据不完整。

复盘重点：
- 数据更新时间是否展示？
- 指标异常是否先做数据完整性检查？
- 建议输出前是否标注置信度和数据缺口？

改进动作：
- 所有经营建议必须带数据时间戳。
- 数据缺失超过阈值时，只能输出“数据异常提醒”，不能输出经营建议。
- 诊断结果增加“建议可信度”和“需人工确认项”。

### 场景 3：AI Coding Skill 生成测试用例遗漏核心链路

问题表现：AI 生成了大量边界用例，但漏掉了主交易链路，导致测试看起来完整，实际风险更高。

复盘重点：
- 输入需求是否包含核心业务链路？
- Skill 是否内置“主链路优先”规则？
- 输出是否区分 P0 主链路、P1 分支链路、P2 边界场景？

改进动作：
- 用例生成前先识别主业务链路。
- 输出模板固定分层：主链路 / 异常链路 / 权限链路 / 数据链路。
- 未识别到主链路时，先追问，不直接生成。

## 管理者关注点（成本 / 效率 / 风险）

### 1. 成本

没有复盘机制，团队会重复修同类问题，Skill 维护成本会越来越高。

### 2. 效率

复盘机制能把高频异常转成统一规则，减少人工解释和临时救火。

### 3. 风险

越靠近客户、交易、权益、经营建议的 Skill，越要有异常复盘和冻结机制。不能等客户投诉后才补边界。

## 一句话总结

Skill 出错不可怕，可怕的是每次都靠人解释；真正的组织级 Skill，必须能从异常中持续升级。
