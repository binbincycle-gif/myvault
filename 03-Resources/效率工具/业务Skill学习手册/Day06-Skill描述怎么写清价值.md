# Day06｜Skill 描述怎么写清价值

## 今日主题

今天进入第二阶段：**学会把 Skill 写对。**

第一件事不是写参数，也不是写接口，而是把 Skill 的「描述」写清楚。

Skill 描述决定三件事：

1. Agent 什么时候该调用它；
2. 用户能不能一眼看懂它解决什么问题；
3. 后续维护者能不能判断它的边界。

很多 Skill 写不好的根源，是描述只写了“功能”，没有写“业务价值”和“适用场景”。

---

## 技术原理（技术视角）

### 1. Skill 描述是 Agent 的路由入口

在 Agent 系统里，Skill 描述不是宣传语，而是路由规则的一部分。

它至少要回答：

```text
这个 Skill 解决什么问题？
什么用户/场景下应该调用？
什么情况下不应该调用？
调用后产出什么结果？
```

如果描述过泛，Agent 会乱调用；如果描述过窄，Agent 又会错过真正适合的场景。

### 2. 好描述要包含四个要素

```text
对象 → 场景 → 能力 → 结果
```

| 要素 | 要回答的问题 | 示例 |
|---|---|---|
| 对象 | 谁会用？ | 运营、导购、管理者、客服、产品经理 |
| 场景 | 在什么业务时刻用？ | 看标签变化、判断会员风险、生成资源预警 |
| 能力 | Skill 做什么处理？ | 查询、分析、归因、生成建议、输出报告 |
| 结果 | 用户拿到什么可执行成果？ | 风险清单、行动建议、话术、决策摘要 |

### 3. 描述不是越长越好

Skill 描述要短，但不能空。

不推荐：

> 会员分析 Skill，可以分析会员相关数据。

问题：太泛，Agent 不知道什么时候用，也不知道输出什么。

推荐：

> 当运营或管理者需要判断某品牌会员标签覆盖、变化趋势和异常门店时，输入品牌与时间范围，输出标签占比、变化原因、异常提醒和可执行运营建议。

这句话里包含：

- 谁用：运营 / 管理者
- 什么时候用：判断标签覆盖、趋势、异常
- 输入什么：品牌、时间范围
- 输出什么：占比、原因、异常、建议
- 价值是什么：能直接支持运营动作

## 业务翻译（业务视角）

业务侧看 Skill 描述，不是为了理解技术，而是为了判断：

1. 这个能力是不是我现在要用的？
2. 它能不能替我省判断时间？
3. 它最后给我的东西能不能直接推进工作？

所以描述不要写成“系统能做什么”，要写成“业务能拿它解决什么事”。

### 功能描述 vs 价值描述

#### 功能描述

> 支持查询会员标签、消费记录、触达记录。

这只是能力清单。

#### 价值描述

> 当运营需要判断一批会员是否值得二次触达时，Skill 汇总标签、消费和触达记录，输出会员分层、触达优先级和推荐动作。

这才是业务价值。

## 典型场景（EZR 业务版）

### 场景 1：导购客户洞察 Skill

不推荐描述：

> 查询会员信息，生成客户画像。

推荐描述：

> 当导购准备跟进某个会员时，输入会员ID或会员手机号，Skill 汇总该会员近期消费、偏好、互动和未成交记录，输出今日跟进重点、推荐商品方向和可直接使用的话术。

这类描述能让 Agent 明确：

- 不是泛泛画像；
- 是导购跟进前使用；
- 结果必须落到“今天怎么说、推什么、为什么”。

### 场景 2：资源预警 Skill

不推荐描述：

> 生成资源负载报告。

推荐描述：

> 当技术管理者需要判断未来两周人员负载风险时，Skill 读取任务排期和人员分组，输出超负载人员、低负载人员、可释放人员、调配建议和数据质量风险。

这里的重点不是“报告”，而是“资源调配判断”。

### 场景 3：线上 Bug 月度复盘 Skill

不推荐描述：

> 统计 Bug 数据并生成复盘。

推荐描述：

> 当管理者需要复盘某月线上问题时，Skill 按业务线、场景、责任状态和闭环效率分析 Bug 数据，输出 KPI 摘要、高频问题、未闭环清单和治理建议。

这样描述后，Agent 就知道它不是日常查 Bug，而是月度治理复盘。

```text
       ↓
┌──────────────┐
│ 业务场景      │
│ 在什么时刻调用 │
└──────┬───────┘
       ↓
┌──────────────┐
│ 处理能力      │
│ 查询/分析/生成/判断 │
└──────┬───────┘
       ↓
┌──────────────┐
│ 交付结果      │
│ 清单/建议/话术/报告 │
└──────┬───────┘
       ↓
┌──────────────┐
│ 业务价值      │
│ 可决策/可执行/可追踪 │
└──────────────┘
```

记住一句话：

> Skill 描述不是“我有什么功能”，而是“谁在什么场景下，用我完成什么业务结果”。

## 管理者关注点（成本 / 效率 / 风险）

### 1. 成本

描述写清楚，可以减少后续反复沟通。研发、产品、业务对 Skill 的理解会更一致。

### 2. 效率

描述写清楚，Agent 才能自动判断是否调用，用户也不用每次解释一遍业务背景。

### 3. 风险

描述不清会带来两个风险：

- 乱调用：不该用的场景被调用，结果误导业务；
- 乱期待：用户以为 Skill 能解决所有问题，实际边界不清。

所以描述里要敢于写边界，比如：

> 适用于会员运营诊断，不适用于财务口径收入核算。

## 今日练习

选一个你们当前最常见的业务能力，按下面模板写一版 Skill 描述：

```text
当【目标用户】在【业务场景】需要【解决的问题】时，
输入【必要输入】，
Skill 会【处理动作】，
输出【结果结构】，
用于【下一步业务动作】。
```

示例：

```text
当运营负责人在周会前需要判断会员运营健康度时，
输入品牌、门店范围和时间周期，
Skill 会分析会员规模、活跃、复购、标签变化和异常门店，
输出经营摘要、风险点、机会点和下一步运营建议，
用于周会决策和任务下发。
```

## 今日小结

今天只记住一个标准：

> 一个好的 Skill 描述，必须让人和 Agent 同时知道：什么时候用、怎么用、用完能推进什么事。

如果描述只能说明“它能查什么”，还不够；如果描述能说明“它能帮谁做什么判断、推进什么动作”，这个 Skill 才真正开始有业务价值。
