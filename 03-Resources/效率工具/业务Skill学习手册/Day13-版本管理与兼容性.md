# Day13｜版本管理与兼容性

## 今日主题

今天继续第三阶段：**学会产品化与规模化。**

Day12 讲权限、审批、审计，解决的是“Skill 能不能安全进入生产流程”。Day13 要解决另一个生产级问题：

> Skill 一旦被真实团队、客户或 Agent 工作流依赖，就不能随便改。每一次字段、权限、输出、执行逻辑变化，都可能影响老流程。

业务 Skill 不是写完就结束，而是要长期迭代。版本管理的本质，是让新能力可以发布，同时不破坏已经在跑的老业务。

---

## 技术原理（技术视角）

### 1. Skill 为什么需要版本

一个 Skill 至少有四类东西会变化：

| 变化对象 | 示例                         | 风险     |
| ---- | -------------------------- | ------ |
| 输入参数 | `memberId` 改成 `customerId` | 老调用失败  |
| 输出结构 | 原来返回文本，后来返回 JSON           | 下游解析失败 |
| 权限范围 | 从门店会员扩展到区域会员               | 数据越权风险 |
| 执行动作 | 从生成建议升级为自动提交               | 经营动作失控 |

如果没有版本，所有变化都会直接打到使用者身上。

### 2. 兼容性优先级

生产级 Skill 改动时，优先级建议是：

```text
不破坏老调用 > 新能力更强 > 写法更好看
```

常见兼容策略：

| 策略 | 做法 | 适用场景 |
|---|---|---|
| 保留旧字段 | 新字段上线后，旧字段仍可用一段时间 | 参数重命名 |
| 增加默认值 | 新参数不是必填，系统自动补默认值 | 新增控制项 |
| 双版本并行 | v1 和 v2 同时存在 | 输出结构变化较大 |
| 灰度发布 | 先给内部或少量客户使用 | 风险未知的新能力 |
| 回滚开关 | 出问题可退回旧逻辑 | 影响经营动作的 Skill |

### 3. 破坏性变更要显式标记

下面这些都算破坏性变更：

- 删除必填参数；
- 改变参数含义；
- 输出字段改名或删除；
- 权限范围扩大；
- 从“只生成建议”变成“自动执行”；
- 影响下游工作流判断条件。

破坏性变更不能静默上线，至少要做到：

1. 标记版本号；
2. 通知使用团队；
3. 给迁移时间；
4. 提供回滚方案；
5. 记录变更原因。

## 业务翻译（业务视角）

业务上可以这样理解：

> Skill 版本管理，就是别让今天的新想法，打断客户昨天已经跑起来的流程。

对 EZR 这类 ToB CRM 场景尤其重要。客户一旦把 Skill 接进导购任务、客服流程、经营诊断、指标看板，就会形成依赖。你改一个字段，可能不是“技术小调整”，而是让一线导购收不到任务、客服流程断掉、经营报表口径变了。

所以业务负责人要问：

1. 这次改动影响哪些客户 / 团队 / 工作流？
2. 是否影响老数据、老权限、老输出？
3. 能不能灰度？
4. 出问题能不能退？
5. 有没有告诉前线如何解释？

## 典型场景（EZR 业务版）

### 场景 1：指标库 Skill 升级

原来指标库 Skill 只解释“销售额、客单价、复购率”等指标口径。后来要升级为经营诊断 Skill，自动判断异常原因并生成建议。

建议拆成两个版本：

```text
v1: 指标解释 Skill
- 输入：指标名称、时间范围
- 输出：口径说明、数据来源、适用场景

v2: 经营诊断 Skill
- 输入：指标名称、时间范围、门店/品牌范围、对比口径
- 输出：异常判断、可能原因、建议动作、置信度
```

不要直接把 v1 改成 v2。因为原来只想查口径的人，不一定接受系统自动输出经营建议。

### 场景 2：AI 客服 Skill 迭代

第一版只生成客服回复草稿；第二版希望自动创建工单或触发转人工。

这属于执行层升级，必须保留边界：

```text
v1: 生成回复草稿，人工确认后发送
v1.1: 增加知识库引用和置信度
v2: 可根据规则建议转人工，但不自动提交
v3: 低风险场景自动建工单，高风险场景仍需审批
```

每一步都要有权限、审批和审计记录，不能从“辅助客服”一步跳成“替客服执行”。

### 场景 3：导购智能助手入口升级

App 首页新增智能助手入口后，第一版可能只是“今日会员提醒”；后续会升级成“导购每日任务工作台”。

建议版本节奏：

| 版本 | 能力 | 边界 |
|---|---|---|
| v1 | 提醒今天该看哪些会员 | 只展示建议 |
| v1.1 | 生成触达话术 | 导购确认后发送 |
| v2 | 生成每日任务清单 | 店长可查看执行情况 |
| v3 | 联动营销策略和优惠券 | 涉及券/群发必须审批 |

这样产品可以持续升级，但不会突然改变一线导购和品牌运营的工作方式。

## 管理者关注点（成本 / 效率 / 风险）

### 1. 成本
没有版本管理，后期每次升级都会变成救火：客户报错、前线解释、研发回滚、运营补偿。版本管理前期看起来慢，长期是在省维护成本。

### 2. 效率
稳定版本可以让前线放心复用；灰度版本可以让创新继续推进。两者并行，组织不会因为怕风险而不敢迭代，也不会因为追新能力而破坏老流程。

### 3. 风险
ToB AI Skill 的风险不只是技术报错，而是客户流程被打断、权限被扩大、经营动作失控。版本发布必须和权限、审批、审计一起看。

## 一句话总结

Skill 的版本管理不是技术洁癖，而是 ToB AI 能力进入真实业务流程后的基本交付纪律：新能力要能长出来，老流程不能被打断。
