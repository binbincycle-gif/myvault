# Day30｜Skill 上线前检查清单：从可用到可交付

## 今日主题

Day29 讲的是 Skill 安全边界：权限、审批、回滚与人工确认。

Day30 往前再推一步：**一个业务 Skill 不能因为 Demo 能跑就上线，必须经过“可交付检查”。**

> Demo 证明“能不能做”，上线检查证明“能不能交给真实团队长期使用”。

业务 Skill 从个人工具变成组织资产，最容易卡在这里：

- 试用时效果不错，但真实业务口径没写清；
- Agent 能调用，但输入要求太隐性；
- 输出看起来完整，但无法落到动作；
- 一出错没人知道该找谁、怎么修、是否能回滚；
- 换一个客户、门店、团队就失效。

所以，上线前必须用一张检查清单，把“可用”推进到“可交付”。

---

## 技术原理（技术视角）

### 1. Skill 上线不是发布文件，而是发布一套调用契约

一个可交付 Skill 至少要有 5 个契约：

```text
1. 触发契约：什么场景该调用，什么场景不该调用。
2. 输入契约：需要哪些参数、上下文、数据口径。
3. 输出契约：结果按什么结构返回，哪些字段必须有。
4. 执行契约：是否只生成建议，还是会触发业务动作。
5. 运维契约：异常、版本、审计、回滚由谁负责。
```

如果这些没写清，Agent 可能会“看起来会用”，但实际会误调用、漏输入、乱解释。

### 2. 上线前要做三类测试

业务 Skill 不只测接口通不通，还要测业务结果是否稳定。

```text
A. 正常路径测试：标准输入下能否输出预期结果。
B. 边界路径测试：缺少数据、权限不足、客户场景不匹配时能否正确降级。
C. 业务验收测试：一线角色是否能直接根据结果行动。
```

例如“导购客户跟进 Skill”不能只测试能生成话术，还要测试：

- 没有会员历史购买时怎么处理；
- 会员不属于当前导购时是否拒绝；
- 推荐权益超权限时是否要求审批；
- 输出的话术是否能被导购直接复制或一键确认。

### 3. Skill 必须有版本与负责人

上线后的 Skill 会持续变化：业务规则变、客户权限变、数据字段变、Agent 调用方式变。

因此每个 Skill 至少要记录：

```text
Skill 名称 / 当前版本 / Owner / 适用客户或团队 / 最近更新时间 / 变更说明 / 回滚版本
```

没有 Owner 的 Skill，本质上不是组织资产，只是一次性脚本。

## 业务翻译（业务视角）

业务上可以这样理解：

> 一个 Skill 能不能交付，不看它能不能回答问题，而看它能不能稳定帮人完成一个业务动作。

对 EZR 来说，Skill 上线前要特别看三件事：

1. **是否绑定真实角色**：总部运营、店长、导购、客服、实施顾问分别怎么用。
2. **是否接住真实流程**：不是生成一段建议就结束，而是能进入跟进、审批、执行、回写。
3. **是否能复用到多个客户**：如果只能靠某个人临场解释，说明还不是产品能力。

所以，Skill 的上线标准不是“AI 回答得不错”，而是：

```text
角色知道什么时候用 → Agent 知道怎么调用 → 结果能落到业务动作 → 异常能被处理 → 经验能继续沉淀
```

## 典型场景（EZR 业务版）

### 场景：导购沉默会员唤醒 Skill

上线前检查：

| 检查项 | 要求 |
|---|---|
| 触发场景 | 导购每天查看待跟进沉默会员时触发 |
| 调用角色 | 导购、店长可用；总部运营可看汇总策略 |
| 输入数据 | 会员归属、最近消费、互动记录、偏好标签、可用权益 |
| 输出结构 | 客户优先级、推荐理由、建议话术、推荐权益、下一步动作 |
| 权限边界 | 只能读取当前导购/门店授权会员 |
| 人工确认 | 发送话术、发券、批量触达必须确认 |
| 异常处理 | 数据不足时输出“缺少依据”，不强行推荐 |
| 回写要求 | 记录是否触达、是否回复、是否转化、失败原因 |
| 验收口径 | 导购能否在 3 分钟内完成一次有效跟进 |

这个 Skill 如果只做到“生成话术”，还只是工具；如果能完成“识别对象 → 给出动作 → 执行确认 → 结果回写”，才是业务能力。

### 场景：会员经营诊断 Skill

上线前检查：

- 诊断口径是否经过业务确认；
- 分层结果是否可解释；
- 是否区分总部视角和门店视角；
- 是否能输出行动建议，而不是只有图表总结；
- 是否避免直接写入高影响标签；
- 是否保留每次诊断的输入数据版本和规则版本。

## 管理者关注点（成本/效率/风险）

### 1. 不要把 Demo 当交付

Demo 可以宽松，交付必须严肃。

管理者评审 Skill 时，不要只问“效果好不好”，要问：

- 谁每天会用？
- 用完后做什么？
- 哪个指标会改善？
- 异常谁处理？
- 下个客户能不能复用？

### 2. Skill 上线要有最小运营机制

每个上线 Skill 至少要有：

```text
Owner + 使用说明 + 常见问题 + 版本记录 + 异常反馈入口 + 周期复盘指标
```

否则上线越多，后面越乱。

### 3. 第一批 Skill 要少而硬

早期不要追求 Skill 数量。更建议先打 1-3 个样板：

- 导购客户跟进；
- 会员经营诊断；
- 活动复盘建议。

每个样板都跑通“调用、执行、回写、复盘”，再复制到更多场景。

## 今日练习

选一个准备上线或正在试点的业务 Skill，补齐上线前检查清单：

| 项目 | 内容 |
|---|---|
| Skill 名称 | 例如：导购沉默会员唤醒 Skill |
| 目标角色 | 谁每天会用 |
| 触发场景 | 什么情况下该调用 |
| 必要输入 | 需要哪些参数/数据/上下文 |
| 输出结构 | 必须输出哪些字段 |
| 可执行动作 | 能触发哪些业务动作 |
| 权限边界 | 哪些数据/动作不能越权 |
| 人工确认点 | 哪些动作必须确认 |
| 异常降级 | 数据不足/权限不足/规则冲突时怎么办 |
| 回写机制 | 执行结果如何沉淀 |
| Owner | 谁负责维护 |
| 验收指标 | 用什么判断值得继续投入 |

## 本日自检

1. 这个 Skill 是“Demo 能跑”，还是“真实业务能用”？
2. Agent 在什么情况下会正确调用它？什么情况下应该拒绝调用？
3. 一线人员拿到输出后，是否知道下一步动作？
4. 出错后是否知道找谁、看哪条记录、如何回滚？
5. 这个 Skill 能否复制到第二个客户或第二个团队？

---

## 一句话总结

> Skill 上线前要完成从“功能可演示”到“能力可交付”的检查：触发清楚、输入稳定、输出可行动、权限可控、异常可处理、结果可复盘。
