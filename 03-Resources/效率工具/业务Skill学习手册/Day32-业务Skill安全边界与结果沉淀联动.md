# Day32｜业务Skill安全边界与结果沉淀联动

## 今日主题

把 Day28 的“结果沉淀”和 Day29 的“权限、审批、回滚、人工确认”合并起来看：**一个业务 Skill 不仅要能产生结果，还要能在安全边界内执行，并把执行证据和业务结果沉淀下来。**

如果只有结果沉淀，没有权限治理，可能把错误或越权动作沉淀成组织经验；如果只有安全边界，没有结果回写，Skill 只能停留在一次性建议，无法形成复利。

## 技术原理（技术视角）

### 1. Skill 执行链要同时记录“结果”和“责任”

业务 Skill 的最小可追溯链路应包括：

```text
调用者身份
  ↓
数据权限校验
  ↓
Skill 输出建议
  ↓
风险分级
  ↓
人工确认 / 审批
  ↓
执行动作
  ↓
结果回写
  ↓
经验沉淀或异常纠偏
```

每一步都要能回答：谁调用、看了什么、建议了什么、谁确认、执行了什么、结果如何、哪些内容允许进入长期知识。

### 2. 沉淀内容必须经过可信度分层

建议按以下规则处理：

- **运行日志**：保留调用过程、权限判断、错误信息、原始输入输出。
- **项目记忆**：保留已确认的客户规则、门店执行经验、项目异常。
- **组织知识**：只保留经过人工确认、可跨项目复用的口径、模板、风险清单和有效模式。

未经确认的模型推测、错误建议、敏感会员明细，不应直接进入组织知识。

### 3. 动作级权限比功能级权限更重要

同一个 Skill 在不同角色手里，允许的动作不同：

- 导购：查看本人会员池，生成一对一跟进建议；
- 店长：查看门店范围，审核部分任务；
- 总部运营：配置规则、查看汇总结果；
- 管理员：维护 Skill 配置和审计策略。

因此要按“身份 + 数据范围 + 业务动作 + 风险等级”综合判定，不能只判断“能不能打开这个 Skill”。

## 业务翻译（业务视角）

业务上，Skill 不是一个更聪明的按钮，而是一个进入经营流程的数字岗位。岗位要有：

- 能看什么；
- 能建议什么；
- 能执行到哪一步；
- 谁对结果负责；
- 出错后如何撤回；
- 哪些经验可以被组织继承。

对于 EZR，真正可交付的业务 Skill 必须同时具备三种能力：

1. **业务价值**：能推动会员触达、到店、成交或交付效率；
2. **治理能力**：权限、审批、审计、回滚可落地；
3. **进化能力**：执行结果能回写 CRM，并反哺下一次调用。

## 典型场景（EZR 业务版）

### 场景：导购沉默会员唤醒 Skill

建议将动作分成四级：

- **L0 只读查询**：读取导购本人会员池和沉默口径；
- **L1 建议生成**：输出优先级、推荐商品、推荐理由和话术；
- **L2 半自动执行**：导购确认后创建跟进任务或发送单条消息；
- **L3 高风险执行**：批量触达、发放高面额权益、跨门店触达，必须审批，默认不自动执行。

执行后至少回写：

- 是否采纳建议；
- 是否实际触达；
- 触达渠道和话术版本；
- 客户是否回复、到店、下单；
- 未采纳和异常原因；
- 是否允许将该案例脱敏后沉淀为经验。

### 最小闭环

```text
会员机会识别
  → 生成跟进建议
  → 导购确认
  → 触达客户
  → CRM回写反馈
  → 复盘有效话术与权益
  → 更新Skill规则
```

## 管理者关注点（成本 / 效率 / 风险）

1. **不要把“人工确认”当口号**：确认点必须设计成产品流程，有明确按钮、责任人和记录。
2. **不要把所有结果都写入知识库**：先区分临时记录、项目记忆、组织知识，避免知识污染。
3. **不要只看调用次数**：更应该看采纳率、触达完成率、结果转化率、异常率和有效经验复用率。
4. **先做半自动闭环**：优先验证“建议是否有用、动作是否被执行、结果是否能回写”，再考虑扩大自动化范围。
5. **商业化前必须过治理门槛**：没有权限、审计、回滚和客户可解释性，不能把 Demo 直接包装成交付产品。

## 今日练习

为一个正在推进的业务 Skill 补一张“安全与沉淀联动表”：

| 环节 | 必须明确的内容 |
|---|---|
| 调用身份 | 谁调用，代表谁工作 |
| 数据边界 | 可读哪些数据，数据范围是什么 |
| 输出等级 | 查询、建议、半自动执行还是自动执行 |
| 人工确认 | 哪些动作必须由谁确认 |
| 审批条件 | 哪些高风险动作需要审批 |
| 执行记录 | 记录谁、何时、基于什么输入执行 |
| 结果回写 | 回写到 CRM 的哪些字段 |
| 沉淀规则 | 哪些内容进入项目记忆或组织知识 |
| 纠偏机制 | 错误结果如何撤回、修正和清理 |

## 本日自检

1. 当前业务 Skill 的“结果回写”是否和“权限审计”连接起来了？
2. 如果导购采纳了错误建议，能否追溯到调用身份、数据口径和确认人？
3. 哪些结果值得沉淀成组织知识，哪些只能保留在运行日志？
4. 在智能导购 MVP 中，今天能否先完成一个 L1→L2→结果回写的最小闭环？

## 一句话总结

> 可进化的业务 Skill，必须在安全边界内执行，在结果回写中学习，在人工确认和审计机制下形成组织资产。
