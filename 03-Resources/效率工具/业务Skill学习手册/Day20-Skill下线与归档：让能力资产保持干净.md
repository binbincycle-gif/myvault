# Day20｜Skill下线与归档：让能力资产保持干净

## 今日主题

Day19 讲的是灰度发布：一个 Skill 写出来后，要先小范围验证价值、边界和风险，再决定是否扩大。

Day20 继续往后走一步：**Skill 不是上线后就永远存在，它也需要下线、归档和替换机制。**

> Skill 下线与归档的核心，不是“把旧东西删掉”，而是让组织的 AI 能力资产始终可信、可用、可治理。

业务 Skill 一旦进入组织使用，就会慢慢形成依赖。如果旧 Skill 不下线、不标记、不归档，最容易出现三类问题：

1. 旧口径继续被人使用，导致结论和当前业务规则不一致。
2. 多个相似 Skill 并存，员工不知道该用哪个。
3. Skill 已经不维护，但仍在被调用，出了问题找不到责任人。

所以今天要学的是：如何判断一个 Skill 应该继续运营、合并升级、冻结观察，还是正式下线归档。

---

## 技术原理（技术视角）

### 1. Skill 要有生命周期状态

一个组织级 Skill 不应该只有“有 / 没有”两种状态，至少要有 6 种状态：

| 状态 | 含义 | 管理动作 |
|---|---|---|
| 草稿 | 还在设计中 | 不开放真实业务使用 |
| 灰度 | 小范围试点 | 限定人群、场景、数据和权限 |
| 正式 | 已通过验证 | 进入目录、看板和运营机制 |
| 冻结 | 暂停扩大使用 | 保留现状，等待修复或评审 |
| 废弃 | 不建议继续使用 | 标记替代方案，限制新调用 |
| 归档 | 已退出生产使用 | 保留历史记录，不再触发 |

没有生命周期状态，Skill 目录会很快变成“AI 工具垃圾箱”。

### 2. 下线判断要看 5 类信号

Skill 是否应该下线，不能只看“有没有人用”。至少看 5 类信号：

| 信号 | 判断问题 |
|---|---|
| 业务规则变化 | 原 Skill 的判断逻辑是否已经过期？ |
| 数据口径变化 | 输入数据、指标定义、权限范围是否变化？ |
| 使用量下降 | 用户是否已经转向更好的工作流？ |
| 异常率升高 | 是否频繁出现事实、权限、口径或体验问题？ |
| 替代能力出现 | 是否已有新版 Skill / 工作流覆盖同一场景？ |

如果一个 Skill 已经低使用、高异常、无人维护，就应该进入废弃或归档，而不是继续挂在目录里。

### 3. 下线不是直接删除，而是受控迁移

Skill 下线至少要做三件事：

```text
标记：明确 Skill 已废弃 / 待下线 / 已归档
迁移：说明推荐使用哪个新版 Skill 或人工流程
留痕：保留版本、负责人、下线原因和影响范围
```

直接删除会破坏可追溯性；完全不删会污染能力目录。正确做法是：生产入口下线，历史资产归档。

## 业务翻译（业务视角）

业务上可以这样理解：

> Skill 下线与归档，就是定期清理组织的 AI 能力货架，保证员工看到的是当前最可靠、最值得使用的能力。

过去 SaaS 功能旧一点，用户最多不用。但 Skill 不一样，它会参与判断、建议、总结、流程甚至客户沟通。旧 Skill 如果继续被用，可能会把过期规则包装成“智能建议”，反而更危险。

管理者要盯住三句话：

1. Skill 上架要有标准，下架也要有标准。
2. 没有负责人维护的 Skill，不能长期留在正式目录。
3. 下线不是否定过去，而是为了让新的能力更可信。

## 典型场景（EZR 业务版）

### 场景 1：会员经营诊断 Skill 口径变化

**背景**：会员分层规则升级，新增了生命周期、沉默风险和复购潜力字段。

**风险**：旧诊断 Skill 仍按原标签判断，可能给出过期建议。

**处理方式**：
- 将旧 Skill 标记为“废弃”。
- 在入口提示“请使用新版会员经营诊断 Skill”。
- 归档旧版本的输入、输出、指标口径和下线原因。
- 对过去使用旧 Skill 生成的重要报告，保留口径说明。

### 场景 2：导购推荐 Skill 被新版工作流替代

**背景**：原 Skill 只生成“推荐跟进会员”，新版工作流已经覆盖“推荐名单 → 推荐理由 → 话术 → 触达反馈 → 转化复盘”。

**风险**：两个 Skill 并存，导购不知道该用哪个，数据反馈也被拆散。

**处理方式**：
- 原 Skill 不再作为独立入口开放。
- 将其能力合并进新版导购工作流。
- 目录中保留归档记录，说明已被哪个工作流替代。

### 场景 3：AI Coding 测试用例 Skill 长期无人维护

**背景**：测试框架、接口规范和权限模型已经变化，但 Skill 提示词和样例没有更新。

**风险**：生成的测试用例覆盖旧链路，影响质量判断。

**处理方式**：
- 先冻结，不再扩大使用范围。
- 由测试负责人判断是否升级。
- 若两周内无人维护，正式废弃并归档。
- 如保留价值，重建新版 Skill，并补充新接口、新权限、新异常链路样例。

## 管理者关注点（成本 / 效率 / 风险）

### 1. 成本

不下线旧 Skill，会让员工反复踩坑，也会增加解释、纠错和培训成本。

### 2. 效率

能力目录越干净，员工越容易找到正确入口。Skill 越多不等于组织越智能，可信能力越多才算。

### 3. 风险

涉及客户、交易、权益、指标、权限的 Skill，如果口径过期还继续被用，风险比普通文档更高。必须有冻结、废弃和归档机制。

## 本日自检

1. 当前业务 Skill 目录里，是否存在多个功能相似但没人合并的 Skill？
2. 是否有 Skill 的业务规则、数据口径或权限边界已经过期？
3. 每个正式 Skill 是否有明确负责人和维护周期？
4. 如果今天要下线一个 Skill，是否能说明替代方案和影响范围？

---

## 一句话总结

Skill 资产不是越多越好；能上架、能运营、能下线、能归档，才是真正可治理的组织级 AI 能力。
