# Day08｜输出结构与结果解释

## 今日主题

今天继续第二阶段：**学会把 Skill 写对。**

Day07 讲「参数」：让 Skill 拿到稳定输入。  
Day08 讲「输出」：让 Skill 返回可理解、可执行、可复盘的结果。

一句话：

> 输入决定 Skill 能不能干活，输出决定业务敢不敢用、能不能继续用。

很多 Skill 看起来能跑，但业务不愿意用，原因不是能力弱，而是输出像一段“聪明但没法落地的文字”：没有结论、没有动作、没有依据、没有风险边界，也没有下一步。

---

## 技术原理（技术视角）

### 1. 输出也是契约，不是自由发挥

Skill 的输出要像接口返回一样稳定。

至少回答 5 件事：

```text
结论是什么？
依据是什么？
建议做什么？
风险在哪里？
后续如何验证？
```

如果输入 Schema 是“进门规则”，输出结构就是“交付物标准”。

### 2. 好输出要分层

不推荐把所有内容混成一段长文。

推荐按使用者分层：

| 层级 | 目的 | 典型内容 |
|---|---|---|
| summary | 让管理者快速判断 | 一句话结论 / 风险等级 / 是否需要拍板 |
| evidence | 让结果可信 | 数据口径 / 关键样本 / 计算依据 |
| actions | 让一线能执行 | 负责人 / 动作 / 截止时间 / 优先级 |
| risks | 让组织可控 | 权限、合规、误判、执行风险 |
| nextCheck | 让结果可复盘 | 晚上/明天看什么指标 |

### 3. 输出要尽量结构化

业务 Skill 可以同时输出两层：

1. **人看的解释**：适合会议、群沟通、日报。
2. **机器看的结构**：适合继续被 Agent 编排、沉淀台账、触发下游动作。

示例：

```json
{
  "summary": "本周沉默高价值会员中，A类门店风险最高，建议优先安排导购跟进。",
  "riskLevel": "high",
  "actions": [
    {
      "ownerRole": "store_manager",
      "action": "安排导购今日完成TOP20会员一对一触达",
      "deadline": "today_18:00",
      "priority": "P1"
    }
  ],
  "nextCheck": "今晚复盘触达完成率、回复率、成交转化。"
}
```

## 业务翻译（业务视角）

业务侧不关心输出格式多漂亮，只关心三件事：

1. **看得懂**：结论是不是第一眼就明白；
2. **敢执行**：建议有没有依据和风险边界；
3. **能复盘**：晚上或下周能不能判断这个建议有没有价值。

输出差，业务体验是：

- “说了很多，但不知道要干嘛”；
- “建议像对的，但不知道依据”；
- “没有责任人和截止时间”；
- “执行完也不知道效果好不好”。

输出好，业务体验是：

- 管理者能拍板；
- 一线能照着做；
- 研发能继续接流程；
- 运营能沉淀成 SOP。

## 典型场景（EZR 业务版）

### 场景 1：会员标签洞察 Skill

目标：帮助运营判断会员标签覆盖和异常。

推荐输出结构：

```json
{
  "summary": "会员标签覆盖率下降，主要集中在新客入会后的7日内。",
  "keyFindings": [
    "近7日新客标签覆盖率低于历史均值",
    "导购手工补标比例下降",
    "部分门店标签缺失集中"
  ],
  "suggestedActions": [
    "先抽查覆盖率最低的10家门店",
    "补一条新客入会后自动打标规则",
    "本周复盘标签覆盖率是否回升"
  ],
  "risks": ["样本周期较短，需避免直接扩大到全部门店判断"],
  "nextCheck": "明天看新客标签覆盖率、门店补标完成率。"
}
```

管理重点：不要只给“数据列表”，必须给“判断 + 动作 + 复盘口径”。

### 场景 2：导购跟进建议 Skill

目标：导购打开会员详情时，拿到今日跟进建议。

推荐输出结构：

```json
{
  "customerBrief": "近30天浏览连衣裙3次未下单，偏好中高价格带，最近一次互动停留在尺码咨询。",
  "recommendation": "建议先从尺码和上身效果切入，不要直接促销逼单。",
  "messageDrafts": [
    "上次您看的那款连衣裙尺码我帮您确认过了，按您之前买过的版型建议选M，会更稳。",
    "这款这周有到店试穿反馈，我可以发您两张真实上身图参考。"
  ],
  "riskNote": "不要直接推满减券，客户当前更像是尺码顾虑，不是价格顾虑。",
  "nextCheck": "记录客户是否回复、是否进店/下单、是否继续沉默。"
}
```

管理重点：导购 Skill 的输出不能只生成话术，要解释“为什么这样说”。否则导购无法学习，只是在复制文案。

### 场景 3：资源预警 Skill

目标：帮助技术管理者判断未来两周资源风险。

推荐输出结构：

```json
{
  "summary": "未来两周业务测试组负载偏高，存在验收排队风险。",
  "riskLevel": "medium_high",
  "evidence": [
    "多人排期超过正常负载区间",
    "未分配任务集中在本周后半段",
    "关键迭代存在测试资源冲突"
  ],
  "actions": [
    "今天先确认P1需求测试优先级",
    "低优任务延期或拆分验收",
    "必要时协调可支援人员临时补位"
  ],
  "decisionNeeded": "是否允许部分非关键需求顺延到下周。",
  "nextCheck": "今晚看P1需求是否都有明确测试责任人和验收时间。"
}
```

管理重点：预警类 Skill 一定要区分“事实、判断、建议、需拍板项”。混在一起容易造成误解。

## 输出结构设计清单

写业务 Skill 时，输出至少检查 8 项：

1. 是否有一句话结论？
2. 是否说明数据/判断依据？
3. 是否给出可执行动作？
4. 是否明确责任角色或使用场景？
5. 是否标出风险边界？
6. 是否有下一步复盘指标？
7. 是否方便复制到会议/群/日报？
8. 是否能被下游 Agent 继续读取和编排？

## 图示

```text
Skill 输出
  ↓
一句话结论
  ↓
关键依据
  ↓
建议动作
  ↓
风险边界
  ↓
复盘指标
  ↓
可继续编排 / 可沉淀台账
```

记住一句话：

> Skill 的输出不是“回答问题”，而是交付一个能被人执行、被组织复盘、被系统继续编排的结果包。

---

## 管理者关注点（成本 / 效率 / 风险）

### 1. 成本

输出结构稳定后，会议材料、日报、群沟通可以复用同一套结果，减少二次整理成本。

### 2. 效率

输出里直接带动作、责任角色和复盘口径，能减少“看完还要再开会解释”的情况。

### 3. 风险

AI 输出如果只给结论不解释依据，容易被误用；如果只给建议不写边界，容易越权执行。尤其是营销、发券、客户触达、资源调配类 Skill，要默认加入风险说明和审批提示。

## 本日自检

1. 我写的 Skill 输出，是“文章”，还是“结果包”？
2. 业务看完后，能不能在 30 秒内知道下一步做什么？
3. 这个输出能不能被另一个 Agent 继续拿去执行或复盘？

---

## 一句话总结

参数让 Skill 稳定输入，输出让 Skill 形成价值；没有结构化输出，Skill 就很难从“能回答”升级为“能交付”。
