# Day27｜Skill 上下文工程：让 Agent 拿到正确业务资料

## 今日主题

Day26 讲的是：从 Agent 调用视角看，一个 Skill 要让 Agent 知道什么时候该用、缺什么信息、边界在哪里。

Day27 继续往前走一步：**Skill 被正确调用之后，Agent 是否拿到了足够准确、足够新、足够可执行的业务上下文。**

> Skill 的效果，往往不是输在模型能力，而是输在上下文不准：资料过旧、口径不清、字段缺失、权限边界模糊。

---

## 技术原理（技术视角）

### 1. Skill 执行依赖三类上下文

一个业务 Skill 稳定执行，通常需要三类上下文：

1. **任务上下文**：用户今天要解决什么问题，目标是什么，输出给谁看。
2. **业务上下文**：客户、组织、流程、指标、字段、规则、历史案例。
3. **运行上下文**：当前可用工具、权限、数据源、是否允许写入或对外发送。

如果只拿到任务上下文，没有业务上下文，Agent 会输出泛泛建议；如果有业务上下文但没有运行上下文，Agent 可能越权或给出无法落地的动作。

### 2. 上下文不是越多越好，而是要可判定

业务 Skill 最怕把大量文档一次性塞给 Agent。真正有效的上下文应该满足：

- **来源清楚**：来自哪个系统、哪个知识库、哪个会议纪要。
- **口径明确**：字段、指标、范围、时间窗口说清楚。
- **优先级清楚**：冲突时以哪个来源为准。
- **边界可执行**：哪些只能读，哪些能写，哪些必须人工确认。

上下文工程的目标不是“让 Agent 看很多资料”，而是“让 Agent 知道该信什么、该用什么、不能做什么”。

### 3. 业务 Skill 要内置上下文检查

一个成熟的 Skill，执行前至少要检查：

```text
1. 当前目标是否明确？
2. 所需业务资料是否存在？
3. 数据口径是否有时间范围？
4. 是否涉及敏感数据或外部动作？
5. 输出是否需要引用来源或标注置信度？
```

只要其中一项缺失，Agent 就不应该硬给确定结论，而应该：

- 先给草案；
- 标注假设；
- 追问关键缺口；
- 或降级为“待确认清单”。

## 业务翻译（业务视角）

业务上可以这样理解：

> 以前做系统，是把数据放进页面；现在做 Skill，是把正确上下文放到 Agent 手边。

例如智能导购场景里，Agent 不能只知道“生成跟进话术”，还要知道：

- 这个品牌的会员分层规则；
- 当前门店活动；
- 会员历史购买偏好；
- 导购可用权益；
- 哪些动作需要人工确认；
- 跟进后结果要回写哪里。

否则话术再漂亮，也只是内容生成，不是业务能力。

## 典型场景（EZR 业务版）

### 场景：沉睡会员激活 Skill

如果 Agent 只拿到一句话：

> 帮我生成沉睡会员激活建议。

输出大概率会变成通用营销话术。

更好的上下文包应该包括：

```text
业务目标：提升沉睡会员回店 / 复购
适用范围：品牌、门店、导购权限范围
会员口径：多久未消费算沉睡，是否排除黑名单 / 退货异常会员
数据字段：最近消费时间、客单价、品类偏好、尺码、折扣敏感度、历史触达记录
可用权益：优惠券、会员日、导购专属福利、门店活动
动作边界：只生成建议，不自动群发；发券和触达必须人工确认
结果回写：跟进状态、触达方式、会员反馈、是否到店 / 下单
复盘指标：触达率、回复率、到店率、转化率、客单价变化
```

这样 Skill 才能从“写文案”升级为“驱动导购动作”。

## 管理者关注点（成本 / 效率 / 风险）

### 1. 成本

上下文不标准，后续每个 Skill 都要重复解释业务背景，组织资产无法复用。

### 2. 效率

把高频业务上下文做成标准包后，Agent 执行速度会明显提升，且不同人调用结果更一致。

### 3. 风险

CRM、会员、导购、营销类 Skill 涉及客户数据和外部触达，必须把权限、确认、审计、回写边界写清楚，不能让 Agent 自由发挥。

## 本日自检

1. 你手上准备做成 Skill 的业务能力，是否已经列出必需上下文？
2. 这些上下文来自哪里？知识库、接口、报表、会议纪要，还是人工经验？
3. 如果数据缺失或口径冲突，Skill 是继续执行、先追问，还是降级输出待确认清单？

---

## 一句话总结

Skill 不是只写执行步骤，更要设计上下文入口；Agent 拿不到正确业务资料，就只能生成内容，不能交付结果。
