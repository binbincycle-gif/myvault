# Day60｜Skill 上下文工程：让 Agent 拿到正确业务资料

> 对应学习章节：[[Day27-Skill上下文工程：让Agent拿到正确业务资料]]
> 衔接上篇：[[2026-10-23-Day59-Agent调用视角-Skill行动边界]]

## 今日主题

Skill 被正确触发，不代表能正确执行。决定结果的往往不是模型，而是 Agent 是否获得了**准确、最新、可执行且受控的业务上下文**。

核心判断：**Skill 不是只写执行步骤，更要设计上下文入口；拿不到正确资料，Agent 只能生成内容，不能交付结果。**

## 三类上下文，缺一不可

| 类型 | 要回答的问题 | CRM/导购场景示例 |
|---|---|---|
| 任务上下文 | 今天解决什么、输出给谁、成功标准是什么 | 提升沉睡会员回店，输出给某门店导购 |
| 业务上下文 | 客户、规则、字段、口径、历史案例是什么 | 品牌规则、会员分层、活动、权益、触达记录 |
| 运行上下文 | 有什么工具和权限、能否写入/外发 | 可读哪些会员、是否可建任务、发券是否需确认 |

只有任务上下文，会输出泛泛建议；缺运行上下文，可能越权或给出无法落地的动作。

## 上下文工程不是“塞更多资料”

有效上下文必须做到：

1. **来源清楚**：来自哪个系统、知识库或会议纪要。
2. **口径明确**：字段、指标、范围、时间窗口可判定。
3. **优先级清楚**：来源冲突时，以什么为准。
4. **边界可执行**：哪些只读、哪些能写、哪些必须人工确认。

目标不是让 Agent 看得更多，而是让它知道**该信什么、该用什么、不能做什么**。

## Skill 执行前的 5 项检查

```text
1. 当前目标是否明确？
2. 所需业务资料是否存在？
3. 数据口径与时间范围是否明确？
4. 是否涉及敏感数据或对外动作？
5. 输出是否需要引用来源或标注置信度？
```

任意一项缺失，不应该硬给确定结论；应选择：给草案并标假设、追问关键缺口，或降级为待确认清单。

## 沉睡会员激活 Skill 的上下文包

```text
业务目标：提升沉睡会员回店/复购
适用范围：品牌、门店、导购权限范围
会员口径：沉睡周期；排除黑名单与退货异常会员
数据字段：最近消费、客单、品类偏好、尺码、折扣敏感度、历史触达
可用权益：优惠券、会员日、导购福利、门店活动
动作边界：只生成建议；发券和触达须人工确认
结果回写：跟进状态、触达方式、会员反馈、是否到店/下单
复盘指标：触达率、回复率、到店率、转化率、客单价变化
```

## 今日可执行动作

1. 为 CRM Agent 首个闭环场景建立一张**上下文清单**：任务、业务、运行三类字段逐项列出来源、时间范围和更新责任人。
2. 把“来源冲突/数据缺失”写进场景降级规则：哪些可先出草案，哪些必须追问，哪些必须停止执行。
3. 对任何涉及会员数据、权益、外发或写入的能力，强制把权限、人工确认、审计、回写字段放进上下文包。

## 晚间自检

1. 所需上下文分别来自知识库、接口、报表还是人工经验？
2. 数据缺失或口径冲突时，Agent 的降级动作是什么？
3. 上下文是否写清数据时间窗口、权限与人工确认边界？
4. 输出是否能回写并支持后续复盘？

## 一句话结论

**高质量 Skill 不靠“更多提示词”，靠在执行前把任务目标、业务规则和运行边界交代准确。**
