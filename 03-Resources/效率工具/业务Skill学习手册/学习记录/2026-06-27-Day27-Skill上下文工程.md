## 核心结论
业务 Skill 的稳定性，很多时候不是输在模型，而是输在上下文：资料过旧、口径不清、字段缺失、权限边界模糊。一个可交付的 Skill，必须在执行前确认三类上下文：

1. **任务上下文**：今天要解决什么问题，输出给谁，成功标准是什么。
2. **业务上下文**：客户、组织、流程、指标、字段、规则、历史案例。
3. **运行上下文**：可用工具、权限边界、数据源、是否允许写入或对外发送。

## 对 EZR / 智能导购的直接启发
以“沉睡会员激活 Skill”为例，不能只让 Agent 生成话术，而要给它一套可判定的上下文包：

- 会员口径：多久未消费算沉睡，是否排除黑名单 / 退货异常会员。
- 数据字段：最近消费时间、客单价、品类偏好、尺码、折扣敏感度、历史触达记录。
- 可用权益：优惠券、会员日、导购专属福利、门店活动。
- 权限边界：只生成建议，不自动群发；发券和触达必须人工确认。
- 结果回写：跟进状态、触达方式、会员反馈、是否到店 / 下单。
- 复盘指标：触达率、回复率、到店率、转化率、客单价变化。

## 今天可落到的一个动作
给“近 30 天高价值未触达会员识别 / 跟进建议 Skill”补一版上下文检查清单：

```text
Skill 名称：高价值未触达会员跟进建议
目标场景：导购每日会员经营
任务上下文：找出近 30 天高价值但未触达会员，并生成跟进建议
业务上下文：会员分层口径、最近消费、偏好、触达历史、可用权益、门店活动
运行上下文：导购仅查看本人会员池；AI 只生成建议；发送触达需导购确认
缺失降级：缺权益/活动时，只输出会员清单 + 待确认字段，不生成强促销话术
结果回写：跟进状态、会员反馈、成交/未成交原因
复盘指标：触达率、回复率、到店率、转化率
```

## 晚上复盘问题
1. 今天是否明确了一个业务 Skill 的必需上下文，而不是只写执行步骤？
2. 哪些上下文来自系统字段，哪些还停留在人工经验？
3. 如果字段缺失或口径冲突，Skill 是否有降级策略？

## 一句话沉淀
Skill 不是只写“怎么做”，而是先保证 Agent 拿到“该信什么、该用什么、不能做什么”。
