## 今日抓到的核心判断

业务 Skill 的规模化，不是“让更多人试试”，而是把一条已验证的业务动作链，整理成别人也能照着执行的交付包。

对“导购沉默会员唤醒 Skill”来说，放大前必须回答：

```text
谁用 → 什么时候用 → 需要哪些数据 → 输出什么动作 → 哪些必须人工确认 → 结果怎么回写 → 风险怎么兜底
```

如果这些没写清，扩大试点范围只会带来三类问题：
- 换导购后不知道怎么用；
- 换门店后数据口径不一致；
- 换品牌后权限、权益和话术风险不可控。

所以今天的重点不是新增功能，而是把 Day32/Day33 的 MVP 试点经验，压成一份可复制的 Skill 交付包。

## 导购沉默会员唤醒 Skill｜交付包草案

| 模块 | 当前建议 |
|---|---|
| Skill 名称 | 导购沉默会员唤醒 Skill |
| 适用角色 | 导购、店长、区域运营；总部运营只看汇总策略，不直接代替导购触达 |
| 触发时机 | 每日开店前、活动前一天、会员沉默预警后 |
| 核心输入 | 会员归属、最近消费、互动记录、偏好标签、活动/权益信息、导购身份权限 |
| 核心输出 | 今日优先跟进会员、推荐理由、建议话术、风险提示、下一步动作 |
| 人工确认 | 是否触达、是否采用话术、是否发券、是否升级为重点客户 |
| 反馈字段 | 是否采纳、是否触达、客户是否回复、是否到店/成交/预约/加购、未采纳原因、风险备注 |
| 禁止动作 | 不自动发消息、不自动发券、不跨门店查看会员、不生成高承诺营销话术 |
| 复盘节奏 | 每日看使用和触达，每周看采纳率、回复率、成交线索和可沉淀规则 |

## 三层复制节奏

### 第 1 层：同门店多导购复制
目标：验证这个 Skill 是否只适合某个强导购，还是普通导购也能用。

要看：
- 新导购是否能在 3 分钟内完成一次跟进；
- 推荐理由是否容易理解；
- 话术是否需要大量人工改写；
- 触达反馈是否能稳定回写。

### 第 2 层：同品牌不同门店复制
目标：验证门店差异是否影响推荐效果。

要看：
- 不同门店会员沉默原因是否一致；
- 权益和活动配置是否能复用；
- 店长是否能通过汇总数据指导导购动作；
- 是否出现跨门店权限或客户归属风险。

### 第 3 层：不同品牌客户化复制
目标：验证这是不是标准产品能力，而不是单客户项目经验。

要看：
- 输入字段是否能配置化；
- 推荐规则是否需要品牌化参数；
- 话术风格是否可按品牌调节；
- 权限、审计、回滚是否足够支撑客户交付。

## 今日可以推进的一个动作

给“导购沉默会员唤醒 Skill”补一份 **最小交付包**，先不要做大文档，只补 7 个字段：

```text
1. 触发条件
2. 使用角色
3. 必要输入
4. 标准输出
5. 人工确认点
6. 反馈字段
7. 风险边界
```

这份交付包的目标，是让下一个试点门店不靠产品经理口头解释，也能知道怎么用、怎么反馈、出了问题怎么停。

## 对产品和技术的提醒

### 产品侧
- 不要把“扩大试点”理解成“多开几个账号”。
- 先把使用说明、反馈字段和风险边界写清，再扩范围。
- 产品下一阶段重点不是堆功能，而是验证：换导购、换门店、换品牌后，动作链是否还能成立。

### 技术侧
- 需要尽早固化调用日志、采纳状态、触达反馈和结果回写字段。
- 权限判断要按导购/门店/品牌范围做，不允许为了试点临时放宽。
- 后续如果接自动触达，必须增加审批、审计、回滚机制；当前阶段继续坚持人工确认。

### 组织侧
- 试点 Owner 要负责交付包，而不是只负责 Demo。
- 扩大前必须给出“放大范围、负责人、复盘时间、暂停条件”。
- 每扩大一层，都要重新看使用、动作、结果、风险，不用一次性铺开。

## 晚上复盘问题

3. 哪些字段必须标准化，哪些字段允许品牌/门店配置？
4. 当前最适合先复制到同门店多导购，还是同品牌不同门店？
5. 有没有明确暂停条件，避免风险扩大后才补救？

## 一句话总结

Day34 的重点是把“导购沉默会员唤醒 Skill”从 MVP 试点推向可复制交付：**先交付包，后扩范围；先复制动作链，后复制功能入口；先守住权限和反馈闭环，再谈规模化。**
