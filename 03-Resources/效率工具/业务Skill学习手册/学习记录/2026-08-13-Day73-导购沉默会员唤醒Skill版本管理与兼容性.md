Day72 补的是生产级安全底线：权限、审批、审计。

Day73 要补的是生产级迭代纪律：**导购沉默会员唤醒 Skill 一旦被导购、店长、运营或客户工作流依赖，就不能随便改字段、改权限、改输出、改执行动作。**

一句话：**版本管理不是技术洁癖，而是避免“今天的新能力”打断“昨天已经跑起来的客户流程”。**

## 导购沉默会员唤醒 Skill｜版本管理与兼容性 v0.1

### 1. 建议版本边界

| 版本 | 核心能力 | 默认边界 | 是否可进入生产 |
|---|---|---|---|
| v0.1 | 生成沉默会员分层与唤醒建议 | 只输出建议，不触达、不写回 | 内部验证 |
| v0.2 | 生成导购一对一话术草稿 | 导购确认后发送 | 小范围灰度 |
| v0.3 | 支持触达结果回写与复盘指标 | 只写回授权字段，保留审计 | 试点门店 |
| v1.0 | 标准化沉默会员唤醒 Skill | 权限、审批、审计、回滚齐备 | 可交付客户 |
| v1.1 | 增加运营策略配置，如沉默周期、会员分层规则 | 新增参数必须有默认值 | 兼容升级 |
| v2.0 | 联动权益、优惠券、活动任务 | 涉及权益必须审批，不能自动发券 | 高风险灰度 |

### 2. 兼容性原则

```text
不破坏老调用 > 新能力更强 > 写法更好看
```

对导购沉默会员唤醒 Skill 来说，以下能力上线必须遵守兼容策略：

| 改动类型 | 示例 | 兼容策略 |
|---|---|---|
| 参数新增 | 新增 `silentDays`、`memberLevel`、`storeScope` | 默认非必填，系统补默认值 |
| 参数改名 | `memberId` 改为 `customerId` | 保留旧字段一段时间，输出迁移提醒 |
| 输出变化 | 原来输出文本，改为 JSON 列表 | v1/v2 双版本并行 |
| 权限扩大 | 从导购本人会员池扩到本店会员池 | 必须标记高风险变更，走审批 |
| 执行动作升级 | 从生成话术变为自动触达 | 必须新版本，不允许覆盖旧版本 |
| 结果回写变化 | 新增“未采纳原因”“客户反馈标签” | 增加默认值，不影响旧流程 |

### 3. 破坏性变更清单

以下改动不能静默上线：

1. 删除原有必填参数或改变参数含义；
2. 输出字段改名、删除或结构大改；
3. 扩大会员数据查看范围；
4. 从“只生成建议”升级为“自动执行触达 / 发券 / 写回”；
5. 改变沉默会员筛选口径，导致名单大幅变化；
6. 改变导购、店长、运营的可见范围；
7. 影响下游看板、复盘报表或客户汇报口径。

### 4. 灰度与回滚规则

#### 灰度规则

```text
内部样例验证 → 单品牌/单门店灰度 → 多门店扩围 → 标准交付包发布
```

每次灰度必须记录：

- 版本号；
- 灰度客户 / 门店 / 导购范围；
- 变更内容；
- 影响字段；
- 风险等级；
- 回滚方式；
- 负责人；
- 复盘时间。

#### 回滚规则

至少保留三类回滚能力：

1. **配置回滚**：沉默周期、分层规则、话术模板可以退回旧配置；
2. **输出回滚**：新版输出异常时，Agent 可以退回旧版生成逻辑；
3. **动作回滚 / 补救**：批量写回、标签修改、权益发放出错时，有补救方案和审计链路。

## 与 Day72 权限审批审计的衔接

Day72 的核心是“谁能看什么、做什么、审计什么”。Day73 要在这个基础上补一个规则：

```text
任何版本升级，只要影响权限、审批、审计字段，都必须按高风险变更处理。
```

尤其是下面三类升级，不能只让研发改代码：

1. **权限范围扩大**：必须产品、业务、客户负责人确认；
2. **执行动作升级**：必须补审批和回滚；
3. **输出结构变化**：必须通知依赖该输出的 Agent、看板、工作流。

## 今天可落地动作

如果今天继续推进智能导购 / 导购小龙虾，建议补一份《导购沉默会员唤醒 Skill 版本说明 v0.1》：

1. 明确当前版本是 v0.1 / v0.2 / v1.0 中哪一档；
2. 列出当前输入参数、输出字段、权限边界、可执行动作；
3. 标记哪些后续升级属于破坏性变更；
4. 写清灰度范围和回滚方式；
5. 在评审时让产品、研发、测试、业务各确认一次。

管理上只问一句：**这个 Skill 下一次升级时，会不会让已经在跑的客户流程断掉？**

## 管理提醒

1. **不要直接覆盖旧版本。** ToB 客户流程一旦跑起来，稳定性优先于新能力。
2. **不要把字段调整当小事。** Agent、看板、工作流都可能依赖输出字段。
3. **不要让权限升级夹在版本升级里偷偷上线。** 权限扩大必须单独评审。
4. **不要没有回滚就灰度。** 灰度不是试错免责，而是可控验证。
5. **不要只写研发版本号。** 业务版本说明必须让前线、交付、客户成功看得懂。
