## 我今天抓到的核心一句话

**看板发现问题，异常复盘决定能力会不会变强；一次异常必须沉淀为规则、数据、权限或体验的版本升级。**

## 结合 EZR / OpenClaw / 智能导购的理解

导购沉默会员唤醒 Skill 进入 Beta 后，风险不只来自模型输出，也来自 CRM 数据口径、实时判权、活动权益、触达频控和动作回写中的任何断点。

OpenClaw/Agent 可以完成名单筛选、建议生成和流程编排，但不能替代 EZR CRM 的实时数据事实源和权限判断。发生异常时，不能只写“AI 推荐不准”，要定位是：

1. **输入异常**：导购未补充门店、客户关系、当前营销场景等必要上下文；
2. **数据异常**：沉默会员口径、交易/互动数据延迟，或活动适用范围未同步；
3. **逻辑异常**：召回优先级、触达频次和话术规则冲突；
4. **权限异常**：跨门店/跨导购访问，或未获授权就触发批量动作；
5. **体验异常**：建议不能直接执行、解释不清、回写状态不可见。

真正可产品化的能力，要做到：**异常被记录、可定位、能冻结、能回滚、会复测。**

## 今日形成的异常复盘卡（v0.1）

| 字段 | 要求 |
|---|---|
| 异常编号与时间 | 唯一编号、发生时间、Skill/规则版本 |
| 试点范围 | 品牌、门店、导购角色、灰度人群（脱敏） |
| 输入与输出证据 | 参数/上下文摘要、推荐名单或话术关键片段（脱敏） |
| 数据事实 | 数据更新时间、沉默口径版本、权益/商品规则版本 |
| 异常分类 | 输入 / 数据 / 逻辑 / 权限 / 体验，可多选 |
| 影响级别 | P0 越权或误触达；P1 大范围误判；P2 单点可修复问题 |
| 即时处置 | 拦截、人工确认、回滚、冻结扩围、下线 |
| 根因与修复 | 补字段、补规则、补权限、补体验，明确责任人和版本 |
| 复测结论 | 用同类样本复测，确认不复发后才恢复灰度 |

## 冻结与升级规则

- **立即冻结扩围（P0）**：越权访问、批量误触达、活动权益错误承诺、关键动作未回写或不可审计。
- **暂停并修复（P1）**：沉默口径或数据时效失真，导致推荐名单显著错误；连续出现同类话术/优先级误判。
- **纳入版本迭代（P2）**：导购采用率低、输出解释不清、操作路径过长，但未影响客户权益和数据安全。
- **恢复条件**：根因明确、规则或权限已升级、同类样本复测通过、责任人确认，并在看板留下恢复记录。

## 今天要落到项目上的动作

在智能导购 MVP 的本周评审中，把“异常复盘卡 + 冻结规则”作为 Beta 准入项：

- **产品**：定义异常影响等级与导购侧反馈入口，确保无法执行/不采纳都有原因可回收；
- **研发**：补齐调用、实时判权、人工确认、执行、回写和版本号的审计链路；
- **业务/运营**：指定试点门店负责人，每周提交异常复盘结论，并对每项异常给出“恢复/继续冻结”的决策。

首个建议压测场景：**活动权益变化或数据延迟时，Skill 必须停止生成承诺型话术，转为“需人工确认”并记录原因。**

## 风险边界

- 不能把数据、规则和权限问题笼统归因于“模型幻觉”。
- 未接入 CRM 实时判权、人工确认和审计回写前，不能开放批量触达或扩大门店灰度。
- 不把异常数量作为惩罚导购或团队的指标；目标是暴露问题、升级能力。
- P0/P1 复盘不闭环，不进入下一轮扩围决策。

今天是否把“异常发生后的谁来停、谁来改、改完如何复测、何时恢复”明确到智能导购 Beta 的责任人和流程里？首个最可能出现的异常，究竟是数据口径、权益规则、权限判定，还是导购操作路径？
