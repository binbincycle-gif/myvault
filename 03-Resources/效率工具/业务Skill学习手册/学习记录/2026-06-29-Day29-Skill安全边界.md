# 2026-06-29｜Day29 学习记录：Skill 安全边界

## 今日阅读
- 原文：[[Day29-Skill安全边界：权限、审批、回滚与人工确认]]
- 主题：业务 Skill 从“生成建议”走向“调用系统能力”时，必须前置设计权限、审批、回滚与审计。

## 核心结论

业务 Skill 越接近真实经营流程，越不能只写“能做什么”，必须同步写清楚“谁能用、能看什么、能改什么、哪些必须人工确认、出错后如何撤回、过程如何追溯”。

一句话：**没有边界的自动化，不是能力，是风险。**

## 今天最重要的启发

Skill 的安全设计要从“账号权限”升级为“身份 + 场景 + 动作”三层判断：

1. **身份**：总部运营、店长、导购、客服、管理员等角色不同，权限不同。
2. **场景**：只读查询、建议生成、提交审批、执行动作，风险等级不同。
3. **动作**：读数据、改标签、发券、群发、导出、建单等动作要分级治理。

建议把 Skill 动作分成四级：

```text
L0 只读查询：查看数据、读取知识库、生成摘要。
L1 建议生成：生成方案、话术、清单、诊断结论。
L2 半自动执行：生成待执行动作，由人确认后提交。
L3 自动执行：系统直接触发发送、改价、发券、建单、改配置。
```

当前 EZR 业务 Skill 建议优先停在 **L1 / L2**：AI 生成建议和待执行动作，但触达、发券、改标签、导出等关键动作必须人工确认或审批。

## 对 EZR / 智能导购的落地联想

以“导购客户跟进 Skill”为例，边界应这样设计：

| 项目 | 建议边界 |
|---|---|
| 调用角色 | 导购、店长、总部运营，按角色区分视图 |
| 可读数据 | 导购只读本人会员池；店长可看门店汇总；总部看品牌汇总和脱敏明细 |
| 可生成内容 | 重点客户清单、推荐理由、跟进话术、权益建议 |
| 可执行动作 | 初期只生成待执行任务，不自动群发、不自动发券 |
| 人工确认点 | 发送话术、选择触达渠道、是否使用权益 |
| 审批条件 | 批量触达、高面额发券、跨门店客户触达、敏感客诉场景 |
| 回滚方式 | 撤回待发送任务、作废权益、修正标签、记录异常原因 |
| 审计记录 | 调用人、会员范围、数据口径、生成内容、确认人、执行时间、结果回写 |

## 今天可落到的一个动作

把“安全边界表”加入后续所有业务 Skill 评审模板，尤其是这几类高风险场景：

- 导购小龙虾 / 智能导购
- 会员画像与标签建议
- AI 取数 / 数据导出
- 营销活动策略与发券建议
- 客户触达话术生成与群发

评审时固定问 5 个问题：

1. 这个 Skill 读了哪些数据？
2. 这个 Skill 会不会改变业务状态？
3. 哪些动作必须人工确认？
4. 出错以后有没有撤回或修正方式？
5. 执行记录能不能追溯到人、时间、输入、输出和动作？

## 晚上复盘问题

1. 今天是否给至少一个业务 Skill 补了权限、审批、回滚和审计边界？
2. 哪些动作仍然只是靠“提示词约束”，但其实应该交给系统权限和流程控制？
3. 智能导购第一版是否明确了：AI 只生成建议，还是已经允许半自动执行？

## 一句话沉淀

业务 Skill 要商业化，不只是 AI 准不准，而是客户敢不敢让它进入真实系统；权限、审批、回滚、审计，就是 Skill 从“演示能力”走向“可交付产品”的底线。
