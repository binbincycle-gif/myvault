## 今日抓到的核心判断

Day59 解决的是：导购沉默会员唤醒 Skill 如何从 AI 功能包装成客户愿意理解和付费的经营能力。

Day60 要继续补最后一块：**商业化包装讲得清，不代表可以交付；上线前必须确认它能被真实团队长期、稳定、可控地使用。**

> 导购沉默会员唤醒 Skill 不能因为 Demo 能推荐名单、生成话术就上线。真正上线标准是：导购知道什么时候用，Agent 知道怎么调用，店长能看过程，总部能看结果，异常能降级，CRM 能回写，后续能复盘。

如果缺少上线前检查，会出现四类风险：

1. **误调用风险**：Agent 在不合适场景调用，给出不该给的建议。
2. **越权风险**：导购看到非授权会员、权益或门店数据。
3. **动作断点风险**：生成建议后没有触达、确认、回写，变成一次性文本。
4. **交付不可复制风险**：只能靠产品/实施临场解释，换客户就失效。

## 导购沉默会员唤醒 Skill｜上线前检查清单 v0.1

| 项目 | 上线前必须确认 |
|---|---|
| Skill 名称 | 导购沉默会员唤醒 Skill |
| 目标角色 | 导购日常使用；店长看过程；总部运营看策略与效果 |
| 触发场景 | 导购每日进入待跟进客户 / 店长查看沉默会员任务 / 总部发起沉默会员唤醒策略 |
| 必要输入 | 会员归属、最近消费时间、消费金额、互动记录、偏好标签、可用权益、导购/门店权限 |
| 输出结构 | 客户优先级、推荐理由、建议话术、推荐权益、下一步动作、风险提示 |
| 可执行动作 | 查看客户、确认触达、复制/编辑话术、申请权益、记录结果、标记失败原因 |
| 权限边界 | 只能读取当前导购/门店授权会员；跨店/跨导购数据必须按 SaaS 实时判权 |
| 人工确认点 | 发消息、发券、批量触达、承诺权益、变更会员标签必须人工确认或审批 |
| 异常降级 | 数据不足输出“依据不足”；权限不足拒绝；权益冲突提示审批；客户免打扰则拦截触达 |
| 回写机制 | 触达状态、客户响应、成交/复购、未采纳原因、失败原因结构化回写 CRM |
| Owner | 产品 Owner + 业务 Owner + 技术 Owner 三方明确，不允许无主上线 |
| 验收指标 | 导购 3 分钟内完成一次有效跟进；采纳率、触达率、响应率、复购/唤醒率可追踪 |

## 上线前必须补齐的 5 个交付件

```text
1. 调用说明
- 什么场景调用
- 什么场景不调用
- 必要输入字段
- 输出字段解释

2. 业务使用说明
- 导购怎么用
- 店长怎么看
- 总部运营怎么配置/复盘

3. 权限与安全说明
- 数据读取范围
- 动作权限范围
- 人工确认点
- 审计记录位置

4. 异常处理说明
- 数据缺失怎么降级
- 权限不足怎么提示
- 客户免打扰怎么拦截
- 结果异常找谁处理

5. 复盘指标看板
- 采纳率
- 触达率
- 响应率
- 复购/唤醒率
- 未采纳/失败原因分布
```

## 管理提醒

1. **不要把 Demo 当交付。** Demo 证明能跑，交付证明能被真实团队长期使用。
2. **第一批 Skill 要少而硬。** 与其上线一堆半成品，不如先把导购沉默会员唤醒打成一个完整样板。
3. **上线标准要从功能转成契约。** 触发、输入、输出、执行、运维五个契约缺一不可。
4. **权限、审计、回写要前置。** 这三个不补，后面客户越多风险越大。
5. **交付包决定复制速度。** 使用说明、异常说明、看板指标、Owner 机制，是从一个客户复制到多个客户的基础。

## 晚上复盘问题

1. 今天这个 Skill 是“Demo 能跑”，还是“真实业务能交付”？
2. 导购、店长、总部运营三类角色的使用方式是否讲清楚？
3. Agent 什么时候应该调用，什么时候应该拒绝调用？
4. 权限、人工确认、异常降级、结果回写是否形成闭环？
5. 如果明天换一个客户试点，是否可以不用产品经理临场解释也能跑起来？
