# 2026-09-08 Day38｜业务Skill安全边界与结果沉淀联动

## 今日阅读

阅读《业务Skill学习手册》Day29《Skill安全边界：权限、审批、回滚与人工确认》，并联动复习 Day28《Skill记忆与沉淀：让执行结果反哺能力》、昨日 Day31《Skill上线前可交付检查》。

## 我今天抓到的核心一句话

业务 Skill 不能只追求“能执行”，还必须做到：**在安全边界内执行，把责任和证据记录下来，再把经过确认的结果沉淀成可复用能力。**

## 结合 EZR / OpenClaw / 智能导购的理解

当前导购沉默会员唤醒 Skill，不能只输出会员名单和话术。真正的最小闭环应该是：

1. Agent 识别会员机会；
2. 按导购身份和会员范围做权限校验；
3. 生成推荐动作和话术；
4. 导购人工确认；
5. 触达客户或创建跟进任务；
6. 将采纳、触达、回复、到店、成交和异常原因回写 CRM；
7. 仅将经过确认的脱敏经验沉淀到项目知识或组织知识。

## 今日重点判断

### 1. 权限必须从“能不能用”升级到“能执行什么动作”

同一个 Skill，导购、店长、总部运营的权限不能相同。需要同时判断：

- 调用者身份；
- 可查看的数据范围；
- 当前业务场景；
- 准备执行的动作；
- 动作风险等级。

### 2. 人工确认必须产品化

“需要人工确认”不能只写在说明文档里，必须在流程中有明确的确认节点、责任人和审计记录。优先走 L1 建议生成 → L2 人工确认后执行，不急着开放 L3 自动执行。

### 3. 结果沉淀必须经过可信度分层

- 运行日志：保存调用过程、错误、权限判断和原始结果；
- 项目记忆：保存已确认的客户和门店经验；
- 组织知识：只沉淀经过人工确认、可跨项目复用的口径、模板和风险规则。

会员明细、未经确认的模型推测和错误建议，不应直接进入长期知识库。

## 今天形成的可执行检查表

| 环节 | 检查问题 |
|---|---|
| 调用身份 | 谁调用，代表谁工作？ |
| 数据边界 | 能读哪些会员数据？ |
| 动作等级 | 是查询、建议、半自动还是自动执行？ |
| 人工确认 | 哪些动作必须由谁确认？ |
| 执行审计 | 能否追溯输入、输出、确认人和执行时间？ |
| CRM回写 | 是否记录采纳、触达、回复、到店、成交？ |
| 知识沉淀 | 哪些结果可进入项目知识或组织知识？ |
| 纠偏回滚 | 错误建议和错误沉淀如何修正？ |

## 对当前项目的下一步

1. 将“权限校验 → 人工确认 → 触达 → CRM回写”补进智能导购 MVP 流程图。
2. 给导购沉默会员唤醒 Skill 增加结果回写字段和异常原因字段。
3. 在 Skill 上线前检查清单中增加“安全与沉淀联动”一项，禁止只验输出、不验责任链。

## 问题与反思

1. 当前智能导购 MVP 是否已经明确导购、店长、总部运营三类角色的动作边界？
2. 哪些回写字段必须进入 CRM，哪些内容只能留在运行日志？
3. 如果一次建议造成客诉或越权，是否可以完整追溯并快速回滚？
4. 是否应该先选 3 个真实会员样例，跑通 L1→L2→结果回写，而不是继续扩展功能范围？
