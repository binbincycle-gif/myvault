# Day19｜Skill灰度发布：先小范围验证再规模化推广

## 今日主题

Day18 讲的是异常复盘：Skill 出问题后，如何定位、修正和防复发。

Day19 进一步解决一个更现实的问题：**一个业务 Skill 写出来后，不能直接全员开放，而要先灰度发布。**

> Skill 灰度发布的核心，不是“慢一点上线”，而是用小范围真实场景验证价值、边界和风险，再决定是否扩大使用。

业务 Skill 和普通文档不同，一旦被大量员工使用，就会影响判断、流程、客户沟通甚至经营动作。如果没有灰度机制，最容易出现三类问题：

1. Skill 看起来好用，但真实业务输入一复杂就不稳定。
2. 少数试用反馈很好，但换团队、换客户后效果下降。
3. 没有权限、审计、回滚方案，出了问题只能临时解释。

所以今天要学的是：如何把 Skill 发布从“写完就用”，升级为“试点验证 → 受控扩大 → 稳定运营”。

---

## 技术原理（技术视角）

### 1. 灰度发布要控制 4 个变量

| 变量 | 控制方式 | 目的 |
|---|---|---|
| 使用人群 | 先给少数角色 / 团队 / 项目使用 | 避免问题快速扩散 |
| 使用场景 | 只开放指定业务动作 | 防止被用到设计外场景 |
| 数据范围 | 限制品牌、门店、客户、时间范围 | 降低越权和口径风险 |
| 能力权限 | 先建议、后执行；先人工确认、后自动动作 | 控制生产风险 |

灰度不是简单地“只给几个人用”，而是要同时控制人、场景、数据和动作权限。

### 2. 灰度阶段要定义通过标准

一个 Skill 是否能扩大使用，不能只看“大家觉得不错”，至少要看 5 类信号：

| 指标 | 判断问题 |
|---|---|
| 使用率 | 目标用户是否真的愿意用？ |
| 成功率 | 是否稳定完成预期任务？ |
| 修正率 | 输出被人工修改的比例高不高？ |
| 异常率 | 是否出现口径、权限、事实或体验问题？ |
| 业务影响 | 是否真的节省时间、提升质量或推动转化？ |

没有通过标准的灰度，本质上只是“内测聊天”。

### 3. 灰度必须有回滚机制

Skill 灰度至少要准备三种回滚：

```text
停用：出现高风险异常，立即关闭入口
降级：从自动执行降为只生成建议
回退：切回上一个稳定版本 / 模板
```

越接近客户、交易、权益、数据权限的 Skill，越不能没有回滚预案。

## 业务翻译（业务视角）

业务上可以这样理解：

> Skill 灰度发布，就是先用一个小战场验证这项 AI 能力是否真的能打，再决定是否扩军。

过去上线一个 SaaS 功能，用户可以不用、少用、慢慢学。但 Skill 不一样，它可能直接给建议、生成结论、辅助沟通，甚至参与流程编排。它一旦错，影响的不只是体验，还有业务判断。

所以管理者要盯住三句话：

1. 先验证一个清晰场景，不要一上来全员开放。
2. 先让 Skill 给建议，不要一上来自动执行。
3. 先看真实数据反馈，不要只听试用感受。

## 典型场景（EZR 业务版）

### 场景 1：智能导购推荐 Skill 灰度

**灰度对象**：先选 1-2 个品牌、少数门店、表现稳定的导购。

**灰度范围**：只做“今日优先跟进会员 + 推荐理由 + 建议话术”，不直接自动发消息。

**通过标准**：
- 导购使用率达到预设目标。
- 推荐名单被导购认可，而不是大量跳过。
- 触达后能回写跟进结果。
- 没有明显权益误导、客户标签误判或越权查看问题。

**扩大条件**：
当“推荐 → 触达 → 反馈 → 复盘”跑通后，再扩到更多门店或品牌。

### 场景 2：经营诊断 Skill 灰度

**灰度对象**：先给运营负责人 / 客户成功负责人使用，不直接开放给所有门店。

**灰度范围**：只输出诊断建议和数据依据，不自动下发经营动作。

**必须控制**：
- 指标口径版本。
- 数据更新时间。
- 置信度和缺失数据提示。
- 人工确认入口。

**回滚条件**：
如果连续出现数据口径被质疑，先降级为“数据摘要 Skill”，暂停给经营建议。

### 场景 3：AI Coding 测试用例 Skill 灰度

**灰度对象**：先选一个真实迭代或一个固定研发小组。

**灰度范围**：只生成测试用例草稿，由测试负责人确认后使用。

**通过标准**：
- 是否覆盖 P0 主链路。
- 是否减少测试准备时间。
- 是否能识别权限、数据、异常链路。
- 是否被团队沉淀成可复用模板。

**扩大条件**：
稳定跑过 2-3 个迭代后，再进入更多项目。

## 图示

```text
Skill 灰度发布流程

候选 Skill
  ↓
定义灰度场景：谁用 / 用在哪 / 用什么数据 / 能做到哪一步
  ↓
小范围试点：建议优先，人工确认
  ↓
观察指标：使用率 / 成功率 / 修正率 / 异常率 / 业务影响
  ↓
评审决策：扩大 / 降级 / 回滚 / 停用
  ↓
进入运营：看板监控 + 异常复盘 + 版本迭代
```

## 管理者关注点（成本 / 效率 / 风险）

### 1. 成本

灰度能避免一个不成熟 Skill 大范围铺开后，产生大量解释、修正和信任修复成本。

### 2. 效率

好的灰度不是拖慢上线，而是用最小范围快速验证“值不值得扩大”。

### 3. 风险

越靠近客户、交易、权益、经营建议和数据权限的 Skill，越必须先灰度。没有灰度，就不要直接规模化。

## 本日自检

1. 当前最想推广的业务 Skill，是否已经定义灰度人群和灰度场景？
2. 这个 Skill 现在是“给建议”，还是已经涉及“自动执行”？
3. 是否有明确扩大标准：使用率、成功率、异常率、业务影响？
4. 如果今天出问题，能不能立即停用、降级或回退到稳定版本？

---

## 一句话总结

Skill 发布不能靠感觉铺开；先灰度验证价值和边界，再规模化，才是组织级 AI 能力的正确打法。
