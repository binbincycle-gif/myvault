# Day 11｜幂等、超时与重试策略

## 今日主题

今天学习 OpenClaw 自动化任务里最容易被低估的三件事：**幂等、超时、重试**。

它们不是“工程师才关心的细节”，而是决定一个 Agent 能不能进入真实工作流的可靠性底座。一个能演示的自动化，只要成功一次就够；一个能长期运行的自动化，必须能面对网络抖动、页面卡顿、外部接口失败、重复触发、人工误点等不稳定情况，并且不会把小问题放大成业务事故。

学习目标很简单：理解为什么 Agent 任务不能只写“成功路径”，而要提前设计“重复执行怎么办、等多久算失败、失败后要不要再试”。

## 技术原理（技术视角）

### 1. 幂等：重复执行，结果仍然一致

**幂等（Idempotency）**指的是：同一个操作执行一次和执行多次，最终结果保持一致。

在 OpenClaw 场景中，幂等主要用来解决“任务被重复触发”的问题。例如：

- 用户重复点了一次按钮；
- cron 任务因为网络异常被重新调度；
- Agent 执行到一半超时，下一轮重新开始；
- 外部消息平台重复推送同一条事件。

如果没有幂等保护，重复执行可能带来：重复发消息、重复创建记录、重复扣库存、重复提交表单、重复写入知识库等问题。

一个简单的判断方法：

| 操作类型 | 是否天然幂等 | 说明 |
|---|---:|---|
| 查询状态 | 是 | 查一次和查十次，结果通常一致 |
| 设置状态为“已完成” | 通常是 | 多次设置仍然是已完成 |
| 新增一条记录 | 否 | 多执行一次就多一条 |
| 发送一封通知 | 否 | 多执行一次就多打一扰 |
| 数字加 1 | 否 | 每执行一次结果都会变化 |

设计幂等时，关键是找到一个稳定的**幂等键**。常见组合包括：

- `任务类型 + 日期`：例如每日学习手册生成任务；
- `消息平台事件 ID`：例如同一条外部消息只处理一次；
- `业务对象 ID + 动作`：例如某个文档只归档一次；
- `文件路径 + 内容哈希`：例如同一份内容不重复写入。

可以把幂等理解为：任务执行前先问一句——**“这件事我是不是已经做过了？”**

### 2. 超时：不要让一个慢环节拖死整条链路

超时（Timeout）解决的是“等多久”的问题。

Agent 经常会调用外部工具：浏览器、Shell、Web 请求、文件系统、消息平台、子 Agent。任何一个环节都有可能卡住。如果没有超时机制，一个任务可能长时间占用会话、队列或资源，让后续任务全部排队。

OpenClaw 的 Agent Loop 文档里提到，单次运行会经历输入接收、上下文组装、模型推理、工具调用、结果持久化等阶段；其中工具调用尤其容易遇到外部不稳定。超时就是给每个阶段设置“最大等待边界”。

实战上常见三层超时：

1. **单次工具超时**：一次浏览器点击、一次接口请求、一次 shell 命令最多等多久；
2. **单个步骤超时**：一个业务步骤，例如“打开页面并提取数据”最多等多久；
3. **整轮任务超时**：整个 Agent run 最多运行多久，避免无限挂起。

超时不是越长越安全。超时过长会拖慢系统，超时过短会误杀正常任务。更合理的做法是：按任务价值和外部依赖稳定性设定等待边界。

### 3. 重试：只重试值得重试的失败

重试（Retry）解决的是“失败后怎么办”的问题。

不是所有失败都应该重试。重试只适合临时性故障，例如：

- 网络瞬断；
- 远端服务 5xx；
- 浏览器页面短暂未加载完成；
- 文件锁暂时占用；
- 消息平台限流后给出 Retry-After。

不适合重试的失败包括：

- 参数错误；
- 权限不足；
- 登录失效；
- 文件路径不存在且无法推断；
- 用户输入本身不完整。

重试策略通常包括三个参数：

| 参数 | 作用 | 推荐理解 |
|---|---|---|
| 最大次数 | 防止无限重试 | 通常 2-3 次足够 |
| 间隔策略 | 避免连续冲击 | 指数退避优于固定间隔 |
| 抖动 jitter | 防止同时重试 | 多任务并发时尤其重要 |

最常见的稳健模式是：**指数退避 + 抖动 + 有限次数**。

也就是说，第一次失败后等 1 秒，第二次等 2 秒，第三次等 4 秒，并加一点随机偏移，避免大量任务在同一时间重新打到外部系统。

### 4. 三者的组合关系

幂等、超时、重试不能分开看：

- 没有超时，任务会卡死；
- 没有重试，临时失败会直接变成业务失败；
- 没有幂等，重试可能制造重复副作用。

可靠任务的基本执行顺序应该是：

1. 接收任务；
2. 生成或读取幂等键；
3. 检查是否已经执行过；
4. 设置超时边界；
5. 执行核心动作；
6. 失败时判断是否可重试；
7. 成功后记录执行结果；
8. 不可恢复时明确返回失败原因。

### 5. 常见误区

- **误区一：重试次数越多越可靠。** 事实是，过度重试会放大故障，尤其是外部系统已经过载时。
- **误区二：只要加了重试，就不用幂等。** 正好相反，凡是有写入、发送、提交动作，先想幂等，再谈重试。
- **误区三：超时设置越长越稳。** 超时过长会占用队列和资源，影响后续任务。
- **误区四：所有异常都可以自动恢复。** 权限、登录、参数、业务规则错误，应快速失败并给人可理解的提示。

## 业务翻译（业务视角）

从业务视角看，幂等、超时、重试回答的是三个管理问题：

- **幂等：重复做，会不会出事故？**
- **超时：等太久，会不会影响整体效率？**
- **重试：失败一次，是不是还有自动恢复机会？**

这套机制让 Agent 从“能跑”变成“敢用”。

如果一个自动化只在理想条件下成功，它适合演示；如果它能识别失败、控制重试、避免重复副作用，它才适合进入日常流程。

对业务的价值主要有四类：

1. **提效**：临时失败自动恢复，减少人工盯任务；
2. **提质**：避免重复写入、重复发送、重复提交；
3. **提速**：慢任务快速失败，不拖住整条队列；
4. **可控**：失败原因可追踪，知道是网络、权限、输入还是外部依赖问题。

一句业务语言就是：**让 Agent 做事时有刹车、有边界、有复盘线索。**

## 典型场景（个人版）

### 场景一：每日学习手册生成

每天只应该生成一篇学习资料。如果 cron 重复触发，不能重复覆盖多篇，也不能跳过顺序。

可用设计：

- 幂等键：`OpenClaw学习手册 + Day编号`；
- 执行前检查：目标 Day 文档是否已完整；
- 写入策略：只更新下一篇未完善文档；
- 失败处理：如果资料不足或路径不存在，明确标记阻塞，不生成半成品。

### 场景二：消息通知

Agent 生成结果后，要通知用户。如果发送接口超时，系统不知道消息到底发没发成功，这时直接重试可能造成重复通知。

可用设计：

- 幂等键：`通知类型 + 日期 + 目标会话`；
- 发送前记录待发送状态；
- 发送成功后记录消息 ID；
- 如果超时，先查询或检查记录，再决定是否重试。

### 场景三：浏览器自动化

浏览器任务经常遇到页面加载慢、按钮暂时不可点、登录态失效等情况。

可用设计：

- 对“页面加载慢”可短暂重试；
- 对“按钮找不到”先重新 snapshot，再尝试一次；
- 对“登录失效”不要盲目重试，应提示需要人工登录；
- 对“提交表单”必须设计幂等，避免重复提交。

### 场景四：写入知识库

写入 Obsidian 文档时，最怕同一段内容重复追加，或中途失败留下半截文件。

可用设计：

- 幂等键：文件路径 + 标题 + 日期；
- 写入前检查目标段落是否存在；
- 尽量一次性完整写入；
- 大改动前保留可回滚版本或使用 Git 状态检查。

## 管理者关注点（成本/效率/风险）

| 维度 | 管理者要问的问题 | 建议口径 |
|---|---|---|
| 成本 | 重试会不会增加调用成本？ | 设置最大次数，记录重试率，避免无限恢复 |
| 效率 | 失败后是自动恢复还是人工介入？ | 临时故障自动重试，权限/参数问题快速反馈 |
| 风险 | 重复执行会不会产生业务副作用？ | 涉及写入、发送、提交、扣减的动作必须先做幂等 |
| 体验 | 用户看到的是错误码还是可理解提示？ | 输出“失败原因 + 是否已重试 + 下一步动作” |
| 治理 | 怎么知道系统正在不稳定？ | 观察超时率、重试率、最终失败率和重复拦截次数 |

管理上不要只看“成功率”，还要看“靠重试救回来的比例”。如果一个任务成功率高但重试率持续升高，说明底层依赖已经在变脆，需要提前治理。

## 本日自检

1. 我能否区分“可以重试的临时故障”和“不该重试的业务错误”？
2. 我能否为一个写入类任务设计出清晰的幂等键？
3. 我能否说清楚超时过长和超时过短分别会带来什么问题？
4. 如果一个任务失败，我是否能输出“是否重试过、重试几次、最后卡在哪里”？

## 一句话总结

**幂等保证重复执行不出事，超时保证任务不会一直卡住，重试保证临时失败有恢复机会；三者合在一起，才是 Agent 进入真实业务流程的可靠性底座。**
