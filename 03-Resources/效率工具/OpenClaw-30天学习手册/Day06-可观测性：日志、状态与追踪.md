# Day 06｜可观测性：日志、状态与追踪

## 今日主题

今天这篇讲 OpenClaw 从“能执行”走向“可运营”的关键能力：**可观测性**。

很多人第一次使用 Agent 系统时，最关注的是它能不能理解指令、能不能调用工具、能不能把结果交付出来。但只要开始把 Agent 放进真实工作流，就会遇到另一个更重要的问题：

> 当任务没完成、结果变慢、工具报错、成本升高、用户追问时，我们能不能快速知道到底发生了什么？

可观测性就是为了解决这个问题。它不是单纯的“日志系统”，也不是给技术同学看的调试面板，而是一套让 AI 执行过程被看见、被解释、被复盘、被管理的基础设施。

在 OpenClaw 的语境里，可观测性通常围绕三层展开：

- **日志（Logs）**：记录发生过什么。
- **状态（State）**：说明现在进行到哪一步。
- **追踪（Trace）**：串起一次任务从入口到结果的完整链路。

这三层组合起来，才能把 Agent 从“黑盒助手”升级为“可治理的执行系统”。

## 技术原理（技术视角）

### 1. 为什么 Agent 系统更需要可观测性

传统软件的可观测性主要关注服务是否稳定，例如接口是否 500、数据库是否超时、CPU/内存是否异常。Agent 系统当然也需要这些，但还远远不够。

因为 Agent 的执行过程有几个典型特点：

- **链路更长**：一次用户请求可能经过消息接入、上下文组装、模型推理、工具调用、文件读写、浏览器操作、消息发送等多个环节。
- **结果更不确定**：模型可能没有报错，但回答偏题、遗漏关键条件，或者生成了“看起来合理但不可用”的内容。
- **外部依赖更多**：网页、文件、Shell、API、消息渠道、权限策略都可能成为失败点。
- **异步任务更多**：长任务、子代理、后台进程、定时任务不一定在同一个同步请求内完成。
- **成本需要管理**：模型调用、工具调用、重试、长上下文都会带来成本，不能只看是否成功。

所以，Agent 的可观测性不仅要回答“系统有没有挂”，还要回答：

1. 这次任务有没有被正确触发？
2. 模型做了什么判断？
3. 调用了哪些工具？参数是否合理？
4. 哪一步失败或变慢？
5. 是否发生重试、超时、人工接管？
6. 最终结果是否真正交付给用户？
7. 这类任务长期看是否稳定、划算、可扩展？

如果没有这些信息，Agent 自动化就只能停留在“演示效果不错”，很难进入持续运营。

### 2. 日志层：回答“发生了什么”

日志是最基础的事实记录。OpenClaw 任务执行过程中，凡是关键节点，都应该留下可检索、可关联、可脱敏的记录。

一条有价值的日志，不只是“报错了”，而应尽量包含：

- **触发来源**：用户消息、cron、webhook、CLI、浏览器任务、子代理任务等。
- **时间信息**：开始时间、结束时间、耗时。
- **身份标识**：sessionId、runId、taskId、traceId 等用于串联链路的标识。
- **动作摘要**：模型调用、工具调用、参数摘要、返回摘要。
- **结果状态**：成功、失败、取消、超时、等待审批、被人工中断。
- **错误信息**：错误类型、错误阶段、可读描述、是否可重试。
- **成本信息**：token、工具耗时、重试次数、外部 API 调用次数等。

日志层的重点不是“什么都记”，而是**关键节点不能断**。

#### 常见误区

- 只在报错时打日志，成功链路没有记录，导致无法对比正常与异常。
- 工具调用很多，但没有统一 ID，排障时无法知道它们属于哪一次任务。
- 日志只记录技术错误，不记录业务结果，例如“消息发送成功”但不知道日报内容是否生成完整。
- 原样记录用户输入、凭证、cookie、内部地址，造成隐私与安全风险。

比较好的做法是：日志记录“足够定位问题的信息”，但敏感内容只保留摘要或脱敏版本。

### 3. 状态层：回答“现在做到哪了”

日志偏历史，状态偏当前。状态层让我们知道任务此刻处于什么阶段。

在 OpenClaw 这类系统里，可以把状态分成三类：

#### Session State：会话状态

Session 是 OpenClaw 维持上下文连续性的基础。它告诉系统：

- 当前对话属于哪个会话；
- 历史消息和上下文是否还可用；
- 本次运行是否应该复用之前的上下文；
- direct chat、group chat、cron job 等不同入口是否隔离。

对排障来说，session 是非常重要的入口。很多问题不是模型“突然变笨”，而是上下文没带上、会话隔离不对、历史消息被压缩或重置。

#### Task State：任务状态

任务状态描述一项工作此刻的执行阶段，例如：

- queued：排队中；
- running：执行中；
- waiting：等待输入、审批或外部依赖；
- retrying：重试中；
- completed：已完成；
- failed：失败；
- cancelled：取消；
- timeout：超时。

状态层的管理价值很强。比如你看到“失败”不够，还要知道是等待审批超时、浏览器元素找不到、模型调用失败，还是消息渠道发送失败。

#### Agent / Tool State：执行状态

Agent 运行时还会涉及工具和执行器状态，例如：

- browser 是否已启动、页面是否加载完成；
- shell 命令是否还在后台运行；
- 子代理是否已完成或需要 steer；
- 文件读写是否成功；
- 外部 API 是否限流；
- 消息工具是否真的发出。

这类状态决定了自动化是否可靠，也决定了人工介入时能不能接得住。

### 4. 追踪层：回答“卡在哪一跳”

当一次任务跨越多个组件，仅靠日志会变得碎片化。追踪层负责把这些碎片串起来。

可以用两个概念理解：

- **Trace**：一次任务的完整链路，从触发到完成。
- **Span**：链路中的一个步骤，例如一次模型调用、一次工具调用、一次浏览器点击、一次文件写入。

例如，一个“生成学习文档并通知用户”的任务，Trace 可能包含：

1. cron 触发；
2. 读取学习手册目录；
3. 判断下一篇未完善 Day 文档；
4. 读取官方文档镜像；
5. 生成正文；
6. 生成 SVG 图示；
7. 写入 Obsidian 知识库；
8. 校验文件结构；
9. 通知主会话用户。

每一步都是一个 Span。追踪层让你看到：

- 哪一步最耗时；
- 哪一步失败率最高；
- 哪些步骤发生了重试；
- 异步任务和子任务是否接上了主链路；
- 最终失败到底是模型、工具、权限、网络还是外部服务导致。

这就是 Trace 的价值：它把“任务没跑完”拆成“第几步、什么原因、影响多大、下一步谁处理”。

### 5. 生命周期事件：让过程可被订阅

OpenClaw 的 Agent Loop 会把一次运行拆成生命周期与流式事件。可以简单理解为：

- **start**：任务开始；
- **assistant stream**：模型输出内容；
- **tool stream**：工具开始、执行、返回；
- **end**：任务完成；
- **error**：任务异常结束。

这些事件让系统不必等最终结果才知道任务是否正常。长任务执行时，用户界面、日志系统、通知系统都可以基于事件更新状态。

这对管理长任务尤其重要。例如浏览器自动化、批量处理、报告生成、子代理协作，都可能持续较长时间。如果没有生命周期事件，用户只能看到“还没回复”，无法判断是正在执行、卡住了，还是已经失败。

### 6. 指标层：从单次排障走向持续运营

日志、状态、追踪解决的是单次任务可见；指标解决的是长期运营可见。

适合 Agent 系统的指标包括：

- **任务成功率**：完成数 / 总任务数。
- **P50 / P95 耗时**：看常态速度和尾部延迟。
- **重试率**：识别流程脆弱点或外部依赖波动。
- **人工介入率**：衡量自动化成熟度。
- **审批等待率**：判断安全策略是否过重或流程是否需要优化。
- **单位任务成本**：模型 token、工具耗时、外部 API 调用综合成本。
- **高风险失败占比**：失败是否影响用户交付、数据安全或外部动作。
- **重复失败 TopN**：优先修复高频高影响问题。

这些指标把 Agent 从“单点工具”变成“可经营对象”。管理者不需要看每一行日志，但需要看到稳定性、成本、效率和风险趋势。

### 7. 设计注意事项

#### 统一标识要早设计

如果一开始没有 sessionId、runId、traceId 这类统一标识，后面再补可观测性会很痛苦。因为日志、工具、子任务、消息渠道各记各的，很难串起来。

#### 脱敏要和日志一起设计

Agent 可能接触文件、消息、网页、内部系统、个人信息。日志系统必须默认考虑脱敏：

- 不记录明文密钥；
- 不完整保存 cookie / token；
- 对手机号、邮箱、身份证号等敏感字段做遮罩；
- 对长 prompt 保存摘要而不是全文；
- 根据权限控制日志可见范围。

#### 不要只记录技术指标

CPU、内存、报错数有价值，但不足以管理 Agent。更关键的是业务视角：任务有没有交付、交付是否及时、失败是否影响用户、人工补位成本是多少。

#### 让告警可行动

“任务失败了”是弱告警；“日报生成任务在消息发送环节失败，已重试 2 次仍失败，建议检查消息渠道权限”才是可行动告警。

可观测性最终不是为了堆图表，而是为了减少定位成本和决策成本。

## 业务翻译（业务视角）

### 这项能力解决什么问题

可观测性解决的是 AI 自动化进入真实业务后的信任问题。

业务负责人真正关心的不是“有没有日志”，而是：

- 我交给 Agent 的任务，到底有没有做？
- 没做成时，系统能不能说明原因？
- 失败会不会悄悄发生，等客户或老板发现才暴露？
- 成本是不是越来越高，但价值没有同步增长？
- 哪些任务适合继续自动化，哪些任务必须保留人工审核？

可观测性把这些问题从“靠人感觉”变成“看事实数据”。

### 为什么业务能理解并愿意使用

可以把 Agent 可观测性类比成三种业务系统能力：

- **物流轨迹**：不只知道包裹最后有没有到，还知道每一站到哪了。
- **工单状态**：不只知道问题有没有解决，还知道当前责任人和处理阶段。
- **经营看板**：不只看单笔订单，还看整体成功率、时效、成本和异常趋势。

Agent 也是一种“数字员工”或“自动化执行单元”。既然人做事需要过程管理，Agent 做事也需要过程管理。

### 提效 / 提质 / 提速 / 可控价值

- **提效**：排障从“翻聊天记录、问人、猜原因”变成按 trace 查链路。
- **提质**：持续发现高频失败模式，反向优化 prompt、工具、流程和审批规则。
- **提速**：任务异常能更早发现，减少排队、卡死、重复等待。
- **可控**：关键操作有留痕，方便审计、复盘、成本核算和风险说明。

业务上可以把它理解为：OpenClaw 不只是“能帮我做事”，还要“做事过程可检查、结果可解释、异常可兜底”。

## 典型场景（个人版）

### 场景 1：每日学习资料没有生成

假设你设置了每天 9 点自动生成 OpenClaw 学习手册。某天没有收到通知。

没有可观测性时，只能从头猜：是不是 cron 没跑？是不是文件路径错了？是不是模型生成失败？是不是通知没发出去？

有可观测性时，可以按链路定位：

1. cron 是否触发；
2. 是否识别到下一篇 Day 文档；
3. 是否读取到本地官方文档镜像；
4. Markdown 是否写入成功；
5. SVG 是否生成成功；
6. 校验是否通过；
7. 主会话通知是否发送成功。

这样问题会从“整个任务没了”缩小到“第 6 步图示文件写入失败”或“第 7 步通知渠道不可用”。

### 场景 2：Browser 自动化偶发超时

网页自动化任务常见问题是：有时成功，有时超时。

如果只有最终失败日志，很难判断原因。追踪可以帮助拆解：

- 页面打开耗时是否变长；
- 元素定位是否失败；
- 点击后是否出现弹窗；
- 登录态是否失效；
- 是否因为等待策略不合理导致超时；
- 是否同一站点的 P95 耗时持续上升。

这时的优化动作也更明确：可能是增加稳定选择器、优化等待条件、拆分页面步骤、加登录态检查，而不是盲目重跑。

### 场景 3：管理者评估某个 Agent 是否值得投入

如果一个 Agent 每周帮忙处理大量资料整理任务，管理者会关心它到底值不值。

可观测性可以提供一组事实：

- 本周任务量多少；
- 成功率多少；
- 平均耗时多少；
- 人工介入多少次；
- 高风险失败多少次；
- 单任务成本是否下降；
- 失败 Top3 原因是什么。

这比“大家感觉挺好用”更能支撑资源决策。Agent 项目要从试点走向规模化，必须能用数据证明价值。

### 场景 4：审批流卡住但没人知道

有些工具调用需要人工审批，例如执行命令、发送外部消息、写入敏感位置。审批设计是安全需要，但如果状态不可见，就会变成效率黑洞。

状态层应该能告诉用户：

- 当前任务正在等待审批；
- 等待的是哪个动作；
- 等待多久了；
- 超时后会取消、重试还是降级；
- 是否需要提醒责任人。

这能避免“安全做了，但体验坏了”。好的可观测性应该让安全策略变得透明，而不是让任务莫名卡住。

## 管理者关注点（成本/效率/风险）

### 成本

可观测性会带来额外成本：日志存储、指标计算、看板维护、告警配置、数据脱敏都需要投入。

但这笔成本要和“没有可观测性”的成本比较：

- 问题定位耗时；
- 核心人员被反复打断；
- 失败任务没人发现；
- 重复重试造成模型成本浪费；
- 无法解释 AI 项目价值；
- 风险事件没有留痕。

管理上更合理的判断不是“监控要不要做”，而是“做到什么粒度最划算”。早期可以先做最小闭环：任务量、成功率、失败原因、耗时、人工介入率。等任务规模上来，再扩展 SLA、成本、风险分级和告警策略。

### 效率

没有可观测性时，排障依赖少数熟悉系统的人。每次问题都要重新翻记录、问上下文、复现流程。

有可观测性后，排障可以标准化：

1. 先看任务是否触发；
2. 再看状态卡在哪；
3. 再看 trace 中的失败 span；
4. 最后看日志摘要和错误类型；
5. 根据错误类型选择重试、修复、降级或人工接管。

这会显著降低沟通成本，也让更多人能参与维护 Agent 流程。

### 风险

可观测性的风险主要有两类。

第一类是“没有看见”的风险：任务失败但没人知道，自动化结果错误但继续流转，外部消息没有送达但系统以为完成。

第二类是“看得太多”的风险：日志里保存了不该保存的敏感信息，或者太多人能看到完整上下文。

所以，管理者要同时关注两件事：

- 关键链路必须可见；
- 敏感内容必须最小化记录、分级授权、可审计访问。

### 组织落地建议

如果要把 OpenClaw 引入团队协作，可以从一个简单口径开始：

- 每个 Agent 任务至少有开始、结束、失败原因和耗时；
- 每个可复用 Skill 至少记录成功率、平均耗时、失败 Top3；
- 涉及外部发送、文件写入、命令执行的任务必须有审计记录；
- 每周看一次异常趋势，而不是只在事故后才看日志。

这套口径不复杂，但能把“AI 工具试用”推进到“AI 执行体系运营”。

## 一句话总结

**可观测性不是为了“监控好看”，而是让 Agent 的每一次执行都能被定位、被解释、被优化、被管理。**
