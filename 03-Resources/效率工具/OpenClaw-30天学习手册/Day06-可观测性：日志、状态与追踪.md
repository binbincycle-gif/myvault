# Day 06｜可观测性：日志、状态与追踪

## 今日主题

今天这篇不讲“怎么让 Agent 更聪明”，而讲一个更容易被忽略、但决定你能不能把 Agent 真正跑进业务里的问题：**当任务出错、变慢、结果异常时，你有没有办法在 5 分钟内知道发生了什么，并知道下一步该谁处理**。

OpenClaw 的可观测性，本质上是在补齐 AI 系统的“驾驶舱”。没有它，AI 自动化只是看上去在跑；有了它，系统才真正进入可管理、可优化、可审计的阶段。

## 技术原理（技术视角）

### 1. 为什么 AI 系统的可观测性比传统应用更重要

传统 Web 系统的失败，通常是接口报错、服务挂掉、数据库超时；而 AI 系统的失败更复杂：

- 模型回答看似成功，但内容偏题或不完整
- 工具执行成功，但参数传错，结果不可用
- 多步骤工作流在中间一跳失败，表面上只看到“任务没完成”
- 任务并没有报错，只是异常变慢，吞吐量下降

所以，可观测性不能只盯“服务是不是活着”，还要盯：

- **任务是否按预期推进**
- **每一步调用发生了什么**
- **失败是模型问题、工具问题还是外部依赖问题**
- **成本、时延、成功率是否还在可接受范围**

### 2. OpenClaw 可观测性的三个核心层次

#### 日志层：回答“发生了什么”
日志是最底层的事实记录。一个完整任务通常要记录：

- 发起时间、发起来源
- 所属 session / task / trace 标识
- 模型调用、工具调用、参数摘要、返回结果摘要
- 耗时、重试次数、错误信息
- 最终状态：成功、失败、取消、超时

日志的价值不是“多”，而是“关键节点足够完整”。

常见误区：
- 只记录报错，不记录关键决策点
- 原样写入全部输入，导致日志里出现敏感信息
- 工具调用很多，但没有统一 ID，导致无法串链路

#### 状态层：回答“现在做到哪了”
状态不是历史，而是当前快照。它更关注任务此刻所处位置。

可拆成三类：

- **Session State**：会话上下文是否还在，消息链是否正常
- **Task State**：任务当前是排队中、执行中、重试中、已失败还是已完成
- **Agent State**：Agent 是否在线、健康、是否卡死、是否有资源压力

如果说日志适合复盘，状态更适合实时运营。

#### 追踪层：回答“卡在哪一跳”
当一个请求会跨越模型、工具、子任务、外部服务时，只看单点日志就不够了，需要一条完整调用链。

追踪里最关键的两个概念：

- **Trace**：一次任务的全链路
- **Span**：链路中的单个步骤，例如一次模型调用或一次工具执行

有了 Trace / Span，你才能看到：

- 问题卡在模型推理，还是卡在 browser / shell / web API
- 某一步是否重复重试导致总体超时
- 哪个子任务最耗时，是否值得单独优化

### 3. 一条完整任务是怎么被“看见”的

一个典型链路通常是：

1. 用户消息或 cron 触发任务
2. 系统为该任务分配 session / task / trace 标识
3. 模型开始推理，形成执行计划
4. 工具逐步执行，并写入每一步日志与状态变化
5. 若某一步失败，记录失败原因、重试策略、最终退出状态
6. 汇总成功率、耗时、错误类型进入统计面板

这意味着，可观测性并不是一个额外外挂，而是**和执行引擎一体化设计**的基础能力。

### 4. 可观测性的关键指标，应该看什么

如果只盯“有没有报错”，太浅。更有管理价值的指标通常包括：

- **任务成功率**：完成 / 总任务数
- **平均耗时 P50 / P95**：看常态与尾部延迟
- **重试率**：说明外部依赖或流程设计是否脆弱
- **人工介入率**：说明自动化成熟度是否足够
- **单位任务成本**：模型、工具、外部 API 的综合消耗
- **高风险失败占比**：失败里哪些会真正影响业务输出

### 5. 常见失败点与设计注意事项

#### 日志缺失
关键步骤没记录，事后只能“猜”。

#### 追踪断裂
异步子任务、外部执行器、脚本进程之间没传递 trace id，导致链路被切断。

#### 过度记录
把完整 prompt、敏感字段、凭证信息直接打进日志，带来合规风险。

#### 指标只有技术视角，没有业务视角
只看 CPU、内存、报错数，但看不到任务是否完成、是否按 SLA 交付、是否值得继续投资源。

## 业务翻译（业务视角）

### 这项能力到底解决什么问题

一句话：**让 Agent 从“黑盒玩具”变成“可运营系统”**。

对业务负责人来说，可观测性不是给工程师看的附属品，而是决定 AI 项目能不能规模化的前提。

### 为什么业务会愿意用

因为业务真正关心的不是技术词，而是这几件事：

- 为什么这次日报没发出来
- 哪类任务总是拖慢
- 哪些失败要人工补位
- 本月投入的模型成本是否值得
- 出问题后能不能追到责任与环节

可观测性把这些问题从“靠感觉”变成“看证据”。

### 它带来的四类价值

- **提效**：排障从到处翻消息、问人，变成按 trace 查链路
- **提质**：能系统识别高频失败模式，持续优化 prompt、工具和流程
- **提速**：告警更早、定位更快，减少任务积压
- **可控**：能审计、能留痕、能解释，便于对管理层和合规团队交代

## 典型场景（个人版）

### 场景 1：日报任务突然没发出来

你定了一个每天 9 点发送的自动日报。今天没收到结果。

有可观测性时，你可以很快判断：

- cron 是否被正常触发
- 模型是否成功生成内容
- 消息发送环节是否失败
- 失败发生在第几步，是否已经自动重试

这和“等人发现、再逐步排查”完全不是一个效率级别。

### 场景 2：Browser 自动化偶发超时

你发现网页抓取任务这周经常变慢，但不是每次都报错。

通过追踪可以看到：

- 是页面加载慢，还是页面元素定位失败
- 是某个站点变慢，还是所有任务都变慢
- 超时前是否发生过重试
- 平均耗时和 P95 是否已经持续上升

这时你才能决定是改流程、加等待策略，还是拆分任务。

### 场景 3：老板问“这个 Agent 值不值得继续投”

如果只有“感觉还行”，很难支撑资源决策；但如果你能拿出：

- 每周任务量
- 成功率
- 人工介入率
- 单任务成本变化
- 高风险失败数量

那就能从“技术尝试”升级为“经营分析对象”。

## 管理者关注点（成本/效率/风险）

### 成本

- 日志、追踪、看板不是“可有可无的附属品”，而是规模化运行的必要成本
- 但记录也不能无上限，尤其是高频任务，需要有留存周期、级别控制和归档策略
- 真正该看的不是“监控花了多少钱”，而是“它是否显著降低了排障和人工兜底成本”

### 效率

- 没有可观测性，问题处理依赖核心人员经验，效率无法复制
- 有可观测性后，问题定位可模板化、值班可轮换、复盘可结构化
- 管理层更容易建立统一口径，比如成功率、SLA、人工介入率

### 风险

- 最大风险不是“没有图表”，而是**任务明明出问题了，但没人知道**
- 第二类风险是日志泄露敏感信息，因此脱敏和权限控制必须一起设计
- 如果只记录技术指标、不记录业务交付指标，最终仍然无法支撑经营决策

## 本日自检

1. 我能否清楚区分日志、状态、追踪各自回答的问题？
2. 如果一个自动化任务失败，我是否知道该先看触发、执行、结果还是追踪链路？
3. 如果让我给管理者报一个 AI 任务体系的周报，我会优先选哪些指标，为什么？

## 一句话总结

**可观测性不是为了“看起来专业”，而是为了让 Agent 任务从黑盒试验，变成能定位、能优化、能追责、能经营的业务系统。**
