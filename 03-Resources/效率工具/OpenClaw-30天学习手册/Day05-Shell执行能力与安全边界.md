# Day 05｜Shell执行能力与安全边界

## 今日主题

今天这篇要建立一个关键判断：**Shell 不是“让 AI 更像工程师”的炫技能力，而是把自然语言请求变成受控系统动作的执行闸门。**

OpenClaw 的 `exec` / `process` 能力，能把命令执行、长任务跟踪、日志采集串成一个自动化闭环。但从组织视角看，真正重要的不是“能不能跑命令”，而是三件事：

- 谁能触发执行；
- 命令在什么边界内执行；
- 出错后能不能追溯、拦截、止损。

所以 Day05 的重点不是学几条终端命令，而是理解 **Shell 执行能力为什么必须和权限、模板、审计一起设计**。只有这样，它才适合进入真实业务流程。

## 技术原理（技术视角）

### 1. Shell 执行，本质上是结构化进程调用

在 OpenClaw 里，模型不会“直接拥有终端”，而是通过工具发起一次受参数约束的执行请求。以 `exec` 为例，真正送入执行引擎的通常包括：

- `command`：具体要执行的命令或脚本；
- `workdir`：在哪个目录执行；
- `timeout` / `yieldMs`：执行多久、多久回收一次结果；
- `background`：是否转成长任务；
- `pty`：是否需要交互式终端。

这意味着，Shell 不是一句模糊的“帮我跑一下”，而是一个可被系统明确描述、校验、记录、回收的动作单元。

**关键认知：**
- 模型负责形成执行意图；
- 工具负责把意图翻译成进程调用；
- 平台负责决定这次调用是否应被允许。

这三层拆不开，一旦混在一起，系统就很难治理。

### 2. 从一次执行，到一条完整链路

一个成熟的 Shell 执行链路，至少会经过下面几步：

1. 用户提出需求，例如“检查服务日志”或“批量生成日报”；
2. 模型把需求转换为命令意图；
3. 策略层检查身份、场景、审批状态；
4. 命令被模板化，并替换成受控参数；
5. `exec` 发起实际执行；
6. 若任务较长，转交 `process` 继续跟踪；
7. 系统回收 `stdout`、`stderr`、退出码、耗时；
8. 将结果结构化反馈给用户，并沉淀审计记录。

真正的工程价值，就藏在第 3 到第 8 步里。没有这些环节，Shell 只是“把命令跑出去了”；有了这些环节，Shell 才能成为可上线的执行基础设施。

### 3. 为什么“模板化”比“自由拼接命令”更重要

很多初学者会把用户原话直接拼接进 shell 命令，这在实验阶段看起来省事，但风险极高。

更稳妥的思路是：

- 先定义固定命令模板；
- 再把可变部分收敛为有限参数；
- 对参数格式、范围、枚举值做校验；
- 最后才允许执行。

例如，“查看昨晚接口错误日志”不应该被直接翻译成一条自由文本命令，而应落到类似：

- 命令模板：`./scripts/query_error_log.sh <date> <service>`
- 允许参数：日期格式、服务名单、时间范围上限

这样做的好处不是“代码更漂亮”，而是**系统从开放式执行，变成半结构化执行**。治理难度会明显下降。

### 4. `exec` 和 `process` 为什么要配合看

`exec` 更像启动器，负责把命令跑起来；`process` 更像运行管家，负责长任务的后续管理。

当一个命令可能：

- 运行超过几秒，
- 需要分段拿日志，
- 可能需要人工中止，
- 需要后台持续观察，

就不应该只把它当一次即时返回，而要把它当“可跟踪进程”处理。

这时 `process` 的价值在于：

- 查看运行状态；
- 拉取增量日志；
- 对卡死任务做 kill；
- 把长任务变成可运维的对象。

如果只会 `exec`，不会 `process`，那你拥有的只是“发令能力”；真正上线后需要的是“发令 + 监管 + 收尾”的完整闭环。

### 5. 安全边界应该落在哪些地方

Shell 能力至少要从以下几个维度加边界：

#### 权限边界
不是每个入口、每个人、每个场景都能执行相同级别的命令。查询类、写入类、系统级改动类要分层。

#### 路径边界
执行目录不应随意漂移。很多风险不是命令本身危险，而是命令在错误目录运行后造成错误影响。

#### 参数边界
避免让模型或用户自由注入未校验字符串，尤其是管道、重定向、分号、通配符等高风险片段。

#### 时间边界
必须有超时。没有超时的自动化任务，最终几乎一定会变成资源黑洞。

#### 并发边界
高成本命令、批处理命令、外部依赖命令都要限制并发，避免打爆机器或外部服务。

#### 审计边界
不只记录“跑了没”，还要记录：谁发起、何时执行、命令摘要、结果码、耗时、是否人工介入。

### 6. 常见误区

#### 误区一：能跑起来就算完成
很多 Demo 到这里就停了，但真实环境里，“跑起来”只是 20%，剩下 80% 是防错、防滥用、可回溯。

#### 误区二：只看 stdout，不看退出码
Shell 里最危险的假象，就是“有输出，看起来像成功”。真正判断执行成败，必须同时看退出码和 `stderr`。

#### 误区三：把开发机权限照搬到正式环境
开发环境为了提速，经常权限放得很松；如果原样复制到生产，Shell 能力就会立刻从提效工具变成事故入口。

#### 误区四：长任务仍按短任务思路处理
命令一旦进入分钟级、持续日志型、需要人工判断型，就必须转为进程管理思路，而不是等一次性返回。

## 业务翻译（业务视角）

### 这项能力解决什么问题

它解决的是组织里一类非常高频、但很少被标准化的问题：**很多动作本来有明确规则，却仍然依赖某个同学手动开终端执行。**

例如：

- 查日志；
- 跑例行检查；
- 触发构建；
- 拉取状态；
- 执行固定脚本；
- 回收任务输出。

这些动作如果继续靠“会命令的人”手工完成，组织效率很容易被少数人绑定。

### 为什么业务能理解并愿意使用

业务不一定关心 `exec` 的参数细节，但一定关心：

- 请求发出去后，是不是能稳定得到结果；
- 高风险动作是不是会被误触发；
- 出了问题，能不能立刻知道卡在哪一层；
- 这套能力是否能复制给更多人，而不是只靠核心工程师。

换句话说，业务真正买单的不是“终端自动化”，而是：

> 把原本依赖个人经验的命令执行，升级成可授权、可复用、可审计的服务能力。

### 提效 / 提质 / 提速 / 可控价值

- **提效**：高频固定动作模板化后，不需要每次人工敲命令；
- **提质**：统一脚本入口和参数校验，减少“同一件事每个人做法不同”；
- **提速**：查询和检查类任务可以秒级触发，减少等待关键人在线；
- **可控**：通过审批、超时、审计、人工介入机制，把高风险动作收在系统边界里。

## 典型场景（个人版）

1. **日志诊断助手**  
   用户说“帮我看今天凌晨支付服务的错误峰值”，系统并不是开放式让模型自由拼命令，而是调用固定日志查询脚本，只允许日期、服务名、时间范围三个参数可变，最后返回结论、关键日志片段和原始命令摘要。

2. **发布前健康检查**  
   发版前执行一组标准只读检查，例如磁盘空间、依赖连通性、进程状态、端口监听情况。系统统一输出“通过项 / 风险项 / 建议动作”，替代人工逐条敲命令。

3. **长任务后台跟踪**  
   某个批量任务需要持续运行十几分钟。系统先用 `exec` 启动，再用 `process` 轮询状态、拉取增量日志，必要时允许人工中止，最终生成结构化结果。

4. **高危动作审批后执行**  
   当请求涉及写入、迁移、删除或外发操作时，系统先阻断直接执行，只有审批通过后，才允许进入命令模板执行阶段，并保留完整审计记录。

## 管理者关注点（成本/效率/风险）

### 成本

- 要让 Shell 真正可上线，前期必须投入命令模板、审批分级、日志留痕、超时控制等基础建设；
- 这部分看起来不像业务功能，但它决定后续能不能规模复用；
- 如果早期偷省这笔成本，后面通常会以事故、返工、人工兜底的形式补回来。

### 效率

- 一旦高频命令标准化，很多“必须找某个人”的动作就能变成“系统按规则执行”；
- 排障效率也会提升，因为输出是结构化的，不再依赖个人解读终端结果；
- 对管理者而言，这会直接提升团队对重复型事务的吞吐能力。

### 风险

- 最大风险不是“命令失败”，而是“错误的人在错误的场景执行了错误的命令”；
- 第二类风险是没有超时、没有并发边界，导致系统被长任务拖垮；
- 第三类风险是缺少审计，出了问题却追不出执行来源和影响范围。

Shell 能力真正可用的前提，不是“AI 会跑命令”，而是“系统能在权限、模板、超时、审计等边界内，把命令执行变成可治理的业务动作”。
