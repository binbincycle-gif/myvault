# Day 05｜Shell执行能力与安全边界

## 今日主题
把“AI 能直接跑命令”升级为“AI 在受控边界内稳定执行命令”。

Shell 能力是 OpenClaw 最有威力的执行引擎之一：它可以调系统命令、脚本、CLI 工具，快速完成诊断、构建、批处理等任务。问题在于，**能力越强，越要边界清晰**。今天的重点不是“怎么让命令跑起来”，而是“怎么让命令跑得可控、可审计、可复盘”。

---

## 技术原理（技术视角）

### 1) Shell 执行本质：受参数约束的进程调用
在 OpenClaw 中，Shell 执行通常通过 `exec` 工具触发。执行单元不是“自然语言”，而是被整理后的命令字符串 + 运行参数（工作目录、超时时间、是否后台、是否需要 PTY 等）。

关键认知：
- 模型负责“生成执行意图”，工具负责“按参数执行进程”；
- 运行参数决定了风险面（例如可访问路径、可运行时长）；
- 执行结果必须结构化返回（stdout/stderr/exit code），否则无法稳定进入下一步自动化。

### 2) 安全边界要前置：先做约束，再放行执行
可控的 Shell 不是“任意命令都能跑”，而是“只在定义好的边界里跑”。典型做法：
1. 命令模板化（把可变部分收敛为参数）；
2. 参数白名单（只允许预期值/预期格式）；
3. 路径约束（限定工作目录）；
4. 超时与并发上限（防止卡死与资源打满）；
5. 高危指令拦截（删除、网络外发、系统级改动等）。

### 3) 关键组件
- **exec**：发起命令执行，可设 `workdir`、`yieldMs`、`timeout`、`background` 等；
- **process**：管理后台任务（查询日志、轮询、停止），把长任务变成可观测流程；
- **Policy Gate（策略层）**：在真正执行前进行权限和命令规则检查；
- **Audit（审计）**：记录执行者、命令摘要、耗时、结果码，支撑问责与复盘。

### 4) 常见失败点
- **直接拼接用户输入进命令**：极易造成命令注入；
- **没有超时**：任务卡死后拖垮队列；
- **只看 stdout，不看 exit code/stderr**：误把失败当成功；
- **无审计链路**：出错后无法追溯“谁在何时执行了什么”；
- **把开发环境权限复制到生产**：一旦误触发，影响面成倍扩大。

## 业务翻译（业务视角）

### 这项能力解决的核心问题
把“人工在终端重复操作”变成“系统按规则自动执行并反馈结果”。

它直接影响两个管理目标：
- **效率目标**：减少重复运维动作与人工脚本执行；
- **风险目标**：把高危动作关进可审计、可回滚、可复盘的流程里。

### 对效率/质量/速度/可控的影响
- **效率**：日常查询、批处理、例行检查可以标准化执行；
- **质量**：统一命令模板，减少“每个人写法不同”导致的误差；
- **速度**：事件响应从“找人上机”变成“授权后秒级触发”；
- **可控**：关键动作有前置策略和审计记录，不再黑箱执行。

---

## 典型场景（个人版）
1. **日志快速诊断助手**  
   用户输入“检查昨晚 API 错误峰值”，系统仅允许执行预定义日志查询命令，超时自动终止，并输出“结论 + 关键片段 + 原始命令摘要”。

2. **发布前健康检查**  
   在固定目录执行一组只读健康检查脚本（磁盘、依赖、端口、服务状态），失败项按结构化格式返回，避免人工逐条跑命令。

## 管理者关注点
- **成本**：前期建设命令模板与策略规则需要投入，但能显著减少后续重复人工与事故处理成本；
- **效率**：高频、低风险命令自动化后，团队响应速度明显提升；
- **风险**：通过权限分级、超时限制、审计留痕，把“可执行能力”从高风险资产变成可治理资产。

## 一句话总结
Shell 能力真正的价值不在“能跑命令”，而在“在可控边界内稳定跑命令，并把结果变成可管理的业务输出”。
