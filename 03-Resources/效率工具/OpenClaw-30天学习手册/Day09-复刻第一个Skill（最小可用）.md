# Day 09｜复刻第一个 Skill（最小可用）

## 今日主题

今天开始进入 Skill 的实操层：不追求一次做出复杂插件，而是先复刻一个**最小可用 Skill**，理解 OpenClaw 如何把一段稳定经验沉淀成 Agent 可读取、可执行、可复用的能力。

这里的 Skill，不是传统意义上必须安装、编译、发布的插件工程。它更像一份“给 Agent 看的能力说明书”：告诉 Agent 在什么场景下应该使用这项能力、执行时遵守什么流程、产出什么格式、哪些动作要谨慎。

最小可用版本通常只需要：

```text
my-first-skill/
└── SKILL.md
```

如果要增强，再逐步增加 `templates/`、`scripts/`、示例文件、检查清单或外部工具说明。今天的重点不是“写代码”，而是先跑通从经验到能力的闭环。

学完今天，你要能回答三个问题：

1. 一个最小 Skill 由什么组成？
2. OpenClaw 为什么能根据任务自动选择 Skill？
3. 为什么管理者要把高频经验沉淀成 Skill，而不是一直靠临场提示词？

## 技术原理（技术视角）

### 1）Skill 的本质：可触发的执行上下文

OpenClaw 的 Skill 采用接近 AgentSkills 的组织方式。最核心的是 `SKILL.md`，它一般包含两部分：

- **YAML frontmatter**：声明 `name`、`description` 等元信息；
- **Markdown 正文**：写清楚触发场景、执行步骤、输出格式、边界条件、资料路径和失败处理。

一个最小 Skill 可以这样写：

```markdown
---
name: hello-world
description: 当用户要求测试自定义 Skill 是否生效，或要求生成简短问候语时使用。
---

# Hello World Skill

## Use when
- 用户想验证 Skill 是否被 OpenClaw 识别。
- 用户要求输出一句简短问候。

## Output
- 使用中文。
- 输出一句自然问候。
- 说明这是来自自定义 Skill 的响应。

## Rules
- 不访问外部系统。
- 不保存用户隐私信息。
- 不执行文件删除、消息发送等外部动作。
```

这已经是一个能被读取的 Skill。它没有独立后端，也不一定要有脚本；它的价值在于让 Agent 在合适场景下获得一套稳定规则，而不是每次重新理解用户偏好。

### 2）OpenClaw 如何发现 Skill

OpenClaw 会从固定目录加载 Skill，常见来源包括：

1. **Workspace skills**：当前工作区的 `skills/`，适合项目专属能力；
2. **Managed / local skills**：例如 `~/.openclaw/skills`，适合本机长期复用；
3. **Bundled skills**：OpenClaw 内置通用能力；
4. **extraDirs**：配置中额外指定的 Skill 目录。

如果同名 Skill 出现在多个位置，一般应理解为“越贴近当前工作区，越适合当前任务”。这让团队可以先用通用 Skill 打底，再在具体项目或知识库里做定制。

### 3）`description` 决定能不能被正确选中

很多 Skill 失效，不是正文写得不够多，而是 `description` 写得太空。Agent 在选择 Skill 时，会优先看描述是否匹配当前任务。

不好的写法：

```yaml
description: 一个很强大的日报工具。
```

问题是它没有说明“什么时候用”。更好的写法是：

```yaml
description: 当用户要求整理每日工作总结、管理复盘、行动项或风险清单时使用，输出适合直接转发的中文管理层版本。
```

好的 `description` 至少回答三个问题：

- 用户怎么说时该触发？
- 这个 Skill 解决哪类任务？
- 输出有什么明显特征？

### 4）最小 Skill 的正文结构

一个实用的最小 Skill，不需要很长，但要包含关键约束：

```markdown
# Daily Summary Skill

## Use when
- 用户给出零散记录，希望整理成日报、周报或复盘。

## Inputs
- 原始记录
- 日期或周期
- 输出对象，如个人、团队、管理层

## Steps
1. 先提炼结论。
2. 再整理已完成事项。
3. 标出风险、阻塞和待确认。
4. 最后给出明日动作。

## Output format
- 结论
- 已完成
- 风险与阻塞
- 明日动作

## Rules
- 不编造未提供的数据。
- 涉及外部发送前必须让用户确认。
- 语气要能直接用于工作沟通。
```

这份正文的作用，是把“怎么做”从对话里抽出来，变成稳定资产。后续同类任务只要触发 Skill，就能沿用同一套做法。

### 5）从最小可用到可治理能力

Skill 可以分阶段演进：

1. **说明型 Skill**：只有 `SKILL.md`，固化流程、格式、边界；
2. **模板型 Skill**：增加 `templates/`，把固定文案、表格结构、检查清单独立出来；
3. **脚本型 Skill**：增加 `scripts/`，让 Agent 调用本地脚本处理稳定数据；
4. **工具型 Skill**：结合浏览器、文件、Web、消息、子 Agent 等工具形成完整流程；
5. **治理型 Skill**：补充权限、审批、审计、脱敏、重试、失败降级。

最小可用的标准不是“功能很多”，而是四句话：

- 能被识别；
- 能按规则执行；
- 能稳定产出；
- 知道哪些事不能做。

### 6）常见误区

| 误区 | 问题 | 更稳的做法 |
|---|---|---|
| 一上来写复杂代码 | 价值没验证就进入工程成本 | 先用 `SKILL.md` 固化流程，再决定是否脚本化 |
| `description` 写得太泛 | Agent 不知道何时该用 | 写清楚触发场景、用户表达和输出特征 |
| 只写步骤，不写边界 | 容易误发、误删、误读敏感信息 | 把确认规则和禁止动作写进 Skill |
| 把 Skill 当知识库文章 | 只解释概念，不能指导执行 | 必须包含步骤、格式、工具边界和失败处理 |
| Skill 名称频繁变化 | 历史引用和团队习惯断裂 | 名称稳定，迭代正文和模板 |

## 业务翻译（业务视角）

### 这项能力解决什么问题

Skill 解决的是“组织经验无法稳定复用”的问题。

没有 Skill 时，很多工作依赖个人经验：某个人知道日报怎么写、会议纪要怎么收口、线上问题怎么复盘、浏览器自动化失败时如何处理。但这些经验如果只在脑子里，每次换人、换 Agent、换场景，都要重新解释一次。

有了 Skill，就可以把经验沉淀为一份 Agent 可读取的 SOP：

- 什么情况触发；
- 要读哪些资料；
- 按什么步骤做；
- 输出什么结构；
- 哪些动作必须确认；
- 失败时怎么降级。

这就是从“人会做”变成“组织可复用”。

### 为什么业务能理解并愿意使用

业务不需要理解 Skill 的底层实现，只需要理解它带来的变化：

1. **输出更稳定**：同类任务不再每次风格漂移；
2. **沟通成本更低**：不用反复解释“按以前那个格式来”；
3. **新人更容易上手**：流程、口径、边界都写在 Skill 里；
4. **风险更可控**：外部发送、删除、敏感数据处理可以提前写明确认规则。

对管理者来说，Skill 是 AI 时代的 SOP。传统 SOP 主要给人看；Skill 同时给人和 Agent 看。

### 提效 / 提质 / 提速 / 可控价值

- **提效**：高频任务不用每次重讲背景、格式和注意事项；
- **提质**：输出标准统一，减少遗漏关键字段；
- **提速**：从“先沟通半小时”变成“直接按 Skill 执行”；
- **可控**：风险边界前置，敏感动作不会被默认自动执行。

一句业务化表达是：

> Skill 不是把 AI 变聪明，而是把组织里已经验证过的做法，变成 AI 能稳定执行的能力包。

## 典型场景（个人版）

### 场景 1：每日学习资料生成

你希望每天自动生成一篇学习资料，而不是每天重新写提示词。Skill 可以固定：

- 知识库根目录；
- Day 文件命名规则；
- 正文结构；
- 图示风格；
- 官方资料引用方式；
- 完成后的通知口径。

这样学习计划就不再是一份静态目录，而是一条持续运行的内容生产流程。

### 场景 2：会议纪要整理

用户贴入会议记录后，Skill 可以固定输出：

1. 会议结论；
2. 已确认决策；
3. 行动项、负责人、时间点；
4. 风险与待确认；
5. 下一步建议。

价值不是“AI 会总结”，而是每次会议纪要都能按同一套管理结构收口。

### 场景 3：周问题复盘

每周整理问题时，Skill 可以规定数据来源、统计口径、风险分级、输出版本和发送前确认规则。这样复盘不会停留在问题列表，而会自然转成管理动作：谁负责、何时闭环、下周如何预防。

### 场景 4：浏览器自动化失败恢复

浏览器自动化经常遇到页面变化、登录失效、元素定位失败。Skill 可以规定恢复顺序：

- 先检查当前标签页；
- 再抓取快照；
- 再重新定位元素；
- 仍失败则降级为人工确认或静态抓取；
- 禁止在不确定状态下提交表单。

这类 Skill 的价值是减少中断，让长流程更稳定。

## 管理者关注点（成本/效率/风险）

### 成本

第一个 Skill 的主要成本不是开发，而是把流程说清楚：触发条件、输入、步骤、输出、边界。建议从高频、低风险、结果格式稳定的任务开始，不要一开始就挑战跨系统、跨权限、强外部影响的任务。

### 效率

Skill 的效率价值来自复用。如果一个任务每月只做一次，且每次判断都不同，未必值得立刻 Skill 化；如果一个任务每天、每周都出现，并且输出结构相对固定，就适合优先沉淀。

### 风险

Skill 里不要写入密钥、内部账号、客户隐私、不可公开资料。涉及以下动作时，必须在规则中写清楚确认机制：

- 对外发送；
- 删除或覆盖文件；
- 读取敏感数据；
- 调用付费接口；
- 长时间无人值守执行。

### 规模化

当团队开始大量创建 Skill，管理重点会从“会不会写”转向“如何治理”：命名是否统一、目录是否清晰、版本是否可追踪、过时规则是否淘汰、失败经验是否回写。否则 Skill 会从资产变成另一种混乱。

## 本日自检

1. 我是否能解释：为什么最小 Skill 只需要一个目录和一个 `SKILL.md`？
2. 我是否能写出包含 `name`、`description`、触发场景、输出格式和风险边界的最小 Skill？
3. 我是否知道 Workspace skills、local skills、bundled skills 的大致区别？
4. 我是否能判断一个任务是否适合先做成说明型 Skill？
5. 我是否会在 Skill 中写清楚外部发送、敏感数据、删除操作等风险边界？
6. 我是否理解：Skill 的价值不是“多一个文件”，而是让经验从个人脑中进入组织资产？

## 一句话总结

最小 Skill 不是“小功能”，而是把一次稳定经验变成可重复执行的 AI SOP：先用 `SKILL.md` 跑通闭环，再逐步补模板、脚本、工具和治理规则。
