# Day 08｜Skill机制总览与开发入口

## 今日主题
Skill 不是给 OpenClaw 多加一个“功能按钮”，而是把原本分散在提示词、脚本、人工步骤里的动作，沉淀成 Agent 能理解、能调用、能治理的能力单元。理解 Skill，等于理解 OpenClaw 如何把“个人会用”升级成“团队可复用”。

## 技术原理（技术视角）
### 1）Skill 在系统里到底扮演什么角色
如果只看表面，Skill 像是一份说明文档；但在运行机制上，它更像一层“能力路由说明书”。

它告诉 Agent 三件事：
- **这类问题什么时候该用我**；
- **调用我时要遵守什么规则**；
- **我背后能接通哪些工具、脚本或外部资源**。

所以 Skill 的核心价值，不是“替代工具”，而是把工具组织成可被模型理解的业务能力。没有 Skill，模型知道有 `read`、`write`、`web_fetch` 这些零件，但不一定知道如何把它们稳定组合成“日报整理”“天气播报”“知识库入库”这类完整动作。

### 2）Skill 的最小构成
在 OpenClaw 里，一个 Skill 通常至少包含一个 `SKILL.md`。这份文件不是普通注释，而是模型使用这项能力的操作说明。它最关键的部分有：

#### name
Skill 的唯一标识。它解决的是“系统怎么认出这项能力”。

#### description
这是最容易被低估的一段。Agent 很多时候靠 description 判断：
- 这个 Skill 适合处理什么问题；
- 什么时候不该调用它；
- 它输出的大概是什么结果。

description 写得模糊，后面所有工具、脚本再完整，匹配质量也会下降。

#### instructions / body
也就是 `SKILL.md` 的正文部分。这里负责告诉模型：
- 这类任务应该按什么顺序处理；
- 要优先用哪些工具；
- 哪些情况需要补充校验；
- 哪些风险动作必须谨慎。

#### resources / scripts（可选）
很多 Skill 不只是纯文本规则，还会配套脚本、模板、示例、引用文件。这样 Skill 就不只是“会说”，而是“带着做事材料一起工作”。

### 3）Skill 与 Tool 的关系
这两个词最容易混：

- **Tool**：具体动作能力，比如读文件、发消息、查网页、执行命令。
- **Skill**：对一类场景的组织方法，决定什么时候调哪些 Tool、按什么顺序调、输出长什么样。

可以把它理解成：
- Tool 是零件；
- Skill 是装配方案；
- Agent 是根据目标选择装配方案的人。

所以团队真正要沉淀的，往往不是“再多几个工具”，而是“哪些场景已经值得封装成 Skill”。

### 4）Skill 是怎么被发现和加载的
根据官方文档，OpenClaw 会从多个目录加载 Skill，包括内置技能、用户技能、workspace 里的技能，并按优先级覆盖。同名 Skill 以更近的目录为准。

这背后有三个重要含义：
1. **Skill 是可扩展的**，不必每次改主程序；
2. **Skill 是可分层管理的**，个人、团队、平台可以各自维护；
3. **Skill 是可治理的**，因为加载来源、依赖条件、配置门槛都可以被约束。

这也是为什么 Skill 适合做长期能力资产，而不只是一次性提示词。

### 5）什么样的任务适合封装成 Skill
通常满足下面三个条件时，就值得考虑封装：
- **高频**：同类任务会反复出现；
- **边界清晰**：输入、输出、步骤比较稳定；
- **可校验**：结果好坏可以被判断，而不是完全凭主观。

比如：
- 固定结构的资料入库；
- 指定格式的日报/周报生成；
- 明确来源的网页信息抓取；
- 标准流程的提醒、通知、汇总。

相反，低频、判断极重、强依赖临场沟通的任务，不一定适合一开始就封装成 Skill。

### 6）常见误区
#### 误区一：把 Skill 当插件目录，而不是方法资产
如果只把 Skill 看成“一个文件夹”，就会忽略它真正的价值在于复用规则、输出规范和治理边界。

#### 误区二：过早追求“大而全”
一个 Skill 想包办太多场景，最后通常 description 不清、规则混乱、维护困难。更好的做法是单点明确，先把一个高频问题做透。

#### 误区三：只关心能不能跑，不关心能不能交给别人用
个人能跑通，不等于团队能复用。只有当 Skill 的适用边界、输入要求、失败处理都明确后，它才是组织资产。

## 业务翻译（业务视角）
### 这项能力解决什么问题
业务现场最常见的问题不是“没有 AI”，而是：
- 每个人都在写自己的提示词；
- 相似任务重复组织很多次；
- 好经验停留在个体，不容易复制；
- 一旦换人，质量和风格就波动。

Skill 机制解决的，正是这类“经验无法标准化”的问题。它把个人打法沉淀成系统可复用能力，让 AI 不只是会答题，而是会按固定做法干活。

### 为什么业务能理解并愿意使用
因为业务不需要理解底层实现，只需要看到三件事：
- **输入更简单**：不用每次重新描述完整操作手册；
- **输出更稳定**：相同场景，结构和质量更一致；
- **协作更顺**：好的做法能被复制，不靠单个人记忆。

### 提效 / 提质 / 提速 / 可控价值
- **提效**：把重复提示、重复整理、重复判断前移到 Skill 里，减少人工重说一遍。
- **提质**：通过统一结构和使用规则，降低输出随人波动的问题。
- **提速**：Agent 更快匹配到可用能力，少走“先试试再修”的弯路。
- **可控**：可以给高风险 Skill 加权限、审批、日志和边界说明，不把自动化交给运气。

一句业务化的翻译是：

> Skill 是把“某个人很会做这件事”，升级成“团队以后都能稳定把这件事做好”的能力封装层。

## 典型场景（个人版）
1. **知识库入库 Skill**  
   当你频繁说“把这篇内容整理成 Obsidian 可检索文档，并补图、放到固定目录”，这就已经不是一次性动作，而是值得封装的标准能力。

2. **日报/周报整理 Skill**  
   输入来源固定、输出结构固定、老板关注点固定，这类任务天然适合 Skill 化。价值不在写得多快，而在每次结构都稳。

3. **公开信息抓取与摘要 Skill**  
   对固定站点、固定字段、固定输出口径的抓取任务，Skill 化后可以减少反复解释“抓什么、怎么写、遇错怎么办”。

4. **定时提醒与播报 Skill**  
   当提醒不只是“到点说一句”，而是包含查询、整理、格式化和发送时，就已经进入 Skill 的适用区间。

## 管理者关注点（成本/效率/风险）
### 成本
Skill 的成本不在写一份 `SKILL.md`，而在前期把场景边界、输入要求、输出口径想清楚。建议优先挑复用频次高、返工成本大的任务做封装，这样投入回收最快。

### 效率
真正值得管理者盯的不是“团队写了多少个 Skill”，而是“有多少高频动作已经不再靠人工重复解释”。如果只是增加文件数量，没有减少重复劳动，那就不算有效沉淀。

### 风险
Skill 一旦连到真实工具，就会带来权限和合规问题。尤其是下面三类：
- 会对外发送信息；
- 会改写或删除数据；
- 会处理敏感内容或外部凭证。

这类 Skill 必须同时设计审批、日志和失败兜底，否则复用越高，风险放大越快。

## 本日自检
1. 我能不能用一句话说清 Skill 和 Tool 的差别？
2. 我能不能判断一个任务是“该直接做”，还是“已经值得封装成 Skill”？
3. 我是否知道一个好 Skill 至少要把适用场景、执行规则和风险边界写清楚？
4. 我能否从自己的工作里举出 1 个适合本周就开始 Skill 化的高频场景？

## 一句话总结
Skill 的本质，不是多一个功能入口，而是把高频、可校验、可复用的做事方法沉淀为 Agent 能稳定调用的组织能力。
