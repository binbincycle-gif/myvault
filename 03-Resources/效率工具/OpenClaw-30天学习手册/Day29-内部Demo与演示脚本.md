# Day 29｜内部 Demo 与演示脚本

## 今日主题

学到第 29 天，重点已经不再是“功能能不能跑”，而是“别人能不能一眼看懂你做成了什么”。内部 Demo 与演示脚本的价值，在于把一次临场发挥的展示，变成可复用、可彩排、可追溯的标准动作。它既是技术成果的展示层，也是推动决策、争取资源、降低沟通成本的放大器。

## 技术原理（技术视角）

### 1. Demo 不是临时表演，而是一条受控执行链路
一个靠谱的 Demo，通常包含四层能力：

1. **场景定义**：先定义这次要证明什么，是证明功能可用、流程闭环、性能稳定，还是证明异常情况下也能恢复。
2. **输入准备**：把用户、时间范围、测试数据、开关参数等前置准备好，避免现场靠手动拼凑。
3. **脚本执行**：按既定顺序完成操作，必要时调用浏览器自动化、数据填充、接口触发或消息通知。
4. **证据输出**：沉淀截图、日志、结果页、指标数据或录屏，保证事后可复盘、可复讲。

如果缺少其中任意一层，Demo 都容易变成“看起来能跑，但无法稳定复现”的一次性事件。

### 2. 演示脚本的核心是参数化，而不是写死流程
内部 Demo 经常面对不同对象：
- 给管理层看，重点是结果、效率、风险；
- 给同事看，重点是流程、细节、可复用性；
- 给潜在合作方看，重点是价值、可信度、边界。

所以同一条脚本不能写死为单一版本，而要做成可切换的参数化结构，例如：
- 演示客户名称用模拟数据替代；
- 时间窗口可切换为“近 7 天 / 近 30 天”；
- 展示路径可切换为“30 秒版 / 5 分钟版 / 深度版”；
- 出错分支可切换为“正常流 / 异常恢复流”。

参数化做得越好，Demo 越像产品资产，而不是某个人的私有技巧。

### 3. Record / Replay 让 Demo 从“讲过”变成“留痕”
很多团队做 Demo 的问题，不是现场讲不好，而是讲完之后无法复现：
- 为什么这次演示成功，下次却失败？
- 现场展示的数据，后来谁来校验？
- 某一步卡顿，是网络问题、环境问题，还是脚本本身问题？

这时候就需要记录与回放能力：
- **记录输入**：演示用的参数、环境变量、账号范围、数据准备口径；
- **记录过程**：关键步骤日志、截图、页面跳转、工具调用顺序；
- **记录结果**：最终结果页、关键指标、成功/失败状态。

有了这些，Demo 才从“讲一遍”升级成“组织可以复用的演示证据链”。

### 4. Demo 的本质是“预期控制”
技术上最容易忽略的一点，是 Demo 的核心不是展示全部能力，而是控制观众的注意力与预期：

- 什么必须看到，什么可以省略；
- 什么是主线流程，什么是补充说明；
- 什么步骤一旦失败必须兜底，什么失败可以现场解释。

这意味着演示脚本其实是一种“流程编排”。它不是把所有能力堆上去，而是按目标把信息密度、顺序、节奏都设计好。

### 5. 常见误区

#### 误区一：认为 Demo 只要有人会讲就行
如果一个 Demo 只能由某个熟手完成，它就不是组织资产，而是个人依赖。

#### 误区二：试图一次展示所有能力
展示太多，反而会让重点模糊。Demo 的目标是让人记住 1 到 3 个核心价值点，而不是铺满功能清单。

#### 误区三：没有失败预案
真正成熟的 Demo，一定会提前设计异常恢复路径，比如网络中断、接口超时、页面加载异常、数据源不可用时如何切到备用结果。

## 业务翻译（业务视角）

### 这项能力解决什么问题
内部 Demo 与演示脚本，本质上在解决三个业务问题：

- **价值说不清**：技术做了很多，但业务方看不到“到底改变了什么”；
- **每次都重来**：同一个能力反复讲、反复演、反复准备，成本很高；
- **难以复制**：演示效果依赖某个人，换人就失真，团队能力无法规模化。

### 为什么业务能理解并愿意使用
因为 Demo 直接作用于“看见价值”的环节。对于业务侧来说，技术能力是否采用，往往不取决于底层是否先进，而取决于以下三件事：

1. 我是不是能快速看懂；
2. 我是不是相信这个能力真的可用；
3. 我是不是知道把它放进我的工作后会产生什么结果。

一场设计好的 Demo，能把抽象能力转译成具体收益：
- **提效**：减少讲解和反复答疑；
- **提质**：展示口径统一，避免“同一个能力每个人讲法不同”；
- **提速**：推动项目更快获得拍板；
- **可控**：演示过程可彩排、可复盘，风险更低。

### 更适合管理者的一句话翻译
> Demo 不是“好看一点的汇报”，而是让一个技术能力更容易被组织采纳的成交界面。

## 典型场景（个人版）

1. **给管理层做阶段成果汇报**  
   你不是要展示所有过程，而是用 3 到 5 分钟讲清楚“问题是什么、方案怎么跑、结果有何变化、风险边界在哪里”。这类 Demo 更强调结果页、对比数据和可复制性。

2. **给团队做新能力培训**  
   同一个能力，如果没有演示脚本，新同学只能靠口头理解。把它做成标准化 Demo 后，新人可以先看一遍“正常流”，再看一遍“异常恢复流”，上手速度会明显提升。

3. **为项目立项或资源申请做验证**  
   当你需要争取人力、预算或排期时，单靠 PPT 很难说服。可运行的 Demo 更像“低成本样机”，能把抽象设想变成直观证据。

4. **沉淀成可复用对外讲解素材**  
   即使初衷是内部使用，只要全程避免公司隐私信息、客户真实数据和内部账号，就有机会沉淀成未来的外部分享素材。

## 管理者关注点（成本/效率/风险）

### 成本
做一套标准化 Demo 脚本，前期会消耗一定准备时间，包括梳理话术、清洗数据、编排步骤、录制或彩排。但这部分投入适合复用频率高、需要反复说服的能力场景，一旦形成模板，边际成本会快速下降。

### 效率
一个成熟的演示脚本，可以把“每次都重新准备”的低效过程压缩成“选场景, 改参数, 直接跑”。对管理者来说，这意味着汇报、培训、立项说明和跨部门沟通都能提速。

### 风险
Demo 最大的风险不只是现场翻车，更是展示了不该展示的数据，或承诺了系统还不稳定的能力。因此必须提前明确：
- 用的是不是脱敏或模拟数据；
- 哪些结果是录制回放，哪些是真实实时执行；
- 哪些功能当前只适合内部验证，不适合对外承诺。

## 本日自检
1. 我是否能解释清楚，为什么 Demo 的核心不是展示“多”，而是展示“准”？
2. 我是否能把一个真实演示拆成“目标定义、参数准备、脚本执行、证据输出”四层结构？
3. 我是否为关键演示准备了异常恢复方案，而不是假设现场一定顺利？
4. 我是否知道哪些数据可以展示，哪些内容必须用模拟数据替代？

## 一句话总结
把 Demo 做成脚本化、参数化、可回放的资产，技术能力才更容易被组织看懂、相信并持续复用。
