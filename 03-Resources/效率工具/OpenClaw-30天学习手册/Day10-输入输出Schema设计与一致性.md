# Day 10｜输入输出 Schema 设计与一致性

## 今日主题
前几天我们已经理解了 Skill 的基本结构、最小可用能力和常见执行链路，今天往前再走一步：为什么有些 Skill 看起来功能不复杂，却总是容易“调用失败、参数传错、结果不稳定”？答案通常不在模型聪不聪明，而在 **Schema 设计是否清楚**。

Schema 可以理解成 Agent 与工具之间的“接口契约”。它解决的不是文档好不好看，而是：**Agent 该传什么、工具会回什么、上下游如何稳定衔接**。如果这个契约含糊，系统就会陷入反复试错；如果契约清楚，Skill 才有机会从“能跑一次”升级为“能长期复用”。

## 技术原理（技术视角）
### 1）什么是 Schema，为什么它比提示词更底层
在 OpenClaw 的 Skill 设计里，提示词负责“教模型理解意图”，Schema 负责“约束模型如何与能力对接”。两者都重要，但位置不同：

- **提示词** 解决“要做什么”；
- **Schema** 解决“怎么把要做的事翻译成结构化参数与结果”。

这意味着：哪怕提示写得很好，如果输入字段混乱、类型不稳定、返回格式经常变，整条调用链依然会不可靠。

所以 Schema 本质上不是“给程序员看的注释”，而是 Agent 侧执行稳定性的基础设施。

### 2）输入 Schema：先把入口说清楚
输入 Schema 的核心任务，是把“自然语言意图”压缩成“工具可接收的结构化参数”。一个好的输入 Schema，至少要回答五个问题：

1. **需要哪些字段**：哪些是完成任务必须提供的；
2. **字段是什么类型**：字符串、数字、布尔、数组还是对象；
3. **字段允许什么范围**：长度、数值区间、枚举值；
4. **哪些字段可选**：缺省时怎么处理；
5. **字段语义是否单一**：一个字段不要同时承担多个意思。

例如“发消息”这个能力，如果只定义一个 `content` 字段，看似简单，实际上很容易出问题：
- 发给谁？
- 是文字还是附件？
- 是否静默发送？
- 是否带标题？

如果这些信息全靠模型从上下文里“猜”，调用就会不稳定。更合理的设计，是把目标对象、内容主体、发送选项拆开，让 Agent 在生成参数时有明确的结构抓手。

### 3）输出 Schema：让结果可被后续步骤继续使用
很多人做 Skill 时，会认真设计输入，却忽视输出。结果就是：工具虽然完成了动作，但返回结构非常随意，导致后续步骤无法稳定接力。

输出 Schema 要解决的核心问题是：**这次调用返回的内容，能否继续进入下一步流程，而不用再次人工解释。**

一个可复用的输出结构，通常应包含三层：
- **状态层**：这次调用成功还是失败，例如 `success`；
- **业务数据层**：成功时的结果主体，例如 `record_id`、`file_path`、`summary`；
- **错误层**：失败时的原因表达，例如 `error.code`、`error.detail`。

为什么必须把错误也结构化？因为对 Agent 来说，“失败”不是结束，往往是下一轮判断的起点。只有把失败原因表达清楚，Agent 才知道应该重试、改参数、换工具，还是向用户请求补充信息。

### 4）一致性的真正含义：不是字段一样，而是认知一样
说到“一致性”，很多人只想到“字段命名统一”。这当然重要，但还不够。一致性至少有三层：

#### 第一层：类型一致
同一个字段不要这次是字符串、下次是对象。比如 `result` 字段，如果有时返回文本，有时返回数组，有时又嵌套更多对象，调用方就很难处理。

#### 第二层：语义一致
同一个字段名不要在不同上下文里表示不同含义。比如 `status` 可能表示任务执行状态、业务单据状态、审批状态。如果不加限定，很快就会混乱。

#### 第三层：失败表达一致
不同 Skill 如果都可能失败，就应尽量用相似的失败结构表达。这样 Agent 在处理异常时，逻辑可以更统一，不用每个工具都重新适配。

真正高质量的 Schema，不只是“今天能用”，而是让未来多个 Skill 叠加后仍然可组合。

### 5）常见字段设计原则
下面这些原则，在 OpenClaw 这类 Agent 工具场景里非常实用：

- **字段名尽量短，但语义明确**：避免 `data1`、`info` 这种模糊命名。
- **必填字段要克制**：只把真的不可缺少的字段列入 required，别把可推断项也全设成必填。
- **枚举优先于自由文本**：状态、模式、类型这类值，能枚举就尽量枚举，减少模型自由发挥空间。
- **数组和对象要写清内部结构**：不要只声明“是数组”，还要定义数组元素是什么。
- **默认值慎用**：默认值能减少调用成本，但如果默认错了，会把错误静悄悄地放大。
- **为错误恢复留出口**：输出里保留错误码或错误类型，方便 Agent 做下一步处理。

### 6）为什么 Schema 能直接影响调用成功率
从执行链路看，Schema 至少影响三个关键环节：

#### 环节一：参数构造
模型会依据字段描述理解要传什么。如果字段命名清楚、描述具体、约束明确，Agent 一次构造正确参数的概率会明显提高。

#### 环节二：参数校验
当输入不合法时，系统能尽早拦住，而不是等业务逻辑跑到中间才爆掉。越早暴露错误，修复成本越低。

#### 环节三：结果复用
输出稳定后，另一个 Skill、后续步骤、自动化脚本都能继续接上，不需要人手工改格式。这就是从“单次调用”升级成“工作流组件”的关键。

### 7）典型失败点
#### 失败点一：字段语义太宽
比如一个 `query` 字段既可能放搜索词，也可能放完整指令，最后谁都不知道它到底承载什么。

#### 失败点二：描述写得过短
如果 description 只有“名称”“内容”“值”，模型很难判断上下文含义。Schema 不是只给程序看，也是在给 Agent 提供执行提示。

#### 失败点三：输出结构不固定
今天返回 `url`，明天返回 `link`；今天用 `message` 表示成功说明，明天又用 `detail`。调用方迟早崩。

#### 失败点四：把容错全推给模型
有些设计把复杂判断都留给 Agent 自己推断，表面上灵活，实则大幅增加不稳定性。高频能力应该尽量通过 Schema 前置约束，而不是事后猜对。

## 业务翻译（业务视角）
### 1）这项能力解决什么问题
从业务视角看，Schema 解决的是“AI 调系统时到底靠不靠谱”。

如果没有清晰 Schema，业务会感受到几个典型问题：
- 同样一句需求，这次成功，下次失败；
- 看起来做的是同一件事，结果格式却不一致；
- 一个流程里接了多个工具后，前后容易断链。

所以 Schema 的本质，是把“AI 理解业务”这件事，从概率问题，尽量拉向工程问题。

### 2）为什么业务能理解并愿意使用
业务不一定关心 JSON Schema 细节，但一定关心：
- 调用是否稳定；
- 数据是否容易接着用；
- 出错时是否能快速定位；
- 一个能力能不能被团队重复复用。

Schema 设计清楚后，业务会更容易把 Agent 看成“可接入流程的能力节点”，而不是只能做演示的聪明对话框。

### 3）提效 / 提质 / 提速 / 可控价值
- **提效**：减少反复试参数、人工纠错和重复调试。
- **提质**：输出结构稳定，后续汇总、记录、审批、通知都更容易标准化。
- **提速**：跨工具组合时更顺滑，不需要每次都手工解释结果。
- **可控**：输入边界和输出边界清楚后，问题更容易排查，版本演进也更可管理。

一句更容易被管理者理解的翻译是：

> Schema 不是技术细节，它是 AI 能否规模化接入业务流程的接口纪律。

## 典型场景（个人版）
1. **知识库写入 Skill**  
   输入需要明确：目标路径、文档标题、正文内容、是否覆盖；输出需要统一：是否成功、写入路径、失败原因。否则“写成功了但写错位置”这类问题很难排查。

2. **日程创建 Skill**  
   输入至少应区分标题、开始时间、时长、参与人、提醒方式；输出则应给出事件 ID、创建状态、冲突信息。这样后续才能继续改期、通知或取消。

3. **检索 + 摘要组合流程**  
   前一个 Skill 输出的是文档列表，后一个 Skill 需要接收文档路径或 URL。如果前一个结果字段不稳定，后一个就无法可靠接力。

4. **审批类 Skill**  
   输入必须清楚表达审批对象、动作、风险摘要；输出必须明确是通过、拒绝还是待补信息。否则自动化流程很容易误判状态。

## 管理者关注点（成本 / 效率 / 风险）
### 成本
Schema 设计会增加一点前期思考成本，需要把字段、边界、默认值和异常结构先想清楚。但这类成本通常是一次性的，远低于后期在调用失败、返工排错上持续消耗的时间。

### 效率
当一个团队开始复用多个 Skill 时，Schema 一致性会直接决定协作效率。接口越稳定，复用越容易，跨人协作成本越低。

### 风险
最容易被忽视的风险有三个：
- 字段设计模糊，导致错误参数静默进入系统；
- 输出格式漂移，导致工作流后半段不稳定；
- 版本变更无纪律，让旧调用链突然失效。

所以管理上要盯的是：**有没有接口纪律，而不是只看有没有把功能做出来。**

3. 我是否知道字段一致性不只包括命名一致，还包括类型、语义和错误结构一致？
4. 我能否举出一个自己工作中的能力，并先定义清楚输入字段、输出结果和失败表达？

## 一句话总结
Schema 的价值，不在于把字段写整齐，而在于把 Agent 与工具之间的协作关系，变成稳定、可校验、可复用的接口契约。
