# Day 27｜告警机制与 SLA 口径

## 今日主题
到 Day27，学习重点开始从“把能力做出来”切到“把能力管起来”。前面我们已经搭过浏览器自动化、发布助手、稳定性周报等能力，但只要系统一进入真实生产环境，一个问题就会立刻出现：**什么时候算出故障了，谁该先知道，多久没恢复就算失约**。

这就是今天要讲的主题，**告警机制与 SLA 口径**。它不是“多发几条消息”这么简单，而是要回答三件事：
- 哪些信号值得被持续监控；
- 哪些异常应该立刻打断人；
- 哪些服务承诺必须能被量化和复盘。

如果没有告警机制，团队会变成“用户先报错，内部再排查”；如果没有 SLA 口径，团队就只能说“我们挺稳定”，但说不清到底稳定到什么程度。真正成熟的做法，是把服务运行状态变成一套**可观测、可判断、可升级、可追责**的机制。

## 技术原理（技术视角）
### 1. 核心机制：先定义信号，再定义动作
告警体系不是从“通知谁”开始，而是从“观察什么”开始。一个完整链路通常包含五层：

1. **指标采集**：持续收集服务健康信号，例如成功率、响应时长、错误率、任务失败数、队列积压量。
2. **规则判断**：把指标放进规则里判断，例如“5 分钟错误率连续超过 2%”。
3. **分级路由**：不同严重度走不同处理路径，不是所有异常都用最高优先级打人。
4. **通知与升级**：首次通知谁、多久没人处理后升级给谁，要预先定义清楚。
5. **闭环记录**：记录告警何时触发、谁接手、何时恢复、是否影响 SLA。

这里最容易被忽略的一点是，**告警是行动系统，不是消息系统**。如果只有提示，没有接手、升级和复盘，它就只是提醒音，不是真正的治理能力。

### 2. 指标采集：不要一上来就全量监控
一个常见误区是，团队一开始就想把 CPU、内存、日志、接口、业务指标全部接入，结果是指标很多，但没有主次。更合理的做法是先抓三类关键指标：

- **可用性指标**：请求是否成功，例如成功率、5xx 比例、健康检查通过率。
- **性能指标**：服务是否变慢，例如 P95 / P99 响应时间、任务平均耗时。
- **业务结果指标**：关键动作是否真的完成，例如支付成功率、导出成功率、定时任务完成率。

为什么业务结果指标重要？因为很多故障不是“服务挂了”，而是“服务能访问，但关键流程失败”。只盯系统层，会错过最影响业务体验的那部分风险。

### 3. 告警规则：阈值只是起点，持续时间更关键
很多人第一次配告警，会写成这种规则：
- 响应时间 > 2 秒就告警
- 错误率 > 1% 就告警

这类规则看起来简单，但非常容易误报。因为真实系统里偶发尖峰很常见，真正值得打人的不是“一次异常”，而是“**连续异常并持续一段时间**”。

因此，告警规则通常要同时包含三个维度：
- **阈值**：超过多少算异常；
- **时间窗口**：在多长时间内统计；
- **持续性条件**：连续几次满足才触发。

例如：
- 5 分钟窗口内 API 错误率 > 2%，连续 3 次检查仍未恢复；
- 10 分钟内任务失败数 > 20，且失败任务集中在同一工作流；
- 页面可访问，但关键下单链路成功率跌破 95%。

这种设计的价值在于，它更接近“对业务有影响的异常”，而不是“监控系统过度敏感”。

### 4. 分级与升级：P0 到 P3 不是标签，而是处理承诺
成熟的告警体系通常会做分级，例如：

- **P0**：核心服务中断，影响大面积用户或收入链路，要求立即介入。
- **P1**：关键功能严重异常，已有明显业务影响，但未全量不可用。
- **P2**：局部异常或容量风险，需要尽快处理，但短时间内可控。
- **P3**：提醒类信号或趋势性风险，用于观察和预防。

分级的本质不是为了好看，而是要让每一级对应不同处理动作：
- 谁接手；
- 多少分钟内响应；
- 多久未恢复就升级；
- 是否进入 SLA 统计；
- 是否要求形成复盘记录。

如果只有“高、中、低”三个字，没有对应动作，那么分级就是空的。

### 5. 聚合、抑制与降噪：不让团队被告警反过来管理
当一个底层故障发生时，往往会同时触发很多表面告警。例如数据库连接异常，可能带来 API 失败、任务失败、登录失败、页面超时等一串报警。如果每条都单独通知，团队很快就会进入“告警风暴”。

所以告警系统必须具备三种治理能力：

- **聚合**：把同一根因引发的多条告警合并成一个事件。
- **抑制**：某个上游故障已确认后，压制其下游重复告警。
- **静默**：在处理窗口内临时关闭重复提醒，避免值班同学被连续轰炸。

这里要强调一个判断标准，**好告警不是越多越好，而是越少越准越好**。

### 6. SLA 口径：把“稳定”从感觉变成计算
SLA（Service Level Agreement）本质上是服务承诺。常见表达方式是：
- 月度可用性 99.9%
- 核心故障 15 分钟内响应
- P1 问题 4 小时内恢复

但如果没有统一计算口径，这些承诺就会流于口号。SLA 至少要明确四件事：

1. **统计对象**：是整个系统，还是某几个核心服务。
2. **统计时间**：按月、按季度，还是按自然周。
3. **可用性定义**：是接口 5xx、页面打不开，还是关键业务失败都算不可用。
4. **排除规则**：计划维护、外部依赖故障、灰度实验是否计入。

举个例子，同样说“99.9% 可用”，如果按月算，大约只允许 43 分钟左右不可用时间。这个数字一落地，团队对故障容忍度就会立刻从模糊变具体。

### 7. OpenClaw 视角下怎么落地
在 OpenClaw 体系里，告警和 SLA 不一定是一个独立大系统，也可以由多种能力编排完成：

- `cron`：定时执行检查任务，例如每 5 分钟拉取一次健康状态或业务指标。
- `web_fetch` / `browser`：访问状态页、控制台、业务页面，获取真实运行结果。
- `exec`：执行本地诊断命令、脚本或日志采样动作。
- `message`：向指定渠道推送不同级别的告警信息。
- `write`：把事故摘要、恢复时间、影响范围写入知识库，形成复盘资料。

这意味着 OpenClaw 在这里的价值，不只是“发一条报警消息”，而是把**检查、判断、通知、记录**串成闭环。

### 8. 常见误区
#### 误区一：把系统指标当成全部真相
CPU 和内存正常，不代表用户真的能完成核心动作。只做系统监控，容易漏掉业务故障。

#### 误区二：阈值设置过于理想化
规则写得太敏感，会让人形成“反正都是误报”的心理，最终没人信告警。

#### 误区三：只定义 SLA，不定义 SLO 与运行动作
如果团队没有内部目标值、升级动作和复盘机制，SLA 就只是对外说法，难以真正驱动改进。

#### 误区四：告警触发后没有 owner
消息发出去了，但没人明确接手，等于没有真正开始处理。

## 业务翻译（业务视角）
### 这项能力解决什么问题
从业务和管理视角看，告警机制与 SLA 口径解决的是三类核心问题：

- **问题发现太晚**：用户已经投诉，团队才知道有问题。
- **服务承诺说不清**：大家都说系统“还可以”，但没有统一量化标准。
- **事故处理不成体系**：出了问题只能靠经验拉群、追人、问状态。

所以，这项能力的本质，是把“靠感觉管理稳定性”升级成“靠数据管理稳定性”。

### 为什么业务能理解并愿意使用
业务方未必关心 P95 是多少，但一定关心这些问题：
- 今天客户能不能正常用；
- 如果有问题，多久能发现；
- 发现以后，多久有人处理；
- 本月服务质量到底有没有达标。

当技术团队能把这些问题用统一口径讲清楚，业务就更愿意接受自动化运营和更高频的上线节奏，因为风险已经被显性化了。

### 提效 / 提质 / 提速 / 可控价值
- **提效**：从人工巡检升级为自动发现异常，减少“靠人盯盘”。
- **提质**：把稳定性目标量化，推动规则、流程和责任人更清楚。
- **提速**：缩短故障发现时间和升级时间，避免问题拖大。
- **可控**：用统一 SLA 口径评估服务质量，让复盘和资源投入更有依据。

## 典型场景（个人版）
1. **核心接口波动告警**  
   某个对外 API 在 10 分钟内错误率持续升高。系统先触发 P1 告警给值班负责人，如果 15 分钟未确认，再自动升级给二线负责人和管理者。

2. **定时任务失败监控**  
   每天凌晨跑的同步任务，如果连续两次失败，OpenClaw 通过 `cron + exec + message` 发出告警，并把失败日志摘要写入知识库，便于早上直接判断影响面。

3. **月度 SLA 复盘**  
   团队按月统计核心服务可用性、P1 事件次数、平均恢复时长，并形成一页式月报。这样管理者不再只听“本月比较稳”，而是能看到具体数字和波动原因。

## 管理者关注点（成本 / 效率 / 风险）
### 成本
- 初期成本主要在于梳理核心指标、分级规则、责任人和值班路径。
- 如果没有统一口径，后续每次事故都会用更高的人力成本补课。

### 效率
- 好的告警体系能显著缩短问题发现时间，减少人工巡检和重复沟通。
- 统一 SLA 月报后，管理层讨论会从“这次感觉怎么样”转成“哪个环节最拖恢复时间”。

### 风险
- 最大风险是误报太多，导致团队对告警失去信任。
- 第二个风险是只看系统指标，不看业务成功率，最后错过真实体验问题。
- 还有一个常见风险是升级链不清晰，导致告警虽然发出，但无人真正接手。

## 本日自检
1. 我能否讲清一条告警从“指标采集”走到“升级处理”的完整链路？
2. 我是否知道阈值、时间窗口和持续性条件为什么要同时存在？
3. 我能否区分 P0、P1、P2、P3 的本质差异，不只停留在名字上？
4. 我是否理解 SLA 至少要定义统计对象、统计时间、可用性定义和排除规则？
5. 我能否说清为什么“告警越多越好”其实是错误认知？

## 一句话总结
告警机制解决的是“问题能否被及时发现并快速接手”，SLA 口径解决的是“稳定性能否被量化和兑现”，两者合起来，才是可治理的服务质量体系。
