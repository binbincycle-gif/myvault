# 2026-07-10

## 今日思考

今天一个很值得继续往下做的判断：

> 自己先搭一个开源 Agent，再让这个 Agent 去接内部系统和 EZR SaaS 现有能力，看它到底能不能真正完成任务，从而反过来发现我们系统里哪些能力已经适合 Agent 调用，哪些还只是“给人点页面用的功能”。

这件事的价值，不在“又搭了一个 Agent”，而在 **借外部 Agent 的视角，反向体检 EZR 的能力开放程度**。

过去我们习惯从产品视角看系统：页面、流程、功能、角色。
但如果换成 Agent 视角，判断标准会变成另一套：

1. **有没有标准入口**：不是页面能不能点，而是能力能不能被稳定调用。
2. **有没有上下文**：Agent 是否拿得到任务上下文、业务上下文、身份上下文。
3. **有没有权限边界**：能查什么、能写什么、哪些动作必须审批。
4. **有没有结果回写**：Agent 做完事后，结果能不能进入 CRM / 业务系统形成闭环。
5. **有没有可复盘性**：一次调用做了什么、为什么成功/失败、值不值得沉淀成组织能力。

如果用这个方式去看，很多原本觉得“已经有了”的 SaaS 功能，可能并不等于 Agent 能力。页面有，不代表可调用；接口有，不代表可编排；动作能做，不代表可审计、可回滚、可复盘。

所以这件事本质上不是技术尝鲜，而是一次很好的 **能力地图体检**：

- 哪些能力已经可以变成 Skill / Tool
- 哪些能力还停留在人操作页面
- 哪些能力缺少上下文和权限模型
- 哪些能力做完后没有结果回写，闭环断掉
- 哪些能力一旦开放给 Agent，会形成真正的产品壁垒

## 这件事最值得观察的 3 个发现方向

### 1. 发现“伪能力”
很多内部功能可能只是 UI 层能力，不具备真正的 Agent 可调用性。
这能帮助我们区分：什么是 SaaS 功能，什么才是 SaaS 可释放的能力。

### 2. 发现“能力缺口”
一旦让 Agent 真去做任务，就会暴露缺什么：
- 缺统一身份
- 缺权限判定
- 缺结构化结果
- 缺任务回写
- 缺异常处理

这些缺口，比单纯画能力地图更真实。

### 3. 发现“未来产品化入口”
如果某些内部能力一旦被 Agent 顺畅调用，就说明它未来不一定只属于页面，而可能升级为：
- Skill
- Agent Tool
- 工作流节点
- 跨系统编排能力
- 面向客户开放的 AI 能力接口

这会直接影响 EZR 未来是“被 Agent 使用的 SaaS”，还是“向外输出 Skill 的 SaaS”。

## 今天这条思考，我更认可的落点

一句话收口：

> 先别急着讨论要做什么超级 Agent，先用一个开源 Agent 当探针，去压测 EZR 内部系统和 SaaS 能力的 Agent readiness。

如果这件事做得好，最后拿到的不只是一个 Demo，而是一张更真实的《EZR 可被 Agent 调用的能力地图》。

## 下一步动作

1. 先选一个最小开源 Agent 框架，不求全，只求能接 Tool / MCP / HTTP 能力。
2. 选 3 个真实业务场景做压测：例如智能导购、会员经营诊断、AI Coding 辅助测试。
3. 每跑一个场景，都按 5 个维度复盘：入口、上下文、权限、回写、复盘。
