# CRM中可被Agent调用的能力建设方案（分步推进版）

## 一、方案目标

当前我们已经完成了 CRM 中**报表获取、取数导出**的初步能力，这证明 CRM 已经具备被 Agent 调用的基础入口。

但如果后续只停留在“查数”和“导数”，CRM 对 Agent 的价值会很快见顶。下一步要推动的，不是继续堆查询接口，而是把 CRM 从**数据系统**升级为**可被 Agent 调用的经营操作系统**。

本方案的目标是：

1. 让 Agent 不只是“查数据”，还能理解经营问题。
2. 让 Agent 不只是“给答案”，还能给建议、推动动作。
3. 让 Agent 的动作最终回到 CRM，形成结果闭环。
4. 让整个能力具备权限、审计、可控、可复制的产品化基础。

---

## 二、核心判断

CRM 能力要按下面这条链路建设，而不是按单点功能建设：

**查询 → 诊断 → 策略 → 动作 → 回写 → 权限审计**

如果只做查询，Agent 只是 AI 版 BI；如果做到策略和动作，CRM 才会变成 AI 时代的经营中台。

---

## 三、建设原则

### 1. 先闭环，后铺量
先打透 1-2 个真实场景闭环，不要一开始铺满 CRM 全模块。

### 2. 先高频，后全面
优先做高频、可复用、能体现经营价值的能力，不先追求全覆盖。

### 3. 先建议，后自动执行
涉及营销触达、客户数据、经营动作，前期优先“建议式 Agent”，不要过早自动执行。

### 4. 先能力地图，后产品化
先梳理 CRM 中哪些能力值得被 Agent 调用，再做成稳定接口、Skill、工作流。

---

## 四、总体推进路径

---

## 阶段一：先把“查数能力”升级成“经营对象查询能力”

### 目标
从现在的报表获取、导出取数，扩展成 Agent 可以围绕经营问题完整补上下文。

### 要做的事

#### 1. 梳理 CRM 中可查询的核心经营对象
先统一对象模型：
- 会员
- 导购
- 门店
- 商品
- 活动
- 订单/交易
- 人群包
- 报表
- 指标

#### 2. 定义每类对象对 Agent 的最小查询集

**会员**
- 基础信息
- 最近消费
- 最近触达
- 最近到店
- 最近跟进
- 标签/分层
- 沉默时长

**导购**
- 负责会员数
- 近7日跟进数
- 成交数
- 转化率
- 高价值客户维护情况

**门店**
- 客流
- 成交
- 复购
- 活动表现
- 导购表现

#### 3. 补“上下文查询”而不只是“结果查询”
比如不要只给“本月销售额”，还要能补：
- 同比环比
- 哪些会员贡献
- 哪些导购贡献
- 哪些活动影响
- 哪些商品拉动

### 本阶段交付物
- CRM 可查询对象清单
- 每个对象的最小查询字段清单
- 面向 Agent 的统一查询能力清单 V1

### 阶段验收标准
- Agent 能围绕一个经营问题，把关键上下文补齐。
- 不再只依赖“导出 Excel 再人工分析”。

---

## 阶段二：补“诊断能力”，让 Agent 能回答为什么

### 目标
让 Agent 不只返回结果，还能解释问题。

### 要做的事

#### 1. 先选 3 类最值得做的经营诊断问题

**A. 会员经营诊断**
- 为什么沉默会员没有被激活
- 为什么高潜会员没有转化
- 为什么老客复购下降

**B. 导购经营诊断**
- 为什么导购触达多但成交低
- 为什么高价值客户维护不够
- 为什么门店导购动作不均衡

**C. 营销经营诊断**
- 为什么曝光高点击低
- 为什么加购高成交低
- 为什么活动响应低

#### 2. 给每类诊断定义标准分析框架
每个诊断至少要拆成：
- 看什么数据
- 用什么口径
- 如何归因
- 输出哪些结论
- 有哪些置信度边界

#### 3. 输出标准诊断结果结构
统一成：
- 现象
- 可能原因
- 关键证据
- 建议下一步动作
- 风险提示

### 本阶段交付物
- 经营诊断问题清单 V1
- 每类诊断的分析逻辑清单
- 标准诊断输出模板

### 阶段验收标准
- Agent 可以对真实经营问题给出可读、可信、可追溯的解释。
- 管理者看完能判断下一步怎么做。

---

## 阶段三：补“策略能力”，让 Agent 给出经营建议

### 目标
让 Agent 从“解释问题”走到“建议怎么干”。

### 要做的事

#### 1. 先围绕 3 个高价值场景做策略能力

**场景一：沉默会员唤醒**
Agent 要能输出：
- 哪批会员值得唤醒
- 为什么这批值得先做
- 建议什么内容
- 适合谁来跟进
- 适合什么时间触达

**场景二：导购跟进助手**
Agent 要能输出：
- 今日该跟进谁
- 跟进优先级
- 跟进理由
- 推荐话术
- 预期目标

**场景三：营销活动优化**
Agent 要能输出：
- 哪类人群适合触达
- 哪类商品适合推荐
- 哪个节点适合推送
- 哪条策略值得做 AB 测试

#### 2. 建立建议生成的约束规则
比如：
- 是否允许直接推荐优惠
- 是否允许自动生成触达内容
- 是否必须带依据说明
- 是否必须说明风险边界

#### 3. 把“建议”做成可产品化输出
不要只是聊天回答，要做成：
- 推荐名单
- 建议卡片
- 策略草案
- 待办清单
- 复盘建议

### 本阶段交付物
- 三个策略场景模板
- 策略建议输出结构
- 建议与依据绑定规则

### 阶段验收标准
- Agent 建议能够被业务看懂、愿意采纳。
- 建议不是空话，而是可执行动作。

---

## 阶段四：补“动作能力”，让 Agent 推动事情发生

### 目标
从“建议式 Agent”逐步走到“可执行 Agent”。

### 要做的事

#### 1. 先做低风险动作
建议优先：
- 生成人群包草案
- 生成导购待办清单
- 生成营销任务草案
- 生成日报/周报/复盘草稿
- 创建预警提醒

#### 2. 暂不直接开放高风险自动动作
前期谨慎对待：
- 自动发营销
- 自动大批量触达
- 自动修改客户数据
- 自动创建正式经营策略

先走：
**Agent 生成 → 人工确认 → 执行**

#### 3. 建立动作链路
每个动作要明确：
- 谁触发
- 谁确认
- 谁执行
- 执行结果回哪里
- 异常怎么中止

### 本阶段交付物
- 可开放动作清单 V1
- 高风险动作管控清单
- Agent 动作审批流设计

### 阶段验收标准
- Agent 能推动业务进入下一步，而不是停在建议。
- 关键动作可控、可回滚、可追踪。

---

## 阶段五：补“回写能力”，形成结果闭环

### 目标
让 Agent 的建议和动作最终回到 CRM，形成学习闭环。

### 要做的事

#### 1. 定义哪些结果必须回写
例如：
- 是否已触达
- 是否已跟进
- 是否有回复
- 是否到店
- 是否成交
- 是否复购

#### 2. 定义哪些过程要回写
例如：
- Agent 给了什么建议
- 人有没有采纳
- 为什么没采纳
- 执行过程中遇到什么问题
- 最终效果如何

#### 3. 支持后续复盘和优化
回写不是留痕，而是为了复盘：
- 哪类建议最有效
- 哪类人群最容易转化
- 哪类导购动作最有效
- 哪类内容容易无效或打扰用户

### 本阶段交付物
- Agent 回写字段清单
- 结果回写模型
- 闭环复盘指标清单

### 阶段验收标准
- Agent 输出可以进入 CRM 业务闭环。
- 能持续优化，不是一次性智能回答。

---

## 阶段六：补“权限与审计能力”，形成可上线基础

### 目标
保证 Agent 调用 CRM 时，安全、可控、可审计。

### 要做的事

#### 1. 权限分层
明确：
- 谁能看什么数据
- 谁能导出什么数据
- 谁能触发什么动作
- 谁能回写什么结果

#### 2. 动作审计
记录：
- Agent 查了什么
- Agent 生成了什么建议
- Agent 触发了什么动作
- 谁批准了动作
- 动作结果如何

#### 3. 风险边界
至少要有：
- 敏感数据脱敏
- 越权拦截
- 频控限制
- 人工确认
- 回滚机制

### 本阶段交付物
- Agent 权限模型
- 审计日志模型
- 风险控制清单

### 阶段验收标准
- Agent 不会绕过 CRM 权限体系。
- 关键动作有证据链和责任链。

---

## 五、优先打透的 3 个样板场景

### 样板一：智能问数
路径：
**问数 → 解释 → 建议**

目标：
先让管理层看到 AI 不只是查报表，而是能辅助经营判断。

### 样板二：沉默会员唤醒
路径：
**识别 → 推荐名单 → 触达建议 → 跟进 → 回写**

目标：
打透一个“会员经营闭环”的样板。

### 样板三：导购跟进助手
路径：
**今日跟进名单 → 跟进理由 → 建议话术 → 跟进结果回写**

目标：
打透一个“导购动作闭环”的样板。

---

## 六、分阶段推进节奏建议

### 第一步（当前-30天）
重点：
- 梳理能力地图
- 做查询层和诊断层 V1
- 跑通智能问数样板

### 第二步（30-90天）
重点：
- 做策略能力
- 打通沉默会员唤醒样板
- 开始设计动作与回写

### 第三步（90-180天）
重点：
- 开放低风险动作
- 打通导购跟进闭环
- 建立权限与审计体系
- 形成可复制的 CRM Agent 能力底座

---

## 七、推进组织建议

### 产品经理
- 做能力地图和场景优先级
- 定义输出结构与产品边界

### 技术/架构
- 做接口、工作流、回写、审计底座
- 定义 Agent 调用方式与能力协议

### 数据团队
- 定义指标口径、诊断逻辑、效果评估
- 支持回写后的复盘分析

### 业务/运营/CSM
- 提供真实场景
- 参与样板共建
- 验证建议是否可执行、是否有价值

---

## 八、主要风险

### 1. 只做查询，不做闭环
最后会变成“AI 查数工具”，价值上不去。

### 2. 场景铺太多
每个都做一点，最后没有一个真样板。

### 3. 动作先行，治理滞后
没有权限、审计、频控，越往后风险越大。

### 4. 只站在系统视角，不站在经营视角
最后做出一堆接口，不解决真实业务问题。

---

## 九、建议现在就做的 3 个动作

### 动作1
先拉一张表：
**CRM 现有能力清单 → 哪些可查、哪些可诊断、哪些可建议、哪些可执行、哪些可回写**

### 动作2
从“智能问数、沉默会员唤醒、导购跟进助手”里，先选 1 个作为最近样板。

### 动作3
组织一次小范围对齐会，把产品、技术、数据、业务拉齐，明确：
- 第一批不做什么
- 第一批一定做成什么
- 用什么标准验收

---

## 十、一句话收口

先别急着把 CRM 做成“什么都能干的 Agent 平台”，先打透 1-2 个真实经营闭环样板。只要能把**查询 → 诊断 → 建议 → 动作 → 回写**跑通，CRM 在 AI 时代的产品形态就会开始真正变掉。
