# AI Coding平台演进路线图：从Task到Agent原生组织

> 原图：![[附件/AI-Coding平台演进路线图-2026-06-22.jpg]]

## 一句话结论

AI Coding 平台建设不能停留在“工具集合”，而要分三阶段演进：

1. **基础能力建设**：统一入口，沉淀 Skill、MCP、CodeWiki 和平台治理能力。
2. **基于 Task 的建设**：围绕需求、缺陷、技术改造等任务，形成标准化、可编排、可追踪的交付流水线。
3. **Agent 原生组织**：以多个研发 Agent 协同完成需求理解、方案设计、开发、测试、修复、发布和运维，最终推动研发组织智能化。

核心变化是：

> 从“AI 辅助个人写代码”，升级为“AI 参与任务交付”，最终升级为“Agent 原生研发组织”。

#### 2. Skill 平台

- Skill 市场
- Skill 开发工具
- Skill 模板库
- 版本管理
- 权限管理
- 使用统计

#### 3. MCP 服务中心

- GitLab MCP
- 玄武 MCP
- 脚本中心 MCP
- 数据库 MCP
- 跳转中心 MCP
- 禅道 / 测试 MCP

#### 4. CodeWiki / 知识中心

- 项目 Wiki
- 架构文档
- API 文档
- FAQ / 最佳实践
- 历史方案库
- 事故复盘库

#### 5. 平台管理中心

- 用户管理
- 权限管理

- 模型管理

## 第二阶段：基于 Task 的建设（3-12个月）

### 目标

构建可复用、可编排的 Task 体系，形成标准化交付流水线。

### 核心价值

- 流程标准化
- 交付自动化
- 过程可追踪
- 效率与质量同步提升

### Task 来源

- 玄武需求管理：需求、任务、变更

- 技术需求
- 技术改造

- 测试用例生成

- 回归用例

#### 5. Task 代码 Review

- 代码规范检查
- 安全检查
- 性能检查

#### 6. Task 发布检查

- 脚本检查
- 配置检查
- 依赖检查

### 支撑能力

- Task 模板库
- 流程编排引擎
- 状态跟踪引擎
- 消息通知与协作
- 结果可视化

- 标准化 Task 体系

- 人才培养体系：能力模型、认证

## 管理判断

这张图真正有价值的地方，不是画了一个 AI Coding 平台，而是把 AI Coding 的建设重心从“个人工具提效”拉到了“组织交付体系重构”。

### 关键判断一：第一阶段不是终点

Skill、MCP、CodeWiki、平台入口只是基础设施。如果只停留在工具建设，价值会被限制在个人效率提升。

### 关键判断二：第二阶段 Task 体系是关键拐点

只有围绕 Task 建设标准交付流水线，AI Coding 才能真正进入研发主流程。

这一步决定 AI 是“辅助工具”，还是“交付系统的一部分”。

### 关键判断三：第三阶段是组织形态变化

Agent 原生组织不是简单多几个智能体，而是研发组织从“人驱动流程”变成“目标驱动 + Agent 协同 + 人负责判断和兜底”。

## 下一步可执行动作

1. **先定义 Task 标准对象**
   - 明确需求、缺陷、技术改造、线上问题在 AI Coding 平台中的统一 Task 数据结构。

2. **优先打通 2 条标准流水线**
   - 需求 → 技术方案 → 开发 → 测试用例 → 发布检查。
   - 线上 Bug → 根因分析 → 修复建议 → 回归用例 → 复盘沉淀。

3. **沉淀第一批 Skill / MCP 清单**
   - 需求分析 Skill
   - 技术方案评审 Skill
   - 测试用例生成 Skill
   - Bug 根因分析 Skill
   - 发布检查 Skill
   - GitLab / 玄武 / 禅道 / 脚本中心 MCP

4. **同步设计治理底座**
   - 权限、审计、成本、模型选择、敏感数据边界必须从第一阶段开始设计。

---

## 风险提醒

1. **不要把 AI Coding 平台做成工具门户**
   - 工具门户只能提升使用便利性，不能重构交付效率。

2. **不要跳过 Task 体系直接做 Agent**
   - 没有 Task 标准对象和流程数据，Agent 协同会缺少稳定上下文。

3. **不要忽视组织机制**
   - AI Coding 的落地不是技术问题，而是研发流程、责任边界、评价方式和知识沉淀方式的变化。

4. **不要只看代码生成效率**
   - 真正应该看端到端交付周期、缺陷逃逸率、人工干预率和组织资产沉淀率。
