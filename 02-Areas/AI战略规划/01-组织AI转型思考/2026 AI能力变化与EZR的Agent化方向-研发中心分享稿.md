# 2026 AI 能力变化与 EZR 的 Agent 化方向

> 研发中心内部分享稿 V3  
> 核心主线：未来拉开差距的，不只是模型能力，而是谁能把个人经验、SaaS 能力、业务数据和行业知识，沉淀成可持续进化的 Agent。

---

## 一、开场：我今天想讲的不是 AI 工具，而是一次工作方式和产品方式的变化

今年大家都在用 AI。

有人用它写代码，有人用它查资料，有人用它生成测试用例，有人用它写文档、总结会议、整理方案。

这些都很好，但如果只停留在“用 AI 提效”，我们其实还没有抓住今年 AI 变化的核心。

我今年越来越明确一个判断：

> AI 的变化，不只是让我们工作更快，而是让软件、数据、知识和人的经验，都可以被 Agent 重新组织。

所以今天我想讲四个变化：

1. **工作方式变化：从 Chat 框，到打造自己的 Agent。**
2. **SaaS 功能变化：从功能页面，到 Agent 可识别、可调用的 Skill。**
3. **数据价值变化：从有数据，到 AI 能理解的数据。**
4. **知识库体系变化：从文档仓库，到行业智能体的上下文。**

这四个变化放在一起，就是 EZR 接下来 Agent 化的方向。

---

## 二、第一件事：工作方式变了——从 Chat 框到自己的 Agent

年初我们更多是在用 Chat 框。

Chat 框解决的是单次问题：

- 我问一句；
- AI 答一句；
- 我再补充背景；
- AI 再继续生成。

这种方式能提效，但它的问题也很明显：

- 上下文是临时的；
- 每次都要重新解释；
- AI 不一定了解你的项目；
- 你的经验没有持续沉淀；
- 它更像一个临时助手，而不是长期搭档。

从年初的龙虾、小龙虾，到现在 Codex 智能体，我感受到的变化越来越明显：

> 真正有价值的，不是一次性问答，而是持续迭代出来的个人 Agent。

### 1. 为什么个人 Agent 会越来越重要

一个好的 Coding Agent，会在持续使用中越来越了解你：

- 了解你的代码风格；
- 了解你的业务模块；
- 了解你的项目上下文；
- 了解你的判断标准；
- 了解你常踩的坑；
- 了解你希望它怎么输出结果。

它不是简单替你写代码，而是在逐步变成你的研发搭档。

### 2. 未来差距来自你的 Agent 有多强

过去研发之间的差距，主要来自：

- 技术基础；
- 业务理解；
- 架构能力；
- 跨端经验；
- 排查问题能力。

这些能力未来依然重要，但会叠加一个新的变量：

> 你的 Agent 有多强。

一个强 Agent 会放大你的能力：

- 后端同学可以更快理解前端链路；
- 前端同学可以更快追踪接口和数据流；
- 测试同学可以基于代码改动生成测试建议；
- 新人可以通过上下文包快速理解历史业务；
- 老员工可以把自己的经验沉淀给 Agent，减少重复解释。

所以未来拉开差距的，不只是“谁更会写提示词”，而是：

> 谁能把自己的业务经验、代码经验、判断标准和复盘沉淀，持续喂给自己的 Agent。

### 3. 这里有一个边界：不是每个人各玩各的工具

我希望大家打造自己的 Agent，但这不是各自为战。

正确方向应该是：

```text
个人 Agent 持续积累个人上下文
+ 团队沉淀统一知识库
+ 公司沉淀通用 Skill
+ 平台提供权限、审计、规范
= 可复制、可治理的 AI 协作能力
```

如果每个人只是自己玩工具，最后会变成新的信息孤岛。  
如果个人 Agent 和团队知识库、Skill 体系打通，才会变成组织能力。

## 三、第二件事：SaaS 功能变了——从功能页面到 Agent 可识别的能力

过去 SaaS 的产品设计，是面向人操作系统。

我们会设计：

- 菜单；
- 页面；
- 列表；
- 表单；
- 筛选；
- 按钮；
- 流程跳转。

对应的接口，也大多是服务页面的。

比如：

- 页面要展示什么；
- 按钮要提交什么；
- 列表要筛选什么；
- 表单要保存什么。

这套方式在过去是对的，因为用户是通过页面使用 SaaS。

但 Agent 时代，使用方式会变。

过去是：

```text
人打开 SaaS → 找页面 → 看数据 → 判断 → 操作
```

未来会越来越多变成：

```text
人提出目标 → Agent 理解任务 → 调用 SaaS 能力 → 输出建议 / 动作 / 复盘
```

这意味着，SaaS 的能力不能只藏在页面里，而要变成 Agent 可识别、可调用、可组合的能力。

### 1. 页面不是 Skill，业务动作才是 Skill

这是一个很关键的判断：

> 页面不是 Skill，业务动作才是 Skill。

会员列表不是 Skill。  
识别高潜会员才是 Skill。

订单报表不是 Skill。  
诊断复购下降原因才是 Skill。

营销活动页面不是 Skill。  
生成触达策略才是 Skill。

导购任务列表不是 Skill。  
判断今天该跟进谁、推荐什么、怎么说，才是 Skill。

### 2. 面向智能体的 Skill 要具备 6 个特征

一个真正面向 Agent 的 Skill，不能只是 API 包一层，也不能只是功能换个名字。

它至少要具备 6 个特征：

1. **原子性**  
   不是技术接口越小越好，而是业务动作要清楚。  
   例如“识别高潜会员”比“查询会员列表”更适合成为 Skill。

2. **输入输出明确**  
   Agent 知道需要传什么上下文，也知道会得到什么结果。

3. **业务语义清楚**  
   Skill 名称和输出要能被业务理解，而不是只有研发能看懂。

4. **AI 可操作**  
   Agent 能判断什么时候调用、怎么调用、调用后如何继续下一步。

5. **权限边界明确**  
   能看什么数据、能不能执行动作、是否需要人工确认，必须清楚。

6. **结果可追踪**  
   调用后有没有产生业务效果，要能记录、复盘和优化。

### 3. EZR 要放大 SaaS 能力，而不是只增加 AI 页面

我们过去沉淀了会员、导购、营销、交易、数据分析、客户经营能力。

如果这些能力只是页面功能，Agent 很难直接使用。  
如果这些能力被 Skill 化，Agent 就可以把它们组合成业务流程。

所以 EZR 的 Agent 化，不是每个模块加一个聊天框，而是：

> 把 SaaS 里原来面向人的功能，重构成面向 Agent 的经营能力。

## 四、第三件事：数据的魅力——从有数据，到 AI 能理解的数据

很多公司都有数据，但不是所有数据都能被 AI 用起来。

真正的差别不是“有没有数据”，而是：

> 数据有没有被定义成 AI 能理解、能推理、能生成行动建议的上下文。

### 1. 1.0 阶段：SaaS 定义指标

现阶段我们能做的 AI 取数，更多是基于 SaaS 已经定义好的指标。

比如：

- 复购率；
- 客单价；
- 连带率；
- 会员活跃度；
- 沉默会员数；
- 券核销率；
- 导购触达率；
- 门店销售变化。

这一步有价值，因为它让用户可以用自然语言访问经营数据。

但本质上还是：

> SaaS 定义指标，品牌使用指标。

### 2. 2.0 阶段：品牌定义指标，AI 理解规则并生成查询

未来更有冲击力的是：

> 品牌可以定义自己的经营指标，AI 根据规则理解并生成 SQL / 查询计划。

比如品牌会说：

- 我们定义的高价值会员，不只是累计消费高，还要最近 90 天有互动；
- 我们定义的沉默风险，不是统一 180 天未购，而是结合品类购买周期和导购触达；
- 我们定义的门店机会，不只是销售下降，还要结合库存结构、会员池质量和导购执行；
- 我们定义的有效触达，不只是发了消息，还要看后续行为。

这时候 AI 的价值就不只是查数，而是理解品牌自己的经营语言。

未来链路可能是：

```text
品牌经营规则
→ AI 理解指标定义
→ 生成 SQL / 查询计划
→ SaaS 权限与口径校验
→ 输出结果解释
→ 生成经营建议
→ 沉淀为品牌指标资产
```

### 3. 这件事的价值很大，但边界也必须清楚

品牌定义指标 + AI 生成 SQL，这个方向很有想象力，但不能裸奔。

必须有几条底线：

- 权限校验：不同角色只能看自己权限内的数据；
- 指标口径校验：不能让 AI 随意解释核心经营指标；
- SQL 审计：AI 生成的查询必须可追踪、可回放；
- 成本控制：复杂查询不能拖垮生产系统；
- 结果解释：输出结论必须带口径和依据。

所以数据智能的关键，不只是 AI 生成 SQL，而是形成一套：

```text
指标定义
+ 权限控制
+ 查询生成
+ 口径校验
+ 结果解释
+ 经营建议
```

这才是真正可交付的数据智能能力。

一句话：

> 不是有数据就有智能，而是数据能被 AI 理解、被规则约束、被业务验证，才会变成智能。

## 五、第四件事：知识库体系——没有语境和上下文的 AI 没有灵魂

AI 很强，但如果没有行业语境和上下文，它给出的建议往往是泛的。

它可以讲很多正确的话，但不一定能解决品牌今天的问题。

SaaS 行业知识，是我们深耕这么多年最重要的护城河之一。

### 1. 行业智能体不能只靠模型

零售 CRM 场景里，有很多通用模型天然不知道的东西：

- 品牌怎么做会员经营；
- 导购为什么不愿意触达；
- 门店为什么执行不到位；
- 活动为什么热闹但不带来复购；
- 标签为什么打了没人用；
- 哪些经营建议客户听得懂；
- 哪些功能看起来完整但一线不会用；
- 哪些项目风险在需求阶段就已经埋下。

这些知识不是模型参数里天然可靠存在的。

### 2. 知识库不是文档仓库，而是 Agent 的业务语境

我们要建设的知识库，不只是放文档。

它应该沉淀：

- 行业案例；
- 客户经营问题；
- 项目复盘；
- 指标解释；
- 业务规则；
- 最佳实践；
- 失败原因；
- 话术模板；
- 解决方案；
- 客户成功经验。

这些内容与 SaaS 数据、Skill 能力结合，才可能形成真正的行业智能体。

### 3. 这是 EZR 的优势

通用 AI 公司有模型优势，但它不一定懂服饰零售品牌的真实经营链路。

EZR 的优势是：

- 服务过大量服饰零售品牌；
- 理解会员、导购、私域、营销、交易闭环；
- 有真实 SaaS 数据；
- 有客户成功和交付经验；
- 有行业案例；
- 知道什么建议客户真的能执行。

所以 EZR 要做的不是普通 AI 助手，而是：

```text
大模型能力
+ EZR SaaS 数据
+ EZR Skill 能力
+ 行业知识库
+ 客户案例上下文
+ 反馈闭环
= 零售经营智能体
```

一句话：

> 有 AI 没有上下文，只是聪明；有行业知识和业务语境，才可能真的懂经营。

## 六、把四件事合起来：EZR 的 Agent 化方向

这四个变化最终指向同一个方向：

> EZR 要从 SaaS 功能系统，走向 Agent 时代的零售经营能力平台。

过去我们的系统更多是：

```text
人打开 SaaS
→ 找功能
→ 看数据
→ 做判断
→ 执行动作
```

未来我们要逐步变成：

```text
人提出经营目标
→ Agent 理解任务
→ 调用 EZR Skill
→ 读取 SaaS 数据与知识库上下文
→ 输出策略 / 动作 / 复盘
→ 回写结果
→ 持续优化
```

这里面有三个关键角色。

### 1. Agent 平台：负责理解、编排和控制

它解决：

- 用户要完成什么任务；
- 任务要拆成几步；
- 调用哪些 Skill；
- 使用哪些上下文；
- 哪些动作需要权限；
- 哪些结果要记录；
- 出错后怎么回退。

### 2. Skill：负责封装 SaaS 经营能力

例如：

- 会员机会识别 Skill；
- 商品推荐 Skill；
- 导购话术 Skill；
- 复购下降诊断 Skill；
- 活动效果复盘 Skill；
- 客户风险识别 Skill；
- AI Coding 测试用例 Skill。

### 3. App 智能体：负责面向角色交付结果

例如：

- 导购智能体；
- 店长智能体；
- 运营智能体；
- 客户成功智能体；
- 管理者智能体；
- 研发 Coding Agent。

整体关系是：

```text
App 智能体承接用户场景
→ Agent 平台理解和编排
→ 调用 SaaS Skill
→ 使用数据和知识库上下文
→ 输出结果并反馈
```

## 七、建议先打两个样板

Agent 化不能一开始摊太大。

我建议先打两个样板：一个对内，一个对外。

### 样板一：研发 Coding Agent

目标：让每个人开始打造自己的 Coding Agent。

最小闭环：

```text
需求 / Bug / 改动点
→ Agent 理解业务上下文
→ 分析代码影响范围
→ 生成开发建议
→ 生成测试建议
→ 复盘问题与知识沉淀
```

价值：

- 提升跨端理解能力；
- 提升跨业务理解能力；
- 降低新人上手成本；
- 把个人经验沉淀成团队上下文；
- 提升开发到测试的确定性。

### 样板二：导购智能体

目标：让 EZR 的会员、商品、导购、交易能力被 Agent 调用。

最小闭环：

```text
识别机会会员
→ 生成推荐理由
→ 推荐商品组合
→ 生成导购话术
→ 记录触达结果
→ 沉淀未成交原因
→ 反哺会员画像和推荐策略
```

价值：

- 离一线近；
- 离交易结果近；
- 闭环清楚；
- 客户容易感知价值；
- 能验证 SaaS Skill 化是否成立。

## 八、研发中心接下来要怎么变

### 1. 开发：从写功能，到设计 Agent 可调用能力

以后做需求时，不只问页面怎么做，还要问：

- 这个能力能不能被 Agent 调用？
- 输入输出是否稳定？
- 权限边界是否清楚？
- 是否具备业务语义？
- 调用结果能否追踪？
- 以后能不能被别的智能体复用？

### 2. 测试：从测页面，到测智能体链路

以后测试不只是测按钮和流程，还要测：

- Agent 是否理解错任务；
- Skill 输入输出是否稳定；
- 权限是否越界；
- 指标口径是否正确；
- 异常能否解释；
- 结果能否复盘。

### 3. 产品：从提功能，到定义闭环

以后提 AI 需求，不能只说“加一个智能助手”。

必须说清：

- 目标角色是谁；
- 业务场景是什么；
- 一期最小闭环是什么；
- 要调用哪些 Skill；
- 成功指标是什么；
- 风险边界是什么。

### 4. 管理者：从任务传递，到结果编排

AI 时代，管理者不能只做传声筒。

更重要的是：

- 定义目标；
- 拆解问题；
- 编排资源；
- 控制风险；
- 推动闭环；
- 复盘沉淀。

---

## 九、今年技术中心建议抓三条主线

### 主线一：每个人打造自己的 Agent

不是停留在 Chat 框，而是持续沉淀自己的：

- 业务上下文；
- 项目经验；
- 代码理解；
- 测试方法；
- 输出标准；
- 复盘经验。

未来差距会越来越体现在：

> 你的 Agent 是否比别人更懂你、更懂业务、更能跨边界解决问题。

### 主线二：SaaS 能力 Skill 化

把会员、导购、营销、交易、数据能力逐步拆成 Agent 可调用 Skill。

核心不是多做 AI 页面，而是让 SaaS 能力被智能体放大。

### 主线三：知识库 + 数据 + Skill 打通

真正的行业智能体，不能只有模型。

必须打通：

```text
业务数据
+ 指标规则
+ 行业知识库
+ 客户案例
+ SaaS Skill
+ Agent 编排
```

## 十、风险底线

Agent 化不能变成 AI 乱调用系统。

必须守住几条底线：

1. **没有权限识别，不做生产调用。**
2. **没有指标口径，不输出经营结论。**
3. **没有审计日志，不做关键动作。**
4. **没有人工确认，不自动执行高风险营销动作。**
5. **没有反馈闭环，不算智能体场景跑通。**
6. **没有统一知识库和 Skill 规范，个人 Agent 不能沉淀为组织能力。**

## 十一、最后收口

我对今年 AI 变化的判断，可以压成三句话：

### 第一句：对个人

> 未来拉开差距的，不只是你会不会用 AI，而是你的 Agent 有多强。

### 第二句：对产品

> 未来拉开差距的，不只是 SaaS 有多少功能，而是这些功能能不能被 Agent 识别、调用、组合和复盘。

### 第三句：对公司

> 未来拉开差距的，不只是我们有没有数据和知识，而是能不能把数据、知识、经验和 Skill 组织成真正懂零售经营的行业智能体。

过去 15 年，EZR 帮助品牌把经营流程数字化。  
接下来，我们要帮助品牌把经营能力 AI 化。

研发中心不能只做功能交付团队，而要成为 EZR Agent 化能力的建设者。

# PPT 结构建议

## Slide 1：标题
2026 AI 能力变化与 EZR 的 Agent 化方向

## Slide 2：今天不是 AI 工具培训
讲的是工作方式、产品方式、数据方式、知识体系的变化。

## Slide 3：核心判断
AI 不只是让工作更快，而是重新组织软件、数据、知识和人的经验。

## Slide 4：变化一：工作方式
从 Chat 框到自己的 Agent。

## Slide 5：为什么个人 Agent 会拉开差距
Agent 越懂你，越能跨业务、跨端、跨流程协作。

## Slide 6：个人 Agent 不是各玩各的
个人上下文 + 团队知识库 + 公司 Skill + 平台治理。

## Slide 7：变化二：SaaS 功能
从功能页面到 Agent 可识别能力。

## Slide 8：页面不是 Skill，业务动作才是 Skill
会员列表 vs 识别高潜会员；报表 vs 诊断经营问题。

## Slide 9：面向智能体的 Skill 六要素
原子性、输入输出、业务语义、AI 可操作、权限边界、结果追踪。

## Slide 10：变化三：数据价值
从有数据到 AI 能理解的数据。

## Slide 11：指标 1.0 到 2.0
SaaS 定义指标 → 品牌定义指标，AI 根据规则生成查询。

## Slide 12：数据智能的安全边界
权限、口径、SQL 审计、成本控制、结果解释。

## Slide 13：变化四：知识库体系
没有语境和上下文的 AI 没有灵魂。

## Slide 14：EZR 的行业智能体公式
模型 + SaaS 数据 + Skill + 行业知识库 + 客户案例 + 反馈闭环。

## Slide 15：Agent 平台 × Skill × App 智能体
三者分工与整体链路。

## Slide 16：两个打样场景
研发 Coding Agent；导购智能体。

## Slide 17：研发中心要怎么变
开发、测试、产品、管理者分别变化。

## Slide 18：今年三条主线
每个人打造 Agent；SaaS Skill 化；知识库 + 数据 + Skill 打通。

## Slide 19：风险底线
权限、口径、审计、人工确认、反馈闭环、组织沉淀。

## Slide 20：结束语
未来差距来自个人 Agent、SaaS 可调用能力、行业智能体上下文。
