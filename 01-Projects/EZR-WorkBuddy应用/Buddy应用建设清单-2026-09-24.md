# EZR WorkBuddy Buddy 应用｜建设清单

- 版本：2026-09-24
- 依据：《WorkBuddy 开放平台 · Buddy 应用》官方文档 + 两包已有资产实测
- 目标：把 EZR 全域 CRM 能力封装成 WorkBuddy 的垂直行业 Buddy 应用（AI Harness），用户打开即进入零售品牌经营工作台

## 一、必须先建立的认知（决定后面怎么做）

Buddy 应用**不是从零造 AI 产品，而是造配置**。WorkBuddy 提供框架与 AI 底座（多 Agent 协同、上下文压缩、记忆、工具编排、安全权限），EZR 只需把行业 Know-How 装进 6 个可自定义维度：

| 维度 | EZR 要填什么 |
|---|---|
| 工作模式 | 零售经营各角色的 System Prompt + 预绑定技能 |
| 场景胶囊 | 输入框上方的高频快捷任务入口 |
| 模型配置 | 从平台模型池勾选并排序、指定默认模型 |
| 垂直行业市场 | 应用内可见的技能 / 专家 / 连接器 / 灵感案例 |
| 内嵌已有功能 | MCP Apps —— 把 EZR CRM 接进来 |
| 底层能力 | WorkBuddy 提供，无需自建 |

## 二、已有资产盘点（实测结论）

### 已就绪：连接器包 `ezr-crm 3`
- `connector-meta.json`：名称「EZR 全域CRM」，type=mcp，version 1.0.1，minWorkbuddyVersion 4.24.0，含中英文描述与各 7 条示例问法 ✅
- `mcp.json`：streamableHttp → `https://skillsgateway-tp.ezrpro.com/ezr/mcp`，timeout 30000 ✅
- `icon.svg`：140×140 EZR logo ✅（注意：这是**连接器市场图标**，不是 Buddy 应用 icon，两者规范不同）
- `skills/ezr-crm-brand-operator/SKILL.md`：工具使用说明，覆盖 64 个 MCP 工具 ✅

### 已就绪：技能包 `aggregated-skills-collection`
- 1 个路由主技能 `ezr-crm-suite` + 14 个子技能（经营报告、专题报告、会员/销售/营销/企微/分销/商品分析、四类快速查询、两类导出）✅
- 每个子技能含 `references/api-endpoints.md` + `best-practices.md`，两份报告类含 `templates/report.html` ✅
- 已验证：无硬编码 Token / 密钥 ✅；主技能引用的 14 个子技能目录**全部存在** ✅
- 待清理：3 个 `.DS_Store` / `__MACOSX` 垃圾文件 ⚠️

### 关键技术验证（本次实测通过）
- MCP 端点未带 Token 返回 **401**，`WWW-Authenticate` 指向 OAuth 保护资源元数据 ✅
- `/.well-known/oauth-protected-resource` → 200，scope 含 `ezr.crm.read` ✅
- `/.well-known/oauth-authorization-server` → 200，具备 authorize / token / register / revoke / jwks，支持 PKCE S256 ✅
- `/oauth/register`（RFC 7591 动态客户端注册）→ **201 成功**，token_endpoint_auth_method 支持 `none` ✅
- 结论：EZR 侧是**自带 OAuth 授权服务器的 MCP**，完全匹配 WorkBuddy 内置 OAuth 管理器（OAuth 2.1 + PKCE、公共客户端、无需 client_secret）的自动接入流程

## 三、待办清单

### A. 平台准入（前置，最容易被卡）
1. 注册并入驻 WorkBuddy 开放平台
2. 完成**开发者 / 企业资质认证**
3. 创建「应用」业务类型 → 填写基础信息 → **提交创建审核**（通过后才进入草稿态）

### B. 模块 1 创建应用（基础信息）
4. 应用头像：**256×256** 品牌图标
5. 应用名称 + 应用简介（用户可读，不写功能清单）
6. **授权列表（OAuth 授权项）**：需与 EZR 授权服务器实际 scope 对齐（当前为 `ezr.crm.read`，如需导出/写操作要扩 scope）
7. **授权回调 URL**：向 WorkBuddy 索取其标准回调地址并登记
8. **可信 Origin 白名单**：登记 WorkBuddy 允许访问的域名
9. 创建后**立即保存 Client ID / Client Secret**（Secret 仅展示一次，关闭后不可再查看）

### C. 模块 2 首页配置（第一印象 + 使用动线）
10. 首页 Slogan（欢迎语标题）
11. **场景胶囊**：输入框上方快捷模板，建议对齐 CRM 真实高频动作（如「出月度经营报告」「门店业绩诊断」「圈一批沉默会员」）
12. **工作模式 3–5 个**：每个写 System Prompt（角色 / 术语规范 / 输出结构），并绑定对应技能。建议按角色切：品牌运营、区域/店长、导购、会员营销
13. 内置连接器：选择 `ezr-crm`（注意：内置连接器要求支持 **OAuth 认证的 MCP**，EZR 已满足；用户首次进入会有绑定弹窗走 MCP OAuth 授权）

### D. 模块 3 市场配置
14. 专家 / 专家团：可先不启用，或在第二步补
15. 技能列表：上传技能包（**先解决打包结构问题**，见风险 1）
16. 连接器列表：上传连接器包
17. 精选场景：可选开启，需关联专家或专家团

### E. 模块 4 其他配置
18. 是否跳过首次绑定应用授权（EZR 走 OAuth，**不应跳过**）
19. 绑定应用授权文案
20. 输入框占位符（**需中英文两套**）
21. 模型配置：从平台模型池勾选 + 拖动排序 + 指定默认模型（需先拿到可用模型清单）

### F. 设计素材（需按规范重做，不能直接复用连接器 icon）
22. 应用 icon：**16×16px**，线宽 **1.2px**，**有断口**，圆角平滑 **100%**，风格与官方示例一致
23. 专家页精选场景背景图：**1000×910px**，结构为**底图 + 3 层渐变蒙层**，需提供**日间 / 夜间两套**；底图建议极简插画风格

### G. 模块 5 预览调试 → 提交
24. 导出配置 JSON 本地测试验证
25. 下载对应版本 WorkBuddy 客户端，用预览链接打开预览态核对
26. 提交配置审核 → 通过即发布上线
27. 已发布应用的后续变更需**重新提交审核**

### H. 治理与合规（EZR 侧红线，必须前置完成）
28. 数据权限：所有查询默认走当前 CRM 身份权限，不猜 shop_id、不枚举门店
29. 敏感字段：导出/会员明细必须先说明字段与风险，用户确认后才建任务
30. 审计：每次导出任务、授权、下载留痕，下载地址有时效需提示
31. 最小权限：scope 只开业务必需项，导出能力单独评估

## 四、风险与待确认

1. **技能包打包结构可能不合规**：官方技能 zip 结构为 `{skill-name}/SKILL.md`。当前包是「1 个根 SKILL.md（路由）+ 14 个子技能目录」。需确认是拆成 14 个独立技能 zip，还是作为单技能 + references 提交，否则平台解析可能失败。
2. **`auth_mode` 取值需核对**：连接器包写的是 `server-side`。按官方文档，`server-side`/`gateway` 指「WorkBuddy 云端托管 OAuth，**接入前需与 WorkBuddy 团队确认**」；而 EZR 是自带授权服务器，按「MCP Server 自带 OAuth」应**省略 auth_mode** 走标准 MCP OAuth 流程。这是最可能被审核打回的点，建议先与 WorkBuddy 运营确认。
3. **`minWorkbuddyVersion: 4.24.0`** 与所用字段需一致（name_zh / examples_zh 均为 4.24.0 起支持，当前声明合理）。
4. **Client Secret 仅展示一次**，需明确由谁保管、存哪里（不得写入仓库或配置样例）。
5. **连接器 icon 与应用 icon 是两套规范**，不可复用。
6. **X 热度类外部数据**与本应用无关，但注意应用内如出现「X 热点」类内容需另作来源说明。

## 五、建议推进顺序（最小可用版本优先）

**第 1 波（1 周内）**：平台入驻 + 资质认证 + 应用基础信息提交审核；同时向 WorkBuddy 确认 3 件事（回调 URL、auth_mode 取值、模型池清单）。
**第 2 波（审核通过后）**：打通 OAuth 接入 → 上连接器 → 上 3 个最高频场景胶囊 + 3 个工作模式 → 预览验证。
**第 3 波**：补齐 14 个技能市场展示 + 设计素材 + 专家/精选场景 → 提交配置审核 → 发布。
**第 4 波**：按反馈迭代，逐步补专家团与更多行业场景。

## 附：MCP + 技能合并包（2026-09-24 已完成）

### 结论：可以合并，官方形态就是「连接器内含多个 Skill」

官方连接器结构为：
```
your-connector/
├── connector-meta.json   # 必须
├── mcp.json              # 必须
├── icon.svg              # 必须
└── skills/{skill-name}/SKILL.md   # 可选，能力多时可拆多个子目录，WorkBuddy 会全部加载
```
即 `skills/` 下允许多个技能目录并列，**合并后必须以「连接器」一种形态提交，不能同时又拆一份技能包去技能市场单独提交**（一个连接器只能选一种方案）。

### 实际合并产物 `ezr-crm-connector` v1.1.0

- 保留：`connector-meta.json`、`mcp.json`、`icon.svg`（连接器市场图标）
- `skills/` 下共 16 个技能目录：
  - `ezr-crm-brand-operator`（连接器工具使用说明，原连接器自带）
  - `ezr-crm-suite`（原技能包根路由，已升为同级技能）
  - 14 个子技能（报告 / 分析 / 查询 / 导出）

### 合并时做的必要修正

1. **路由相对链接**：`./ezr-x/SKILL.md` → `../ezr-x/SKILL.md`（14 处）——原结构根等于父级，下沉到 `skills/ezr-crm-suite/` 后必须回退一级。
2. **3 处悬空引用改写**：路由里 `@templates/report.html`、`@references/api-endpoints.md`、`@references/best-practices.md` 原本指向不存在于路由目录的资源，改为「对应子技能目录下」的文字指路，避免 AI 读取失败。
3. **移除 `auth_mode: "server-side"`**：EZR 自带 OAuth 授权服务器（实测 `/.well-known/oauth-authorization-server` 与 `/oauth/register` RFC 7591 动态注册均 200/201 通过），按官方文档应省略 auth_mode 走标准 MCP OAuth 流程；`server-side` 仅用于 WorkBuddy 云端托管 OAuth 且需事先与平台确认。
4. **版本号 1.0.1 → 1.1.0**。
5. 清理 `.DS_Store` / `__MACOSX`。

### 校验结果

- 内部引用：44 处解析成功，**0 处断裂**
- 打包：83 个文件，压缩后 162 KB
- 未发现硬编码 Token / 密钥

### 待验证风险

- 16 个 `SKILL.md` 正文合计 **约 141 KB（≈35k tokens）**。若 WorkBuddy 采用渐进式加载（只预载 name+description，正文按需读取），成本可接受；若全量预载，将明显挤占上下文。**需向平台确认加载策略**，必要时精简低频子技能正文或改为按需分包。
